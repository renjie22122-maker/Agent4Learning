# 生产级企业 Agent 平台蓝图

> 从 0 到生产的**落地顺序**、每层的架构、以及每层的验收门槛（DoD）。
> 顺序本身就是结论：`lab-03` 用可运行的方式演示了顺序错了要付多少返工代价。

---

## 一、为什么顺序不能反

真实项目最常见的翻车方式不是"某个技术点做错了"，而是**顺序错了**：

```
✗ 先做多 Agent 协作 → 上线后故障无法定位（没有 trace）
                    → 无法解释账单（没有成本归因）
                    → 无法回滚（没有灰度与开关）
                    → 最后推倒重做
```

每一层都**依赖下一层已经就位**才能验证：

- 没有观测，你无法证明优化有效（`lab-18`）；
- 没有可靠性原语，流量一大所有优化都白搭（`lab-06`）；
- 没有隔离，多租户就是随时引爆的雷（`lab-16`）；
- 没有上下文治理，成本会随对话轮数平方增长（`lab-08`）。

---

## 二、八层递进路线图

### 第 0 层：可运行的单请求链路

**做什么**：一条端到端的 agent 请求能跑通（输入 → 检索/工具 → 模型 → 结构化输出）。

**为什么先做这个**：没有最小闭环，后面所有工程都没有附着点。

**验收门槛（DoD）**
- [ ] 单请求端到端跑通，输出符合 Schema
- [ ] 有一个可重复的本地/测试环境启动命令
- [ ] 失败时返回明确错误码，而不是抛异常到用户

**缺了它会怎样**：讨论架构时没有共识对象，每个人脑子里的"agent"都不一样。

---

### 第 1 层：可观测性（**必须最先做，不是最后做**）

**做什么**：trace + metrics + 成本账本 + 结构化日志。

**为什么**：这是整个项目里唯一"越早做收益越大"的事。事后补埋点意味着你要重新
理解所有历史故障，而那些现场已经消失了。

**关键指标（最小集）**
| 类别 | 指标 |
| --- | --- |
| 链路 | 每请求耗时（P50/P95/P99）、每阶段耗时归因、LLM 调用次数、工具调用次数 |
| 质量 | 结构化输出解析失败率、任务完成率、工具选择正确率 |
| 成本 | 每请求成本、**每成功任务成本**、按租户/功能分摊、缓存命中率 |
| 资源 | 并发利用率、队列深度、最老任务 age、RSS、线程数 |
| 业务 | 成功率、人工介入率、放弃率 |

**验收门槛**
- [ ] 任意一次慢请求能在 1 分钟内定位到具体阶段
- [ ] 任意一笔花费能归因到租户 + 功能
- [ ] 每个失败请求都有可检索的错误码与 trace_id

**缺了它会怎样**：所有后续讨论变成"我觉得"。

> 对应实验：`lab-18` · 文档 `docs/answers/lab-18-observability-slo.md`

---

### 第 2 层：可靠性原语（**正确性的分界线**）

**做什么**：分层超时预算、重试策略、熔断器、舱壁隔离、限流。

**为什么**：这一层之前，系统在正常流量下能跑；这一层之后，系统在**异常流量下**
还能跑。这是 demo 与生产的真正分界线。

**核心组件**
```
Deadline       预算向下传递，child_timeout = min(阶段上限, 父剩余)
RetryPolicy    全抖动退避 + 共享重试预算（防重试风暴 3^N）
CircuitBreaker closed → open → half_open，慢调用也计入失败
Bulkhead       有界并发，满了快速失败，不排队
TokenBucket    分层限流（全局/租户/模型/工具）
```

**验收门槛**
- [ ] 上游延迟劣化 3 倍时，端到端 P95 不超客户端预算
- [ ] 上游完全挂死时，服务在预算内快速失败并返回可重试信号
- [ ] 任一依赖故障不会耗尽本进程的线程/连接
- [ ] 超 SLO 请求占比 < 1%

**缺了它会怎样**：一次上游抖动 = 一次全站故障。

> 对应实验：`lab-06`（超时熔断）、`lab-04`（限流）

---

### 第 3 层：隔离与资源治理

**做什么**：多租户隔离（会话/数据/配额/凭证）+ 批处理与交互式容量分离。

**为什么**：只要有两个以上的使用者，就一定会有"一个人影响所有人"的问题。
隔离不能事后加——它要求 key 从入口就带上，中途补会漏。

**关键设计**
- 请求入口构造 `RequestContext(tenant, user, session, trace, groups, roles)`
- **显式参数传递**，不依赖隐式上下文（隐式上下文在跨线程/跨协程时会丢）
- 权限过滤**下推到召回阶段**（filter at source），不是召回后再过滤
- 每租户独立的并发池、QPS 配额、token 预算、provider 凭证

**验收门槛**
- [ ] 跨租户/跨会话数据泄露事故 = 0（有自动化检测）
- [ ] 单租户打满配额时，其他租户的 P95 不劣化超过 20%
- [ ] 批处理高峰期交互式请求 P95 仍在 SLO 内
- [ ] 每次敏感数据访问都有审计记录

**缺了它会怎样**：企业客户的安全评审直接卡死；或者更糟——上线后才发现泄露。

> 对应实验：`lab-16`（多租户）、`lab-17`（资源治理）、`lab-04`（公平性）

---

### 第 4 层：缓存与成本

**做什么**：五层缓存体系 + 模型路由 + 预算闸门 + 成本归因。

**为什么**：成本是唯一会"随成功线性增长"的指标。用户越多、用得越顺，账单越大。
降本必须在架构层做，不能靠"提醒大家省着点用"。

**五层缓存**
| 层 | 内容 | key 要素 | TTL |
| --- | --- | --- | --- |
| L1 精确 | 相同问题的答案 | tenant + 规范化 query + model + kb_version | 分钟~小时 |
| L2 语义 | 近义问句的答案 | 同上，但用相似度匹配（有阈值风险） | 分钟 |
| L3 前缀 | 稳定 prompt 前缀 | model + prefix_hash | 小时 |
| L4 工具/检索 | 只读工具结果 | tenant + args + index_version | 秒~分钟 |
| L5 会话 | 短期记忆 | tenant + user + session | 会话期 |

**绝不能缓存**：权限相关结果、有副作用的操作、时效性强的数据、个性化创作、
含 PII 的结果、鉴权决策、路由决策。

**验收门槛**
- [ ] 缓存命中率与**错误命中率**都在监控中
- [ ] 每成功任务成本有明确目标并达标
- [ ] 降本后质量指标（准确率/完成率）没有下降
- [ ] 缓存 key 变更时有失效策略（版本号）

**缺了它会怎样**：单位经济模型不成立——用得越好亏得越多。

> 对应实验：`lab-07`、`lab-12`、`lab-13`

---

### 第 5 层：上下文与状态治理

**做什么**：上下文压缩、记忆分层、长任务 checkpoint 与幂等。

**为什么**：多轮对话的 token 成本是**平方增长**的，长任务的重跑成本是**乘以步数**的。
这两个是无形的成本黑洞。

**关键设计**
- 固定丢弃顺序：老对话 → 摘要 → 检索片段 → 工具结果；**系统指令与安全约束永不丢弃**
- 结构化状态外置（目标/已确认事实/待办/决策）放在 prompt 顶部
- 工具大结果只留摘要 + 引用 id，按需回查
- 长任务每步落盘 + 幂等键 + saga 补偿

**验收门槛**
- [ ] 第 30 轮的 prompt token 在第 1 轮的 3 倍以内
- [ ] 压缩后关键事实保留率 ≥ 95%
- [ ] 长任务失败重跑的成本 ≈ 0（只跑未完成的步骤）
- [ ] 有副作用的步骤重复执行次数 = 0

**缺了它会怎样**：成本随使用时长失控；长任务永远跑不完。

> 对应实验：`lab-08`、`lab-09`

---

### 第 6 层：工具与子 Agent 工程化

**做什么**：工具框架（Schema/超时/幂等/权限/截断）+ 子 Agent 隔离与预算。

**为什么**：工具是 agent 与外部世界的接口，也是**所有安全和副作用的入口**。

**工具必须声明**
```python
Tool(
    parameters=...,        # JSON Schema，调用前强制校验
    timeout_s=...,         # 独立超时，绝不共用主链路预算
    idempotent=...,        # 非幂等必须带幂等键
    has_side_effects=...,  # 有副作用要单独记账与补偿
    requires_roles=...,    # 权限在工程层校验
    requires_confirmation=...,  # human-in-the-loop
    max_output_tokens=..., # 结果截断上限
    max_calls_per_request=... # 循环保护
)
```

**子 Agent 的判定**
| 该开 | 不该开 |
| --- | --- |
| 需要独立的上下文空间 | 简单任务（额外开销不值得） |
| 需要收窄权限 | 强依赖父级上下文 |
| 需要独立预算与超时 | 需要与父级共享状态 |
| 多个可并行的独立探索 | 串行依赖的步骤 |

**验收门槛**
- [ ] 非法参数 100% 被拦截，且有结构化错误回灌给模型
- [ ] 工具结果不会撑爆上下文（有截断 + 引用）
- [ ] 无失控循环（四重上限都生效）
- [ ] 子 Agent 失败/超时不会拖垮父级，取消能正确传播

**缺了它会怎样**：一次工具故障或一次参数幻觉就能造成数据事故。

> 对应实验：`lab-15`、`lab-14`

---

### 第 7 层：队列、长任务与服务生命周期

**做什么**：有界任务队列、优先级与公平、租约与 DLQ；优雅启停与灰度发布。

**为什么**：前六层解决"单个请求正确"，这一层解决"系统整体可控"。

**关键设计**
- 有界队列 + 背压（满了拒绝生产者，不无限缓冲）
- 优先级：交互式 > 批处理，并且**硬性预留容量**
- 租约 + 可见性超时（worker 崩溃任务自动回归，不丢）
- 重试上限 + 指数退避 + DLQ
- 优雅停机：先摘 readiness → 等在飞排空 → 超时才强杀
- liveness **绝不**包含依赖健康（否则依赖抖动会被放大成滚动重启）

**验收门槛**
- [ ] 最老任务 age 有监控与告警（不是队列长度）
- [ ] 停机期间被掐断的请求 = 0
- [ ] 发布期间用户可见错误率没有上升
- [ ] 毒丸任务不会阻塞正常任务

**缺了它会怎样**：发布就是一次小型故障；任务堆积无人能解释。

> 对应实验：`lab-05`、`lab-01`、`lab-09`

---

### 第 8 层：评估、发布门禁与高级能力

**做什么**：离线评估集 + 在线 A/B + 灰度与回滚 + 多 Agent 协作。

**为什么放最后**：没有前面的层，评估结果无法解释，灰度无法安全回滚。
多 Agent 是**能力上限**的优化，而前面七层是**下限**的保障。先保下限。

**验收门槛**
- [ ] 有回归评估集，每次 prompt/模型变更都跑
- [ ] 灰度按租户/比例切流，能一键回滚
- [ ] 质量、成本、延迟三者有联合看板
- [ ] 每个变更都能回答"它把哪个指标改好了，代价是什么"

**缺了它会怎样**：改进变成赌博。

## 三、架构分层图

```
                    ┌─────────────────────────────────────┐
   接入层            │ 网关：鉴权 → 生成 RequestContext     │
                    │       → 全局限流 → 路由到实例         │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   生命周期层        │ readiness / liveness / 优雅停机      │
                    │ 预热：前缀缓存 + 索引 + 连接池        │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   隔离与准入层      │ 全局舱壁 → 租户舱壁 → 批处理配额     │
                    │ 四层限流（全局/租户/模型/工具）       │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   缓存层            │ L1 精确 → L2 语义 → L3 前缀          │
                    │ （命中即返回，最便宜的成功路径）      │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   检索与上下文层    │ 权限过滤下推 → 两阶段检索            │
                    │ → 会话加载 → 上下文组装（token 预算） │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   编排层            │ Deadline 分层预算                    │
                    │ 模型路由 → LLM（重试/熔断）           │
                    │ → 工具循环（有界）→ 输出契约校验      │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   状态与任务层      │ 会话存储 / checkpoint / 幂等表 / DLQ  │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
   观测层            │ trace / metrics / cost ledger / 审计  │
                    └─────────────────────────────────────┘
```

## 四、常见反模式速查

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 每层各写一个硬编码超时 | 链路总超时 = 各层之和 × 重试次数 | 预算向下传递 |
| 有界队列改成无界"避免拒绝" | 内存涨 → OOM，且延迟无上限 | 有界 + 背压 + 快速失败 |
| 依赖健康纳入 liveness | 依赖一抖就滚动重启，放大故障 | liveness 只看进程，readiness 看能力 |
| 缓存 key 不带 tenant | 越权返回别人的数据 | key 含所有影响结果的维度 |
| 会话存在全局字典/线程 local | 并发下串会话 | `(tenant, user, session)` 三元组 |
| 召回后再过滤权限 | 慢 + 已泄露到 prompt/日志 | 召回前过滤 |
| 用队列长度做堆积告警 | 长度会波动，掩盖老化 | 监控**最老任务 age** |
| 上下文"全塞进去让模型自己挑" | 成本失控 + lost in the middle | token 预算 + 固定丢弃顺序 |
| 长任务失败从头跑 | 成本 × 步数 | checkpoint + 幂等 + 续跑 |
| 让模型决定要不要重试 | 无限重试烧钱 | 重试策略由配置决定 |
| 降本只看账单不看质量 | 省的钱被返工吃掉 | 成本与质量联合度量 |
| 只看成功率不看有效吞吐 | 误判"两个版本差不多" | 看**成功/s** |
