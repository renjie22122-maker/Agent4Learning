# 审批与结构化追问：现状和建议

当前推荐宿主执行入口是 `request_execution(command, reason, timeout_s=60)`：等待授权后直接执行一次，时限随审批保存。下文保留结构化交互的设计沿革；当前环境、执行结果与单次授权规则以 [权限恢复](PERMISSION-RECOVERY.md) 为准。

## 当前已实现

request_host_command 提交精确宿主命令请求；审批页面由用户允许或拒绝。授权绑定 session、workspace、command，默认30分钟有效，一次性消费。旧聊天一句“允许”不会自动成为授权。已有绑定和一次性消费测试。

## runtime-17 已补齐

聊天内结构化问题卡片与独立的精确命令审批卡片。request_user_input 阻塞在宿主等待真实答复，不额外调用模型；回答写入 SQLite 后等待工具返回，执行链自动继续。最多 6 个建议选项，始终允许自由输入，不预先替用户提交。

request_host_command 使用同一聊天入口等待审批，普通“可以”不等于授权。授权仍绑定原有 session/workspace/command 并一次性消费。用户拒绝的相同命令不能在当前会话反复申请；沙箱错误可以申请明确授权，但只读能力限制、系统权限错误不会被问题卡片绕过。

主会话和存活的子任务都可提问，子任务问题路由到主会话。子任务等待时不占用模型并发槽。中止会唤醒等待者，未获批命令不会执行。

问题与答案跨进程保存。服务重启后，根会话回答通过恢复原会话上下文继续；并不重放未知工具操作。子任务在重启后仍采用 interrupted 规则，答案保留但需要主会话重新协调，不冒充已经恢复原子任务。

验证包含脚本模型等待、错误会话拒绝、重复答复拒绝、普通答复不授权、审批一次性消费、过期、中止、根会话重启后端路由，以及真实 API 与浏览器卡片测试。真实 API 测试中等待阶段保持 1 次模型调用，答复后第 2 次调用正常完成。

## 建议协议

- request_user_input：只用于缺失信息或偏好。显示问题、建议选项、自由输入；一次1–3个真正影响实现的问题。回答不是权限授权。
- request_approval：独立通道，显示具体动作、目标路径/命令、理由、风险、当前拒绝来源。只有宿主认可的授权主体才能批准。
- 状态持久化 pending / answered / denied / cancelled / expired，记录问题ID、会话ID、子任务ID和版本。用户多次点击不会重复执行。
- 等待时挂起相关工作单元，不调用模型空转；无依赖的工作可继续。用户未回复不能被当作默认批准。
- 答复后重新核对工作区、动作和授权有效期，动作发生变化必须重新授权。进程重启只恢复问题状态，不自动重放未知命令。
- 用户已拒绝的相同请求不反复追问。策略允许升级的权限不足可申请一次更明确的授权；系统不可覆盖的禁止与OS执行失败不能通过“用户允许”绕过。

## grill-me 模式

作为可选需求澄清模式，先指出一个会改变方案的未知项，再逐轮提问并归纳目标、约束、非目标和验收标准。需求足够明确就停止提问进入执行；不是无限问卷。不能把问题卡片用作隐式放权。

## 要补的实验

拒绝后不执行、批准后仅执行一次、答复属于错误会话时拒绝、等待时模型调用不增长、撤回/过期后不可执行、重启后仍能答复、普通澄清“可以”不会批准宿主命令、子 Agent 的问题准确路由给用户。

grill-me 是使用该工具逐个澄清关键问题的交互方式，目前没有另设独立模式按钮。自动审批目前仍以宿主权限策略和精确命令审批为基础，并非复制 Codex 内部的自动审批模型。
