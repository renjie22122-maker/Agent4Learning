# 验收清单（Acceptance Checklist）

> 这份清单有两个用途：
> ① 校验**这个项目本身**是否健康（`python verify.py` 就是它的自动化版本）；
> ② 作为你自己团队 agent 服务的**上线前检查表**——每一条都能对应到本项目的实验。

---

## 一、项目自检（自动化）

```bash
python verify.py                     # 51 个默认 lab；可选 ANN / Windows 实验需显式开启
python verify.py lab-06 lab-08       # 指定 lab
python verify.py --list              # 列出所有 lab 与运行命令
python verify.py --jobs 1 --show-fail  # 串行跑并打印失败详情（排查用）
```

验收器对每个 lab 做四项检查：

| 检查 | 通过条件 |
| --- | --- |
| 能跑通 | 退出码 0，且在超时内结束 |
| 协议完整 | `[LAB-START]` `[BROKEN-REPRODUCED]` `[FIX-APPLIED]` `[VERIFY]` `[TAKEAWAY]` `[LAB-END]` 全部存在 |
| 结论方向正确 | 每条 `[VERIFY]` 的 before → after 必须是"修复后更好" |
| 有实测数字 | 至少 1 条可解析的 `[VERIFY]` 断言 |

**为什么"结论方向"要自动校验**：教学项目最容易烂掉的方式是代码还能跑、但结论已经不成立
（有人改了个参数，P95 优化 lab 就不再体现优化，而没有任何东西会报错）。
把结论变成断言，项目才能长期保持诚实。

**指标方向约定**（写 lab 时必须遵守）：

| 指标名包含 | 方向 | 例子 |
| --- | --- | --- |
| `success` `accuracy` `recall` `hit_rate` `quality` `fairness` `goodput` `throughput` `saved` | 越大越好 | `cache_hit_rate` |
| `blocked` `caught` `rejected` `prevented` | 越大越好（拦截计数） | `session_hijack_blocked` |
| `leak` `lost` `duplicate` `unauthorized` `cross_` `wrong` `dropped` `invalid` `pollution` `deviation` `runaway` `miss` | 越少越好（事故计数） | `cross_session_leaks` |
| `good_` `_gain` `saved_` `reduction` `speedup` | 越大越好（显式标注） | `good_requests` |
| 其余（默认） | 越小越好 | `p95_latency_ms` |

> 如果某个指标**增长本身就是结论**（比如"对冲请求让成本上升了 30%"），
> 指标名要显式标注方向（如 `hedge_cost_increase`），否则会被验收器判为方向错误。
> 这不是为了绕过检查 —— 命名清晰本身就是要求。

## 二、上线前检查表（你自己的服务）

### A. 可靠性（对应 lab-06）

- [ ] 所有外部调用（LLM / 检索 / 工具 / DB）都设置了超时
- [ ] 超时值来自统一预算，**不是**各处硬编码的常数
- [ ] 子阶段预算之和会超过总预算时，由 `Deadline` 动态收敛（而不是超支）
- [ ] 重试挂在同一个 deadline 上，且有**进程级共享的重试预算**
- [ ] 只对可重试错误重试（429/503/超时）；业务错误直接失败
- [ ] 有熔断器，且**慢调用也计入失败**（不报错但很慢同样危险）
- [ ] 熔断半开时只放 1 个探针
- [ ] 舱壁满时快速失败并返回可重试信号，而不是无界排队
- [ ] 降级链存在且被测试过（大模型挂 → 中 → 小 → 缓存/模板）

### B. 隔离与限流（对应 lab-04 / lab-16 / lab-17）

- [ ] 每租户独立的并发配额与 QPS 配额
- [ ] 限流分四层：全局 / 租户 / 模型 / 工具
- [ ] 客户端自限流 ≤ 上游容量（不要把上游队列当自己的缓冲区）
- [ ] 批处理与交互式容量**硬性预留**（不是"看情况"）
- [ ] CPU 密集与 IO 密集任务分池
- [ ] 请求上下文 `(tenant, user, session)` 在入口构造并逐层断言
- [ ] 会话存储用三元组 key，且有归属校验
- [ ] 权限过滤在**召回阶段**完成（不是召回后再过滤）
- [ ] 每租户独立 provider 凭证
- [ ] 敏感数据访问写审计日志

### C. 缓存与成本（对应 lab-07 / lab-12 / lab-13）

- [ ] 缓存 key 包含所有影响结果的维度（tenant / model / 知识库版本 / 参数）
- [ ] 所有缓存都有容量上限与 TTL
- [ ] 有"不可缓存"清单并在代码层强制（权限相关/有副作用/时效性/PII）
- [ ] 前缀缓存的前缀是稳定的（易变内容不在前缀里）
- [ ] 有缓存命中率与**错误命中率**监控
- [ ] 模型路由有预算闸门（预算耗尽时降级，不是继续烧）
- [ ] 每次模型调用都有成本归因标签（租户 + 功能 + trace）
- [ ] 降本措施都有质量对照数据

### D. 上下文与状态（对应 lab-08 / lab-09）

- [ ] 上下文有 token 预算，且有**固定的丢弃顺序**
- [ ] 系统指令与安全约束永不因省 token 被丢弃
- [ ] 工具大结果只留摘要 + 引用，按需回查
- [ ] 会话状态有界（轮数上限），不会随进程运行时长增长
- [ ] 长任务每步落盘 checkpoint
- [ ] 有副作用的步骤带幂等键，且幂等表有唯一约束/原子语义
- [ ] 有补偿（saga）逻辑且被测试过
- [ ] 区分可重试错误与不可重试的业务错误

### E. 工具与输出契约（对应 lab-14 / lab-15）

- [ ] 工具参数走 JSON Schema 白名单校验
- [ ] 校验失败的结构化错误会回灌给模型（让它自我修复）
- [ ] 每个工具有独立超时
- [ ] 工具结果有截断上限与引用机制
- [ ] 工具有权限声明，且在工程层强制
- [ ] 有循环保护（单工具调用上限 + 总调用上限）
- [ ] 有副作用的工具需要确认或幂等键
- [ ] 模型输出有 Schema 校验 + 修复重试 + 兜底默认值
- [ ] 解析失败率有监控

### F. 生命周期与发布（对应 lab-01）

- [ ] `liveness` 只反映进程状态，**不包含依赖健康**
- [ ] `readiness` 反映真实服务能力（预热完成才 ready）
- [ ] 有预热流程（前缀缓存 / 索引 / 连接池）
- [ ] SIGTERM 后先摘 readiness，再排空在飞请求，最后退出
- [ ] 停机排空有 grace 上限，超时强杀并记录被中断数量
- [ ] 发布期间用户可见错误率没有上升（有验证）
- [ ] 有灰度与一键回滚能力

### G. 队列与长任务（对应 lab-05 / lab-09）

- [ ] 队列有界，满了对生产者施加背压
- [ ] 监控的是**最老任务 age**，不只是队列长度
- [ ] 有 lease / visibility timeout，worker 崩溃任务不丢
- [ ] 有重试上限 + 指数退避 + 死信队列
- [ ] 毒丸任务不会阻塞正常任务
- [ ] 交互式任务优先级高于批处理，且容量有保障

### H. 观测与 SLO（对应 lab-18）

- [ ] 每个请求有 trace_id 贯穿所有阶段
- [ ] P50/P95/P99 分阶段可归因
- [ ] 成本可按租户 / 功能归因
- [ ] 指标分四层：RED（服务）/ USE（资源）/ Agent 专有 / 业务
- [ ] Agent 专有指标齐全：LLM 调用数、工具调用数、推理轮数、检索候选数、
      解析失败率、压缩率、缓存命中率、每成功任务成本
- [ ] SLO 从用户视角定义，且有 error budget
- [ ] 有 burn-rate 告警（快烧 + 慢烧双窗口）
- [ ] 告警是**症状导向**的（用户可感知），不是原因导向的
- [ ] 告警误报率在可接受范围（有统计）

## 三、常见"看起来通过其实没过"的检查

| 表面通过 | 为什么不算过 |
| --- | --- |
| 成功率 99%，但只统计成功进入的请求 | 被拒绝/超时的请求没进分母，成功率被美化 |
| P95 达标，但失败请求耗时记为 0 | 失败请求同样占用用户等待时间，必须计入 |
| 缓存命中率高 | 可能包含错误命中（语义缓存阈值太低）；要看**错误命中率** |
| 成本下降 | 可能牺牲了质量；必须与质量指标联合看 |
| 吞吐提升 | 可能是成功率下降换来的；要看**有效吞吐（成功/s）** |
| 没有内存泄漏 | 要区分"能 GC 回收的膨胀"和"不回收的泄漏"，做 GC 前后对比 |
| 无越权 | 需要有**主动构造攻击**的测试，而不是"我们没发现" |
| 停机不报错 | 要看被掐断的请求数，而不是只看进程退出码 |
| 降本后账单下降 | 要看**每成功任务成本**，而不是总账单（请求少了账单自然少） |
| 压缩测试全绿 | 如果 fixture 太小，剪枝后压力就掉到阈值以下 —— **摘要层根本没跑到**，断言全是假绿。必须先断言"剪枝后仍超阈值"这个前置条件 |
| 提交表单校验通过 | 空任务被接受会真的启动一个注定失败的任务并花钱。校验必须在**提交时**拒绝，而不是放进去跑一轮再失败 |
| 摘要"压缩得很干净" | 压缩最危险的失败是**把约束弄丢**：模型自己写的摘要不能作为任务书的替代。用户的原始指令必须逐字保留，不能被转述 |
| 不变量检查"没有报错" | 可能是**根本没跑**。勾子挂上了但事件名写错、或者分发方只传了事件数据没传事件类型 —— 检查会静默空转，而报告上一切正常。所以必须区分「没有违规」和「没有检查」 |
| 多轮追问"能用" | 要看**第二次请求里带没带上第一轮的工具结果**。不带的话每轮都从零开始：模型重新 `list_dir`、重新读文件、重复问同样的问题。单轮看着还行，连着用完全没法用 |
| 工作区"能选" | 白名单只允许两个目录 = 用户**根本选不了自己的项目**。要问的是"用户能不能选到他真正要用的目录"，而不是"有没有选择器" |

> **本轮实测抓到的几个真缺陷**（都是靠不变量/测试暴露的，不是靠人翻代码）：
>
> 1. **`summarize()` 把用户任务书折进了模型摘要**。它只固化 `messages[:2]`
>    里的 `system` 消息；真实历史是 `[system, user 任务书, ...]`，于是
>    任务书被丢进 `old` 交给模型"转述"。修法：保留连续 system 前缀 +
>    紧跟的第一条 user。**发现它的是一条"fixture 有效性"断言** ——
>    原来的测试 fixture 太小（7k tokens，剪枝后就低于阈值），
>    `summarize()` 一次都没被调用，5 条断言全是假绿。
> 2. **`dispatch` 只传事件数据、不传事件类型**，于是 `session_invariant`
>    按 `ev.kind` 读到的永远是空串，**所有分支都不命中** ——
>    检查等于没跑，而报告上只有一条被去重合并掉的"检查自身异常"。
>    修法：分发一律给完整 Event 对象；钩子绝不猜入参形状。
> 3. **每一轮的 `step/end` 从来没写过**。循环只在整体结束时写一条，
>    于是 18 轮的会话日志里只有 1 条 `step/end`。后果：无法回答
>    "第 3 轮花了多久"；而且"每个 step/start 都有配对 step/end"
>    这条不变量立不住，只能放宽成"允许 17 个中间悬空" ——
>    **放宽后的检查等于没检查**。
> 4. **续轮的轮次编号从 1 重来**，日志里出现"轮次回退：0 出现在 2 之后"。
>    "第几轮出的问题"这个归因直接失效。
> 5. **一个缩进错误让任务第一次工具调用后就撞硬上限**：
>    `break` 落在了内层 `for call in tool_calls` 的 `else` 里，
>    只跳出内层，外层 while 继续空转 80 轮。表现正是用户看到的
>    "只有一步对话"。
>
> 共同点：**它们全都不报错**。没有不变量和"前置条件断言"，
> 这五个都会以"功能看起来正常"的形式留在代码里。

> **真实案例（本项目踩到过）**：`tools/test_compaction.py` 曾用 60 轮 × 200 字符的
> 合成历史测摘要层，总量只有 ~7k tokens —— 剪枝之后必然低于阈值，`summarize()`
> 一次都没被调用，而 5 条断言全部"通过"。修好 fixture（让不可剪枝的 assistant
> 文本承担足够份额）之后，立刻暴露出一个真 bug：`summarize()` 只固化
> `messages[:2]` 里的 `system` 消息，**用户的原始任务书被折进了模型摘要**。
> 结论：测试的 fixture 规模本身就是被测量对象；先断言前置条件，再断言结果。

## 四、快速自检脚本

```bash
# 项目本身
python verify.py --jobs 4

# Capstone 平台（含 SLO 合规判定，退出码 0 表示达标）
python -m agentplat.run --mode fixed

# 指定参数做实验
python -m agentplat.run --mode both --seed 42
python -m agentplat.run --dump-config
```

`agentplat.run` 的退出码约定：SLO 达标 ≥ 4 项返回 0，否则返回 1。
这个约定让它可以放进 CI —— **平台本身的健康度也是可自动校验的**。
