# 必须硬编码的边界清单（Hardcode Boundary）

> 这是全项目最重要的一份清单。核心命题：
>
> **Agent 的能力可以交给模型，Agent 的正确性不能交给模型。**
>
> 判据只有一条：**这件事做错了，是会"答得不太好"，还是会"造成不可逆的后果"?**
> 前者可以交给模型，后者必须是代码。

---

## 一、总原则

### 1. 三条硬性判据（满足任一条 → 必须硬编码）

| 判据 | 说明 | 反例（交给模型的后果） |
| --- | --- | --- |
| **有副作用** | 会改变外部世界状态 | 重复下单、重复发通知、重复扣款 |
| **涉及权限或金钱** | 越权、金额、配额、预算 | 越权读取、金额写错一个量级 |
| **影响控制流** | 决定"继续/停止/重试/降级" | 无限循环、提前退出、无限重试烧钱 |

### 2. 一句话记法

> **凡是"错了要写事故报告"的，都写进代码；
> 凡是"错了只是不够漂亮"的，才交给模型。**

### 3. 兜底原则

即使某件事交给了模型，也必须有**工程兜底**：

```
模型输出 → Schema 校验 → 业务规则校验 → 上限/白名单 → 兜底默认值 → 记录偏离
```

模型可以"建议"，但**不能"决定"**。

## 二、必须硬编码的清单

| # | 事项 | 为什么不能交给模型 | 正确做法 | 实验 |
| --- | --- | --- | --- | --- |
| 1 | **鉴权与授权** | 模型可以被 prompt injection 说服；而且它根本不知道真实 ACL | 在数据访问层强制过滤（filter at source）；LLM 永不参与授权判断 | `lab-14` `lab-16` |
| 2 | **金额 / 额度 / 配额计算** | 数值幻觉；无金额上限概念 | 确定性代码计算 + 上限校验 + 超限二次确认 | `lab-14` |
| 3 | **循环与终止条件** | 模型倾向"再做一步看看"，无法自我终止 | 最大迭代数 / 最大工具调用数 / token 预算 / wall-clock 预算，四者都要有 | `lab-14` `lab-15` |
| 4 | **幂等与副作用控制** | 模型不记得"刚才已经做过了" | 幂等键由工程生成（`run_id + step`），执行前查表 | `lab-09` `lab-14` |
| 5 | **工具参数校验** | 参数幻觉：编造字段名、类型错误、注入 | JSON Schema 白名单校验 + 转义 + 路径/命令白名单 | `lab-14` `lab-15` |
| 6 | **输出结构契约** | 模型"通常"会返回 JSON，但不保证 | Schema 校验 + 修复重试 + 兜底默认值 + 观测解析失败率 | `lab-14` |
| 7 | **缓存 key 与 TTL** | 模型无法感知租户维度与数据时效 | key 含 `(tenant, query, model, kb_version)`；TTL 按数据类型配置 | `lab-07` |
| 8 | **会话 ID 与上下文归属** | 模型不知道"这是谁的会话" | `(tenant, user, session)` 三元组在入口生成并每层断言 | `lab-16` |
| 9 | **超时预算与重试策略** | 模型没有时间概念，也无法感知全局负载 | 分层 `Deadline` 传递 + 全抖动退避 + 共享重试预算 | `lab-06` |
| 10 | **熔断与降级阈值** | 模型看不到自己的错误率与延迟分布 | 配置化阈值 + 状态机；半开只放 1 个探针 | `lab-06` `lab-13` |
| 11 | **模型路由决策** | 模型无法知道实时预算、灰度状态、上游健康 | 复杂度规则 + 级联升级 + 预算闸门 + 降级链，全部代码化 | `lab-13` |
| 12 | **限流配额** | 模型不知道其他租户的存在 | 四层令牌桶（全局/租户/模型/工具）+ 公平排队 | `lab-04` |
| 13 | **上下文裁剪顺序** | 模型无法可靠地"忘记"指定内容，也不会主动省 token | 固定丢弃顺序；**系统指令与安全约束永不丢弃** | `lab-08` |
| 14 | **Prompt 前缀边界** | 模型不感知缓存，放进时间戳就会让缓存全 miss | 稳定前缀在前、易变内容在后，由 `PromptPrefixBuilder` 强制 | `lab-07` |
| 15 | **批处理与交互式的容量分配** | 模型不知道谁在等待 | 硬性容量预留（批处理 ≤ 70%），不能"看情况" | `lab-17` |
| 16 | **数据保留与删除** | 合规要求，不可协商 | 按策略硬编码 TTL 与删除流程，并有审计 | `lab-16` |
| 17 | **审计日志** | 模型不会为自己留证据 | 每次敏感数据访问强制写审计（who/what/when/why/结果） | `lab-16` |
| 18 | **密钥与凭证隔离** | 模型可能把凭证写进输出 | 每租户独立凭证，只在下游注入，永不进 prompt | `lab-16` |
| 19 | **PII / 敏感信息脱敏** | 模型不区分"可以复述"和"可以外传" | 出口统一脱敏，硬编码规则 + 正则 + 白名单 | `lab-07` `lab-16` |
| 20 | **故障时的用户可见状态** | 模型会"礼貌地编一个答案" | 失败就给明确的降级/失败状态，不允许模型掩盖失败 | `lab-06` `lab-18` |

## 三、可以（也应该）交给模型的部分

不要走另一个极端——把一切都硬编码，那就退化成传统规则引擎了。以下这些**恰恰是模型的价值所在**：

| 事项 | 为什么适合模型 | 需要的兜底 |
| --- | --- | --- |
| 自然语言理解与意图识别 | 规则写不全 | 低置信度时澄清而不是猜 |
| 检索查询改写 / 扩写 | 语言变体太多 | 改写结果仍走同一套检索与权限过滤 |
| **工具选择** | 组合爆炸，规则写不完 | 工具集本身受权限收窄；调用次数有上限 |
| 任务拆解与计划 | 需要语义理解 | 计划执行前做可行性/预算校验 |
| 回答措辞与风格 | 纯表达问题 | 事实来自检索，不由模型编 |
| 摘要与信息抽取 | 模型强项 | 关键字段用 Schema 校验 + 与原文比对 |
| 代码/文本生成 | 模型强项 | 输出经沙箱/校验后使用 |

## 四、决策归属表（交付物）

| 事项 | 归属 | 理由 | 兜底策略 |
| --- | --- | --- | --- |
| 用户能否访问某文档 | **工程** | 越权不可逆，模型可被诱导 | 召回前过滤 + 行级断言，双保险 |
| 下单价 / 退款额 | **工程** | 金额错误不可逆 | 确定性计算 + 上限 + 二次确认 |
| 是否继续循环 | **工程** | 失控烧钱 | 四重上限（迭代/工具/token/时间） |
| 这个操作是否已执行过 | **工程** | 幂等必须可靠 | 幂等键查表，先查后做 |
| 工具入参是否合法 | **工程** | 注入风险 | Schema 白名单 + 转义 |
| 输出是否符合契约 | **工程** | 下游解析会崩 | Schema 校验 + 修复 + 兜底 |
| 这条结果能否缓存 | **工程** | 越权 / 脏数据 | 声明式策略表 + 按租户隔离 key |
| 用哪个模型 | **工程** | 依赖实时预算与健康度 | 规则路由 + 预算闸门 + 降级链 |
| 配额给谁多少 | **工程** | 公平性与商业决策 | 配置化配额 + 公平排队 |
| 该调用哪个工具 | **模型** | 组合爆炸 | 权限收窄的工具集 + 调用上限 |
| 查询该怎么改写 | **模型** | 语言多样性 | 改写后仍走权限过滤 |
| 任务怎么拆 | **模型** | 需要语义理解 | 执行前预算校验 + 步骤数上限 |
| 怎么措辞回答 | **模型** | 纯表达 | 事实必须来自检索结果 |
| 要不要人工介入 | **人**（模型只建议） | 责任归属 | 模型给置信度，阈值由工程定 |

## 五、自检问题清单

在设计任何一个 Agent 流程时，对每一步问这四个问题：

1. **这一步做错了，最坏后果是什么？** —— 不可逆就硬编码。
2. **模型能否知道做这一步所需的全部信息？** —— 信息不在 prompt 里就别让它决定
   （比如实时预算、其他租户的存在、全局错误率）。
3. **模型输出被恶意构造的输入影响会怎样？** —— 涉及权限和副作用就必须独立校验。
4. **这一步失败了，我的兜底是什么？** —— 没有兜底的步骤不要上线。
