# 从 0 搭建一个生产级的企业级 agent 平台，核心落地的工程顺序是什么？

> 对应实验：`labs\lab_03_task_startup_order.py` · 运行：`python -m labs.lab_03_task_startup_order`
> 实测耗时 6.5s，5 条 `[VERIFY]`，2 条 `[BROKEN-REPRODUCED]`；其中"缺了某一层会怎样"
> 的三个故障是**真实跑出来的**（真实部署代价 + 真实计时 + 真实成本对账）。

## 一句话答案

**顺序不是"哪个功能酷"，而是依赖顺序：先建观测与可靠性，再建能力。**

```
L1 单请求链路 + 打点(trace/metrics/cost ledger)   ← 一切的地基：没有它，后面全是盲飞
L2 可靠性原语(Deadline/Retry/Breaker/Bulkhead)    ← 用 L1 的指标验收
L3 缓存与成本治理                                  ← 用 L1 的成本账验收
L4 上下文与状态治理                                ← 用 L1 的 token 打点验收
L5 权限与多租户隔离                                ← 合规底线，必须在放量前
L6 队列与长任务治理                                ← 在线稳定之后再啃离线
L7 评估与发布门禁                                  ← 把前面六层固化成"不许退化"
L8 多智能体 / 高级能力                             ← 复杂度的放大器，永远最后
```

**每一层的交付物不是"功能"，而是"下一层能用的度量与门禁"。** 顺序错了不是"晚点做"，
而是要用**返工 + 事故**来买。实测代价：错误顺序返工 **164 人时**、正确顺序 **12 人时**；
上线时的发布门禁覆盖 **2/15 vs 15/15**。

## 先复现：不做防护会发生什么

"错误顺序"团队：先做多智能体协作编排 + 花哨工具 + demo 打磨（虚拟时钟 6.5 周），
带着 2 个门禁（单元测试 + 手工回归）上线，然后被现实教育：

```
[BROKEN-REPRODUCED] 错误顺序：第 6.5 周上线，只覆盖 2/15 个发布门禁；一次 LLM 段变慢的
故障，没有 trace 只能猜 4 轮、归因耗时 1857ms（生产上就是 4 次发布 + 复现）
[BROKEN-REPRODUCED] 缺观测/可靠性/成本账的三连击：归因靠猜 1857ms、一次抖动等满 2667ms、
账单错摊 55.2%（租户模型档位不同，请求数 ≠ 成本）
```

三个"缺了它就会发生"的故障，都是真实跑出来的：

| 缺哪一层 | 实测故障 | 真实代价的换算 |
| --- | --- | --- |
| **L1 观测（trace）** | 8 段链路里 LLM 段被拖慢 4 倍（220ms），没有 trace 只能一段一段加打点、发布、复现：**猜了 4 轮、1857ms** | 每一轮 = 改代码 + 提测 + 发布 + 等就绪 + 复现；本 lab 用 180ms 代表一轮，生产上 ≈ 20 分钟/轮 → 归因 ≈ 80 分钟起步 |
| **L2 可靠性（deadline）** | 上游"连上了但永不返回"（挂死 2s），没有预算只能等满 **2667ms**；有 500ms 预算则 **515ms** 自救 | 这 2.1s 的差会被乘以并发数，直接变成线程池占用与雪崩起点（见 lab-02） |
| **L3 成本账（cost ledger）** | 36 次调用共 $0.0115。没有 ledger 只能用"请求数占比"摊总账单，**错摊率 55.2%** | 租户 A 用 large、B 用 mid、C 用 small：请求数各 1/3，真实成本却是 $0.01014 / $0.00122 / $0.00010 —— **请求数 ≠ 成本** |

有 trace 的那一侧：跑一轮带 span 的请求 + 读表，**归因耗时 303ms**，
直接指出 `llm` 段吃掉 220ms：

```
┌─ 耗时归因（按顶层 span） ──────────────────────────────
│ agent_request      1   284.9ms
│ llm                1   220.5ms     ← 一眼看出是谁
│ retrieve           1    18.9ms
│ tools              1    16.4ms
│ ...（其余段均 < 13ms）
```

## 根因分析

1. **每一层都是下一层的"验收工具"，不是并列的功能模块。**
   L2 的可靠性做得对不对，只能靠 L1 的指标来判（P95 是否 ≤ SLO、重试是否在预算内）；
   L3 的降本有没有效果，只能靠 L1 的成本账对账。跳过 L1 直接做 L2/L3，
   等于"改了但不知道有没有变好"。

2. **缺失的地基不会消失，它会在事故里以更高的价格出现。**
   实测模型：事故定位止血 3×12h + 事故压力下补 L1~L7 的溢价 148h×25%
   + 给已建功能补打点/补可靠性 260h×35%（要动已有代码 + 回归）
   = **164 人时**；而正确顺序只需要预留 12h 重构。

3. **返工成本远高于新建成本，因为要"动已上线的东西"。**
   给还没打点的功能补 trace，要改接口、改调用链、重跑回归、再灰度 ——
   这是 35% 的存量工时比例，而不是 0。

4. **事故是有外部成本的。** 没有 trace/预算/成本账时，故障不是"慢一点"，
   而是"无法定位、无法回滚、账单无法解释"。这三件事在 ToB 场景里都是合同级问题。

5. **高级能力（多智能体）是复杂度的放大器，不是地基。**
   它会把"一次调用"变成"十次调用 + 状态同步 + 部分失败"，于是 L1~L6 的每一个缺陷
   都会被放大一个数量级。先建能力再补地基，等于在流沙上盖楼。

6. **门禁（gate）是把顺序固化的唯一手段。**
   实测错误顺序上线时只覆盖 **2/15** 个门禁（13%），意味着 87% 的退化路径
   没有任何自动化拦截 —— 只能靠用户投诉发现回归。

## 生产做法

每一层：**为什么必须在这一层之前完成 → 缺了它的典型故障 → 验收门槛（可度量 DoD）→
建议动作清单**。

| 层 | 建议投入 | 前置依赖 | 缺了它的典型故障 | 验收门槛（DoD） |
| --- | --- | --- | --- | --- |
| **L1 单请求链路 + 打点** | 24 人时 | — | 故障无法归因，只能靠猜（实测 1857ms / 4 轮发布） | 每个请求有 trace_id；P95 可按阶段归因；成本可按 tenant/tag 出账 |
| **L2 可靠性原语** | 20 人时 | L1 | 一次上游抖动拖死整链路（实测等满 2667ms） | 端到端预算 ≤ SLO；重试在预算内；熔断状态可观测 |
| **L3 缓存与成本治理** | 18 人时 | L1,L2 | 账单无处归因、成本随流量线性涨（实测错摊 55.2%） | 前缀缓存命中率、单位请求成本可对账（误差 < 5%） |
| **L4 上下文与状态治理** | 20 人时 | L1 | 上下文爆炸、长会话不可控、成本失控 | 上下文分级裁剪；会话状态可持久化与恢复 |
| **L5 权限与多租户隔离** | 22 人时 | L1,L2,L3 | 越权检索 / 串租户（合规事故，后果最重） | 召回阶段即完成权限过滤；租户维度配额与隔离 |
| **L6 队列与长任务治理** | 24 人时 | L2,L4 | 长任务丢失、无法断点续跑、重试产生重复副作用 | 任务可重入 + 幂等；有界队列 + 背压；断点可续 |
| **L7 评估与发布门禁** | 20 人时 | L1..L6 | 回归不可发现，只能靠用户投诉 | 黄金集回归达标才可发布；门禁接进 CI |
| **L8 多智能体 / 高级能力** | 28 人时 | L1..L7 | 把复杂度建在流沙上：出问题无法定位、无法回滚 | 协作链路有预算、有评估、有回滚开关 |

（合计交付 **15** 个发布门禁：L1 三个、L2 两个、L3 两个、L4 一个、L5 两个、
L6 两个、L7 三个。）

### 每层动作清单

| 层 | 动作清单 |
| --- | --- |
| L1 | 定 trace_id 规范 → 接 Tracer/METRICS/CostLedger → 每个 span 打 tenant/tag → 把「单请求可归因」写进 CI |
| L2 | 给每个外部调用定预算 → 重试挂同一 deadline → 舱壁限并发 → 熔断阈值按 P99 设 |
| L3 | 稳定前缀提到最前 → 结果缓存加 TTL/容量上限 → 单位成本看板 → 超预算告警 |
| L4 | 上下文分层(系统/记忆/检索/对话) → 硬性 token 预算裁剪 → 状态外置到存储 |
| L5 | 权限过滤下推到召回 → 租户维度限流/舱壁 → 审计日志 → 越权回归用例 |
| L6 | 任务状态机 + 幂等键 → 有界队列与背压 → 断点快照 → 死信队列与人工兜底 |
| L7 | 建黄金集(含长尾/对抗样本) → 离线评估脚本 → 门禁接 CI → 灰度+自动回滚 |
| L8 | 子 agent 各自带预算与超时 → 协作链路纳入 trace → 用 L7 的评估验收收益 |

### 两种顺序的账（实测推演）

| 指标 | 错误顺序 | 正确顺序 | 说明 |
| --- | --- | --- | --- |
| 首次上线时间（虚拟时钟） | 第 **6.5** 周 | 第 **3.7** 周 | 正确顺序反而**更早上线**：地基只有 148 人时，而"花哨能力"是 260 人时 |
| 上线时覆盖的发布门禁 | **2/15**（13%） | **15/15**（100%） | 门禁是"能不能发现回归"的能力 |
| 首月事故 | **3** 起 × 12h | 0 | 缺 trace/预算/成本账，故障必然暴露给用户 |
| 返工工时 | **164 人时** | **12 人时** | = 事故止血 36h + 压力下补地基溢价 37h + 给已建功能补打点 91h |

**关键洞察：正确顺序并不慢。** 地基（L1~L7）148 人时 ≈ 3.7 周，
而错误顺序把 260 人时花在了高级能力上、第 6.5 周才上线，然后还要再花 164 人时返工。
**先打地基既更快上线，也更便宜。**

## 常见错误认知

1. **"先把多智能体编排做出来，其他后面再补。"**
   错。多智能体是复杂度的**放大器**：它把一次调用变成十次调用 + 状态同步 + 部分失败，
   于是观测/预算/成本/幂等的每一个缺陷都会被放大一个数量级。
   实测：先做能力的团队第 6.5 周上线、2/15 门禁、首月 3 起事故、返工 164 人时。

2. **"打点（trace/metrics/cost）是运维的事，不影响功能交付。"**
   错。没有 L1，L2/L3 都**无法验收**：你说"N 秒预算够用"、"成本降了"，
   拿什么证明？实测没有 trace 时，一次变慢故障的归因要猜 4 轮（1857ms，生产上 ≈ 80 分钟起）。

3. **"日志打全一点就行，不需要 trace。"**
   错。日志是**文本流**，trace 是**结构化的父子 span + 耗时归因**。
   实测有 trace 时的归因是"读表 303ms，直接指出 llm 段 220ms"；
   日志要人工拼时间线，且无法自动算出"谁吃掉了 P95"。

4. **"成本优化等账单变贵了再做。"**
   错。没有按 tenant/tag 记账，账单**无法归因**：实测按请求数摊总账单的错摊率
   **55.2%**（三个租户请求数相同、成本差 100 倍）。这不是"晚点做"，是"做不了"。

5. **"权限/多租户可以等有企业客户了再加。"**
   错。多租户隔离是**架构属性**，不是功能开关：召回阶段的权限过滤、
   租户维度的配额与舱壁、会话隔离的 key 设计，都要在放量前定好，
   后补等于把数据访问层全部重写（且已经泄露过的数据收不回来）。

6. **"门禁太重，会拖慢发布速度。"**
   错。门禁是**唯一能把前面六层固化下来的机制**。实测错误顺序 2/15 门禁，
   意味着 87% 的退化路径没有任何自动化拦截 —— 省下的时间会以"用户投诉 + 回滚"还回去。

7. **"顺序对了，但可以并行推进几层。"**
   部分对：层内可以并行，**层间不能倒置**。L4（上下文）不依赖 L2，可以并行；
   但 L3（成本）依赖 L1/L2 的度量口径，L7（门禁）依赖 L1~L6 的指标 ——
   倒过来做，就只能返工。
