# 生产环境并发量一高 agent 就会 panic，核心原因是什么？最常见的生产环节内存泄漏有哪几种，如何排查修复？

> 对应实验：`labs\lab_02_concurrency_memory.py` · 运行：`python -m labs.lab_02_concurrency_memory`
> 实测耗时 3.5s，6 条 `[VERIFY]`，2 条 `[BROKEN-REPRODUCED]`，5 个泄漏案例各带
> 真实 `tracemalloc` top-5 分配点与 `gc.get_objects()` 计数。

## 一句话答案

**并发一高就 panic 的第一性原因是「没有上限」**，不是模型慢、也不是机器小：

- 队列无界 → 请求上下文全部驻留内存（实测 RSS **+66.9MB**）
- 线程无界 → 一请求一线程（实测峰值 **241** 个线程）
- 上游肯排队 → 排队时间变成超时（实测 P95 **1912ms**）
- 重试无预算 → 流量再放大（失败 46/240，成本照样计费）

**内存一直涨 = 有一处长生命周期容器在攒对象。** 生产上最高频的五种泄漏是：
① 全局缓存无上限　② 全局 list 追加（"只是记个日志"）　③ 闭包/回调持有大对象
④ `threading.local` / 线程池没清理　⑤ 未完成的 asyncio task 持有引用。

排查三件套（顺序不能反）：**RSS 曲线 → `gc.get_objects()` 对象计数 → `tracemalloc` top 分配点**。
判据只有一条：**`gc.collect()` 之后能回收的叫内存膨胀，不能回收的才叫泄漏。**

## 先复现：不做防护会发生什么

同一份 240 并发负载、同一个"很挤"的上游（3 个并发槽 + 近无限等待队列）：

```
[BROKEN-REPRODUCED] v0：240 并发（一请求一线程 + 256KB 上下文）→ RSS +66.9MB、
峰值线程 241、峰值队列 236、P95=1912ms、失败 46/240（内存涨+延迟涨+错误率涨同时发生）
```

传递链（每条都有实测数字）：

```
无界接收 240 并发
  → 每个请求真的分配 256KB 上下文并挂在无界队列上   RSS 曲线 [25.6, 86.2, 73.7, 61.7, 51.8, 40.5]
  → 一请求一线程                                    峰值线程 241 ≈ 请求数
  → 全部挤向只有 3 个槽的上游                       峰值队列深度 236
  → 排队计入客户端预算 → 超时                        错误 429×29 / 503×11 / TIMEOUT×6
  → 硬编码重试 3 次（不看预算）                      P95 1912ms、成本 $0.00377（失败也计费）
```

修复版（有界队列 16 + 背压 + 8 worker + 单次尝试 + 端到端预算）：

```
v1：峰值队列 16、峰值线程 77、RSS +4.5MB、P95=1016ms、成本 $0.00225
```

五种泄漏的实测现场（每种都制造 80 个请求上下文，每个 256KB）：

| 泄漏 | 现场实测 | 修复后残留 |
| --- | --- | --- |
| ① 全局缓存无上限 | RSS +20.7MB / Python 堆 +20.1MB，gc 中存活 **80** 个 | 32 个（有界缓存按容量留，不再增长） |
| ② 全局 list 追加 | 同上，日志条数 = 请求数 | **0** |
| ③ 闭包/回调持有大对象 | 同上，回调表长度 = 历史请求数 | **0** |
| ④ thread-local / 线程池 | **RSS +-0.2MB**、Python 堆 +0.0MB，但 gc 中存活 **80** 个 | **0** |
| ⑤ 未完成的 asyncio task | RSS +20.9MB / Python 堆 +20.2MB，存活 **80** 个 | **0** |

第 ④ 行是最有教学价值的一行：**它的 RSS 几乎没有动**（分配器复用了之前释放的
arena），但 `gc.get_objects()` 里确确实实多了 80 个对象。这就是"只看 RSS 会漏掉泄漏"
的实证。

## 根因分析

### 一、panic 的机制：正反馈雪崩

1. **无界接收 = 把上游的容量问题变成自己的内存问题。**
   上游只有 3 个并发槽，本地却接了 240 个请求；这 237 个"多出来"的请求全部以
   "请求上下文"的形式躺在内存里（实测峰值队列 236 × 256KB ≈ 60MB）。

2. **排队是有成本的，而且是复利的。** 每个请求的预算里包含排队时间，
   队列越深 → 排队越久 → 越容易超时 → 超时触发重试 → 队列更深。

3. **重试是放大器，不是修复手段。** v0 硬编码重试 3 次，在上游已经排爆时
   等于把流量再乘 3；而且 provider 是"先计量再计算"，**超时和失败的调用照样计 token 成本**
   （实测 v0 成本 $0.00377 vs v1 $0.00225，-40.3%）。

4. **线程数上涨带来的是上下文切换与调度开销。** 241 个线程抢 3 个上游槽，
   大部分时间在做条件变量唤醒/睡眠，CPU 在"调度"而不是"干活"。

5. **没有快速失败通道，就没有止损点。** 所有请求都在"等着变好"，
   而系统需要的恰恰是"立刻告诉一部分请求：现在不行，稍后再来"。

### 二、内存泄漏的机制：长生命周期容器 + 强引用

1. **"缓存"和"泄漏"的区别不是意图，而是有没有上限。**
   有容量上限 + TTL 的缓存是资产；没有上限的 dict 就是泄漏（实测 80 个请求 = 80 个常驻对象）。

2. **闭包会意外地把整条对象图钉住。** 回调捕获的是 `ctx`，而 `ctx` 里挂着
   prompt、消息列表、检索结果（本 lab 是 256KB payload）。"取消请求"如果只改状态位
   而不注销回调，对象就永远可达。

3. **长生命周期 worker 是"每任务累积"的放大镜。**
   线程池里的线程活到进程结束，挂在 `threading.local` 上的 per-request 数据
   不会自己掉 —— 线程退出才会顺带释放，而真实线程池的线程不会退出。

4. **未完成的协程任务既占内存又占语义。** `create_task` 之后不 await 不 cancel，
   任务与闭包一起挂在事件循环上；同时"这个任务到底做没做"也永远没有答案。

5. **RSS 不是泄漏的可靠指标。** 分配器会把释放的内存留在 arena 里复用
   （实测 ④ 的 RSS 变化 ≈ 0），所以必须用"对象计数 + 可达性"来判定。

## 生产做法

| # | 做法 | 做什么 | 为什么 | 代价 / 边界 |
| --- | --- | --- | --- | --- |
| 1 | **有界队列 + 背压** | `Queue(maxsize=16)`，满则等一小段（实测 0.30s）后**快速失败** | 把"内存里排队"换成"明确拒绝"，RSS +66.9MB → +4.5MB | 拒绝率上升（实测 97/240 `QUEUE_FULL`）；必须有 429/503 + `Retry-After` 语义，否则客户端会立刻重试把压力打回来 |
| 2 | **有界并发（舱壁）** | 调用方线程数、worker 数都固定（实测 241 → 77 线程） | 线程数是资源，不是免费的；上下文切换会吃掉吞吐 | 并发上限要按上游 P99 容量定；太小会让长尾请求把池子占满（需要配合 deadline） |
| 3 | **单次尝试 + 端到端预算** | 一次调用，超时由 deadline 推导；不做无预算重试 | 重试在上游排爆时等于自我 DDoS（成本 -40.3%） | 瞬时抖动的自愈能力下降，需要靠"上游健康度 + 熔断"补，而不是无脑重试 |
| 4 | **BoundedLRU** | `OrderedDict` 手写：容量上限 + TTL + 命中/淘汰计数 | 缓存必须"占**有上限**的内存"（残留 32 个而不是 80 且不再增长） | 命中率会下降；TTL 要按数据变更频率定，太长会读到脏数据 |
| 5 | **有界日志（deque maxlen）** | 只记摘要（id / token 数），不记对象 | "记个日志"不该把请求上下文挂到全局 | 排查时需要原始上下文 → 用采样/按需 dump，不要全量常驻 |
| 6 | **weakref** | 回调/注册表持弱引用，或取消时显式 unregister | 让"请求结束"等于"对象可回收" | 弱引用可能返回 None，调用方必须处理；关键回调不能只靠弱引用（会被提前回收） |
| 7 | **显式清理 / cancel** | 每个任务结束 `finally` 清理 thread-local；asyncio 任务 `cancel + gather` 并从注册表摘掉 | 长生命周期容器是泄漏高发区（残留 80 → 0） | `cancel` 的异常 traceback 也会钉住帧，收尾要 `await` 收敛 |
| 8 | **观测三件套** | RSS 曲线 + `gc.get_objects()` 计数 + `tracemalloc` top-5 | 只有曲线看不出泄漏；只有计数不知道在哪；只有分配点不知道是否可达 | `tracemalloc` 有性能开销，生产上按需开启（采样或低频快照） |

**判据：泄漏 vs 膨胀**

```
gc.collect()
  ├─ 对象数回落、RSS 不回落  → 内存膨胀（分配器持有 arena，可复用，不是泄漏）
  └─ 对象数不回落            → 真泄漏（还有强引用链，必须找到持有者）
```

本 lab 五类泄漏在 `gc.collect()` 之后对象数都**不回落**（80 个仍在），放掉引用后
RSS 才慢慢回落 —— 两个现象同时打印，就是为了说清这个区别。

## 常见错误认知

1. **"并发高就 panic 是因为机器不够，加内存/加机器就好。"**
   错。实测瓶颈是"没有上限"：加内存只会让峰值队列更深（236 → 更大），
   加机器则会把同样的雪崩复制到更多实例上。先加边界（队列/线程/预算），再看容量。

2. **"重试是可靠性手段，越多越安全。"**
   错。上游排爆时重试是**放大器**：v0 硬编码 3 次重试，超时也照样计费，
   实测成本比 v1 高 40.3%。重试必须挂在同一个 deadline 上，并有共享预算。

3. **"RSS 一直涨就是内存泄漏。"**
   错，有两类完全不同的现象：能回收的是**膨胀**（分配器不还给 OS，但可复用），
   不能回收的才是**泄漏**。实测第 ④ 类泄漏的 RSS 几乎没动（+-0.2MB），
   但对象数涨了 80 —— 只看 RSS 会漏掉它。

4. **"用了 `weakref` / `del` 就不会泄漏了。"**
   错。泄漏的判据是"有没有强引用链"，而不是"有没有写 del"。闭包捕获、
   异常 traceback、线程局部变量、事件循环的任务注册表，都会在你以为已经删掉之后
   继续持有对象（实测 ⑤：即使 `cancel()` 了，异常 traceback 仍会钉住协程帧）。

5. **"缓存命中率越高越好，缓存越大越好。"**
   错。缓存的第一属性是**有界**：没有容量上限的 dict 就是泄漏。
   实测修复版把缓存限制到 `capacity=32 + TTL=30s`，残留从 80 降到 32 并停止增长。

6. **"队列就是为了削峰，越深越能扛。"**
   错。队列深度 = 最坏情况下的（内存 × 延迟）。实测无界队列下 P95 = 1912ms，
   而用户的耐心预算是 3.5s —— 一个队列就能把预算吃光。队列必须有界，
   且"满了"要有明确的快速失败 + 背压信号。
