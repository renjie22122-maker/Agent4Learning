# 讲一下 Agent 的服务如何做启停设计？如何避免发布期间导致用户体验报错？

> 对应实验：`labs\lab_01_service_lifecycle.py` · 运行：`python -m labs.lab_01_service_lifecycle`
> 实测耗时 9.4s，6 条 `[VERIFY]`，2 条 `[BROKEN-REPRODUCED]`，全部数字来自真实运行
> （两个真实服务实现 + 240 个真实线程请求 + 虚拟时钟推演）。

## 一句话答案

**发布期报错几乎都不是"代码 bug"，而是启停顺序问题。** 一个生产级 Agent 服务必须把
四件事分开做，且顺序不能反：

1. **liveness / readiness 分离** —— liveness 只回答"进程要不要被重启"，
   readiness 只回答"能不能接流量"。依赖抖动时只动 readiness。
2. **预热（warmup）门禁** —— 检索索引 / 连接池 / 前缀缓存全部热完，readiness 才置 true。
3. **优雅停机四步** —— `readiness=false`（先摘流量）→ 停止 accept → 等在飞请求排空
   （≤ `grace_s`）→ 超时才强杀并计数。
4. **连接排空 + 滚动发布** —— 停机中的实例把老连接服务完，新连接被 LB 导到 ready 的实例。

一句话记法：**先摘流量、再排空、最后才退出**；顺序反了就是 5xx，而这个顺序本身就是可靠性。

## 先复现：不做防护会发生什么

v0 的服务只有一个 `started` 布尔量，实测（`[BROKEN-REPRODUCED]`）：

```
发布期第一批 12 个请求里 12 个 503（探针提前 ready），SIGTERM 又丢掉 12 个在飞请求，
合计受损 24 个，排空 0.000s，冷路径首批 P95=378ms
依赖抖动 2s：正确配置重启 0 次、掉 6 个副本·秒；liveness 也判依赖则重启 9 次、
掉 39 个副本·秒（滚动重启风暴）
```

故障是怎么一步步传导到用户身上的：

| 时刻 | v0 发生了什么 | 用户看到什么 |
| --- | --- | --- |
| t=0 进程启动 | `started=True`，探针立刻 ready，但索引/连接池/前缀缓存还在后台预热（实测 673ms） | 第一批 12 个请求 **全部 503** |
| 预热完成后的第一批 | 没有连接池 → 每请求 60ms 握手；没有预热前缀缓存 → 命中率 **0%** | P95 **378ms**（vs 预热后 175ms） |
| 发布发 SIGTERM | `started=False` 一刀切，**在飞请求跑完却被判"服务已停"直接丢弃** | 12 个请求 `CONNECTION_RESET`，排空耗时 **0.000s** |
| 依赖抖动 2s | 若 liveness 也查依赖：探针连续失败 → 容器被判"死了" → 3 副本同时重启 | 抖动窗口被冷启动从 2.0s 拉长到 **12.8s**，摘流 39 个副本·秒 |

三个细节值得记住：

- **"0 秒排空"是陷阱，不是优点。** v0 的 `graceful_drain_seconds = 0.000` 不是"排空很快"，
  而是**根本没有排空能力** —— 12 个在飞请求被直接掐断（见同批 `drain_interrupted: 12`）。
  看到 0 先问一句：是快，还是没做？
- **探针撒谎的代价是"第一批请求全灭"。** 预热 673ms 在发布窗口里被完整地暴露给了用户，
  而 readiness 只要晚 673ms 变 true，这一批 503 就完全不会发生。
- **重启风暴是"自己打自己"。** 依赖抖 2s 本来是 2 秒的容量缺口，反模式把它放大成
  12.8 秒 + 9 次重启，而且每次重启的冷启动又会去压那已经抖动的依赖。

## 根因分析

1. **"进程活着"和"能接流量"是两个不同的问题，v0 用一个布尔量回答了两次。**
   `started=True` 同时被当成"进程在"和"服务可用"，于是可观测系统（探针）拿到的是
   一个**永远乐观**的信号，它既拦不住流量，也说不清该不该重启。

2. **依赖抖动 ≠ 进程故障，但探针如果混用就会把它们等同。**
   LLM/检索抖动时进程完全健康（重启它一点用都没有，反而丢掉已经热好的缓存和连接池）。
   只有 readiness 该动；liveness 一动，编排系统就会去做"重启"这个破坏性动作。

3. **SIGTERM 的语义被误解成"立刻停止"。**
   它的真实语义是"准备退出"：Kubernetes 在发完 SIGTERM 之后还会等
   `terminationGracePeriodSeconds` 才 SIGKILL。v0 把这个宽限期浪费掉了 ——
   既没有摘流量（LB 还在送新请求，实测停机后仍有新请求被 accept），
   也没有排空（在飞请求被丢）。

4. **冷启动成本被算进了"运行期"，而不是"启动期"。**
   索引构建、连接池握手、provider 前缀缓存命中，这三样决定了首批请求的 P95。
   它们不是"优化项"，而是 readiness 的前置条件 —— 没热完就是不可用。

5. **发布是一个"流量切换"过程，不是一个"进程重启"过程。**
   实例停机的那一刻，必须有人在负责流量的去处（LB 摘流 + 别的实例承接）。
   v0 什么都没有，所以流量切换期的错误只能由用户承担。

## 生产做法

| # | 做法 | 做什么 | 为什么 | 代价 / 边界 |
| --- | --- | --- | --- | --- |
| 1 | **liveness / readiness 分离** | 两个探针分别回答两个问题；liveness 只检查进程自身心跳 | 依赖抖动只该摘流，不该重启；3 副本全重启 = 自己制造容量缺口 | 需要两个探针端点与两套阈值；readiness 抖动会带来 LB 频繁摘挂（要配 `failureThreshold` 与最小摘流时长） |
| 2 | **预热门禁** | 索引 → 连接池 → provider 前缀缓存 → 检索热路径，全做完才 `ready=true`（实测 875ms） | 首批请求的 P95 是**预热出来的**：378ms → 175ms，缓存命中率 0% → 100% | 启动变慢（875ms）；滚动发布时必须 `maxUnavailable` 配合，否则发布期间容量不足 |
| 3 | **优雅停机四步** | `readiness=false` → 停 accept → 排空(≤grace) → 超时强杀并计数（实测排空 334ms、中断 0） | 先摘流量再停机，用户就不会打到正在退出的实例 | grace 越长发布越慢；grace 到点必须强杀（实测 0.5s grace 时排空 521ms、中断 1 个）——**不能无限等** |
| 4 | **连接排空 + LB 引导** | 停机实例继续服务老连接；新连接只发给 `readiness=true` 的实例（实测滚动发布：pod-A 停机后新连接 **0** 个、老连接排空 **3** 个，整轮 36/36 成功） | 老连接被切断 = 用户看到连接重置 | 需要 LB 支持优雅摘流（连接级 drain），否则"摘流"只是不再发新连接，已有连接仍可能被 RST |
| 5 | **强杀也要可观测** | 中断数、排空耗时、被拒新请求数全部打点 | 超时中断是设计内的行为，但必须能被发现 | 需要额外指标与告警；否则"偶尔断几个"会长期被忽略 |
| 6 | **停机信号与业务解耦** | SIGTERM 只做"停止接收"，不做"取消在飞请求" | 在飞请求是已经承诺给用户的工作 | 长任务需要单独的"可中断"标记（见 lab-06 的 deadline 语义） |

**停机顺序图（顺序反了就是事故）**：

```
SIGTERM
  → ① readiness = false        （探针立刻失败，LB 停止送新连接）
  → ② accepting = false        （本进程拒绝新连接）
  → ③ 等在飞请求排空，最多 grace_s
  → ④ 仍未排空 → 强制中断 + 计数 + 报警
  → ⑤ live = false             （此刻 liveness 才该失败）
```

## 常见错误认知

1. **"探针只写一个就行，活着就是能用。"**
   错。实测同一个服务在"探针撒谎"时第一批 12 个请求 **100% 503**；而 readiness 只要
   等到预热结束（实测 875ms）再置 true，这一批请求就完全不会失败。
   **探针是流量的闸门，不是健康状态的装饰。**

2. **"排空耗时越短越好。"**
   错，这是本 lab 最典型的指标误读。v0 的 `graceful_drain_seconds = 0.000` 看起来
   "最快"，实际是**没等**——12 个在飞请求被直接掐断。排空耗时是**能力指标**：
   0 秒意味着能力为零，合理的值是"略大于在飞请求的 P99"。

3. **"liveness 探针也检查依赖更安全，有问题就重启。"**
   错，这是反模式。实测依赖抖动 2s 时：只摘流重启 **0** 次、损失 6 个副本·秒；
   liveness 也判依赖则重启 **9** 次、损失 **39** 个副本·秒，而且抖动窗口被冷启动
   从 2.0s 拉长到 **12.8s**。**重启一个健康的进程只会让事情更糟。**

4. **"快速发布 = 容器重启得快。"**
   错。发布期的用户体验取决于**流量切换**是否平滑：摘流时机、排空窗口、LB 是否
   停止送新连接。实测把这三件事做对之后，滚动发布期间 pod-A 停机后新连接 **0** 个、
   老连接全部排空、整轮 36/36 成功。

5. **"grace 调大一点（比如 60s）就更安全。"**
   错。grace 是一个**发布速度 vs 中断风险**的权衡：调大 → 每次发布慢 60s（滚动发布
   还要乘以副本数）；调小 → 长请求被强杀（实测 0.5s grace 时中断 1 个）。
   正确做法是取"在飞请求 P99 的 1.2~1.5 倍"，并且**超时必须中断 + 计数 + 报警**。

6. **"预热是性能优化，可以上线后再做。"**
   错。预热是 **readiness 的前置条件**：没有它，探针只能撒谎，而撒谎的代价就是
   发布窗口期第一批请求全失败（实测 12/12）。它是可用性问题，不是性能问题。
