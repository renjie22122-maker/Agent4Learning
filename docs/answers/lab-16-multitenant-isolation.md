# 企业级的 agent 如何做权限和数据层面的隔离，多租户工程化如何做设计落地？多用户并发，agent 的会话隔离，如何工程化落地，如何避免串会话？

> 对应实验：`labs\lab_16_multitenant_isolation.py` · 运行：`python -m labs.lab_16_multitenant_isolation`

## 一句话答案

多租户隔离的本质不是"加几个 `if tenant ==` 判断"，而是三件事：**身份在请求入口构造成
`RequestContext` 并作为参数显式往下传**（不用 contextvar）、**每一层强制断言这个身份存在
且合法**（缺了直接抛异常，快速失败）、**所有共享可变状态按 (tenant, user, session) 做
key 并把权限过滤下推到存储层**。工程上要落地五块：会话隔离（三元组 key + TTL + 版本号 +
归属校验）、数据隔离三层（召回前过滤 / 行级安全 / 存储隔离选型）、RBAC+ABAC 混合鉴权、
每租户配额、全量审计日志与独立凭证。任何一块缺位，都会以"串"的形式暴露成事故。

## 先复现：不做防护会发生什么

lab 里用真实的并发负载复现了 5 类"串"，全部是初版系统的真实写法：

| 事故 | 复现方式 | 实测次数 |
| --- | --- | --- |
| 串会话 | 会话历史挂全局字典、key 用"当前线程"，50 并发用户 × 10 轮 / 8 线程 | **122500 次**读到别人的历史 |
| 越权访问会话 | 拿着别人的 `session_id` 直接开 | **12/12 次**成功读到 alice 的订单号 |
| 串缓存 | 缓存 key 只有 query 文本 | 12 次命中里 **12 次**是别人的答案 |
| 串检索（越权召回）| 先召回 top40 再用 ACL 过滤 | 召回列表里 **495 条**别人的文档；扫描 135420 篇 |
| 串上下文 | 父请求的 context 对象被 subagent 共享 | **190 次**读到别人的中间结果 |
| 串配额 | 全局一个令牌桶 | tenant-b 被 tenant-a 挤掉 **20 次**拒绝 |
| 串凭证 | 模块级全局变量存当前 tenant 的 key | 并发下 **25 次**用错别人的 key |

故障传导链很清楚：**共享可变状态 → 高并发下互相覆盖 → 身份信息丢失 → 越权读写**。
串会话之所以能到 122500 次，是因为线程池复用了线程：线程 A 先服务 u01 再服务 u09，
"线程本地"的会话槽位就变成了跨用户的历史通道。

## 根因分析

1. **身份不是一等公民**。`user_id` 只出现在日志里，没有作为参数贯穿调用链；下游函数签名
   里根本没有 tenant，于是只能去全局/线程本地"捞"，捞到的就是别人的。
2. **contextvar 不是安全网**。`threading.Thread` 不继承父线程的
   contextvar（新线程拿默认值）；线程池里 contextvar 会随线程复用"粘住"上一个请求的值；
   `run_in_executor` 与各种回调里 同样会丢。隔离场景下"悄悄丢了身份"=
   越权，必须是显式参数 + 每层断言。
3. **过滤位置错了**。召回后再用 ACL 丢文档，意味着别人的私有文档已经被打分、被排序、
   被写进候选日志和 prompt —— 结果虽然没返回，**泄露已经发生**，而且要多召回才能保证
   不丢结果，线性成本（精排）随候选数放大。
4. **"共享池"等于没有隔离**。全局缓存、全局配额桶、全局凭证变量，都是把 N 个租户的
   状态压成 1 份，必然互相干扰。
5. **归属校验缺失**。会话只按 `session_id` 取，不校验"这个 session 属不属于你"，等于把
   session_id 当成了永不过期的 bearer token。

## 生产做法

### 1. RequestContext 显式传递（做什么 / 为什么 / 代价）

- **做什么**：请求入口构造
  `frozen dataclass RequestContext(tenant_id, user_id, session_id, trace_id, groups, role, clearance)`
，一路作为参数传下去；每一层入口 `require_ctx()` 校验，缺失/非法直接
  `raise MissingContext`。
- **为什么**：显式参数是不可伪造的（IDE 能查、类型能查、code review 能看见），
  丢了立刻炸在调用点，而不是悄悄降级成"默认租户"造成越权。
- **代价/边界**：函数签名变长、跨线程/跨进程要手动透传；异步任务、线程池任务、
  消息队列消费者都必须在"边界处"显式重建 ctx（把 ctx 序列化进任务载荷）。反过来，
  `trace_id` 这类**只用于观测、丢了不影响正确性**的信息可以用 contextvar，
  两者要分开对待。

### 2. 会话隔离：三元组 key + TTL + 版本号 + 归属校验

- **做什么**：`SessionStore` 以 `(tenant_id, user_id, session_id)` 为逻辑
  key；每条会话带 TTL、版本号、`owner=(tenant,user)`；`append()`
  带乐观锁版本校验；归属不匹配时抛 `SessionHijack` 并打点 `session_hijack_blocked`。
- **为什么**：TTL 保证会话不会永久有效（等价于缩短凭证生命周期）；版本号解决"同一会话
  被并发交错写"；归属校验解决"拿到 id 就能用"。
- **代价/边界**：乐观锁会带来写冲突重试（本 lab 实测 8 线程抢同一版本时 7 次冲突被拒），
  高冲突场景要改成"串行化到单写者"或队列化；TTL 太长等于凭证不过期，太短会导致
  用户在对话中途"失忆"，要按业务定（本 lab 用 600s 演示）。

### 3. 数据隔离三层

- **第一层：召回前过滤（filter at source）**。把 `tenant` / `groups` 下推到检索器 （
  `Query.tenant` / `Query.groups`），在打分前就跳过不可见文档。
- **第二层：行级安全（row-level security）**。取回后对每一条再断言
  `tenant/acl/密级/部门/有效期`，作为双保险（防止存储层过滤写漏）。
- **第三层：存储隔离选型**。见下方选型表。
- **代价/边界**：过滤下推要求索引里带 tenant 前缀（否则倒排表仍会被扫），行级断言会增加
  CPU 开销；多一层断言换来的是"存储层出 bug 也不会越权"。

| 存储隔离方案 | 适用规模/合规 | 代价 |
| --- | --- | --- |
| 共享表 + `tenant` 列 | SaaS 默认，成本最低 | 全表扫描风险、索引要带 tenant 前缀、一个 SQL bug 波及全租户 |
| 独立 schema | 中大型 / 有合规要求 | 迁移与 DDL 变复杂、连接池数量上升 |
| 独立库 / 独立部署 | 金融/医疗强隔离 | 运维成本与成本最高，跨租户统计困难 |

### 4. RBAC + ABAC 混合鉴权，并在工程层强制

- **做什么**：`role → permission` （viewer/analyst/engineer/admin），再叠加属性条件
  （租户一致、部门在 groups 内、密级 ≤ clearance、未过期）。检索入口和**工具调用前**
  都调用 `authorize()`，拒绝时写审计并抛 `AccessDenied`。
- **为什么**：**不能指望 LLM 不越权**（与 lab_14 呼应）—— prompt 里写"请不要访问别人的
  数据"不是安全边界，模型可以被诱导、可以被注入。权限必须由代码在工具执行前拦截。
- **代价/边界**：策略判断增加每请求开销（本 lab 1200 次决策毫秒级，可忽略）；
  真正的成本在**策略维护**：角色爆炸、例外规则、离职/转岗的权限回收，
  所以策略要能集中管理、可审计、可回滚。

### 5. 配额与公平

- **做什么**：每租户一个 `TokenBucket` （QPS/并发）+ token
  日预算计数器；超额降级或拒绝并打点。
- **为什么**：共享桶下"吵闹邻居"会把安静租户饿死（本 lab 实测 tenant-b 被挤掉 20 次）。
- **代价/边界**：分桶会让整体资源利用率下降（每个桶都有闲置余量），所以要按"租户规模 ×
  峰谷比"设定，并留出共享的突发池；同时要有配额调整的运营流程。

### 6. 审计日志

- **做什么**：每次数据访问记一条 `who / what / when / why / result`
  （tenant、user、session、
  action、resource、decision、reason、trace_id），允许/拒绝都要记。
- **为什么**：出事后它是唯一能回答"谁在什么时候看了什么"的东西；合规审计、责任界定、
  事故复盘全靠它。
- **代价/边界**：写放大（每次检索/工具调用一条）、存储成本、PII 要脱敏；必须异步写 +
  采样策略，且**不能在请求路径上同步落库**（会成为新的延迟来源）。

### 7. 密钥与凭证隔离

- **做什么**：每租户独立 provider key / 数据源 DSN，通过 `CredentialVault` 按 ctx 取。
- **为什么**：共用一个 key 有三个硬伤 —— ① 配额无法按租户分摊（账单是糊涂账）、②
  上游审计日志里分不清是谁调的、③ **泄露半径从一个租户扩大到全平台**。
- **代价/边界**：密钥数量随租户线性增长，必须上 KMS/密钥托管与轮换流程，
  否则运维复杂度会变成新的风险点。

135420 降到 108300。

隔离检查清单（本 lab 核心交付物）：

| 隔离维度 | 实现手段 | 验证方法 | 失败后果 |
| --- | --- | --- | --- |
| 会话 | 三元组 key + TTL + 版本号 + 归属校验 | 50 并发×10 轮查串历史 | 串会话 / 泄露对话 |
| 缓存 | (tenant, groups, query) 复合 key | 跨租户同问统计错误命中 | 答案串租户 |
| 检索 | 召回前过滤（metadata 下推）| 越权召回条数 / 扫描量 / p95 | 私有文档进 prompt |
| 行级 | 逐条断言 tenant/acl/密级 | 鉴权决策分布 | 越权读私有数据 |
| 上下文 | frozen ctx + 不可变 facts 链 | subagent 读到的外部事实 | 中间结果污染 |
| 配额 | 每租户令牌桶 + token 日预算 | 小租户被挤掉的拒绝数 | 吵闹邻居饿死 |
| 凭证 | 每租户独立 key/DSN | 并发下用错 key 的次数 | 泄露半径=全平台 |
| 审计 | who/what/when/why/result | 审计事件条数与抽样 | 合规不过 / 无法追责 |
| 存储 | 共享表+tenant 列 / 独立 schema / 独立库 | 按合规等级与规模选型 | 选错=成本或合规事故 |

## 常见错误认知

1. **"用 contextvar 传 tenant 就够了"** ——
   错。新线程不继承、线程池会粘住上一个请求的值、`run_in_executor`
   会丢。隔离场景下必须显式传参 + 每层断言；contextvar 只适合 trace_id
   这类"丢了不影响正确性"的观测信息。
2. **"召回后再用 ACL 过滤，反正返回给用户的是过滤后的"** —— 错。文档已经被打分、被排序、
   被写进候选日志，甚至可能进过 prompt；而且为了不漏结果必须多召回，精排成本线性上升。
   这是"既慢又泄露"的双输做法。
3. **"缓存 key 用 query 文本最省事，反正问题一样答案就一样"** —— 错。答案里往往包含
   该租户的私有上下文（订单号、内部术语、权限内的数据），跨租户命中就是数据泄露。key
   至少要带 `(tenant, groups)`。
4. **"session_id 是随机 UUID，拿到就能用没问题"** —— 错。UUID 只是不可猜测，
   不是**授权**；必须校验会话归属，否则日志泄露、链接分享、越权脚本都能直接接管会话。
5. **"权限写进 system prompt，让模型自己注意"** —— 错。prompt 不是安全边界，
   模型会被注入、会犯错。权限必须在**工具/检索执行前**由代码强制（与 lab_14 呼应）。
6. **"所有租户共用一个 LLM key 更省事"** —— 错。配额无法分摊、上游审计无法归因、
   泄露半径从单租户扩大到全平台；省下的是配置工作，赔上的是可追责性。
