# 生产环境 agent 的 token 成本持续增长，有哪些降本的优化手段？

> 对应实验：`labs\lab_12_cost_reduction.py` · 运行：`python -m labs.lab_12_cost_reduction`

## 一句话答案

**先对账，再降本。** 用 `CostLedger` 把成本按 tag（plan/reason/final）与 model 拆开，
才能知道钱花在哪；然后按九种手段逐项做：
模型路由、prompt 精简、上下文裁剪、前缀缓存、输出硬约束、批处理、结果缓存、预算熔断、重试治理。
实测基线 `$0.030825/请求`（4905 in + 420 out tokens）→ 优化后 `$0.001140/请求`（-96.3%），
输入 token -92.5%、输出 token -81.6%，而**质量分没有下降**（1.000 → 1.000；
有判别力的对照是粗糙路由 0.750 → 修正路由 1.000）。
降本的第一性原理：**把贵的计算只做一次、只做在该做的地方**；
省的是"重复与冗余"，不是"必要的一次计算"。

## 先复现：不做防护会发生什么

"没优化"的 agent 长这样：超长 system prompt（890 token）+ 每轮把完整历史塞进去（528 token）
+ 每次都调大模型 + 输出不限长。24 个请求 / 72 次调用的实测账单：

```
[BROKEN-REPRODUCED] 基线：$0.030825/请求，4905 in + 420 out tokens/请求
    by_tag   plan       $0.24660  (33%)
    by_tag   reason     $0.24660  (33%)
    by_tag   final      $0.24660  (33%)
    by_model large-400b $0.73980  (100%)
```

单次调用的输入是 1635 token，其中 890 是每次都重发的 system，528 是每次都重放的历史
—— **98% 的输入 token 与本次问题无关**。

重试侧的事故：

```
[BROKEN-REPRODUCED] 上游 45% 抖动 + 重试：成本 $0.002148 → $0.004296（+100%），成功请求并没有变多
```

原因是 provider **先计量再计算**：超时和失败的调用照样产生 token 成本。

## 根因分析

1. **没有对账 = 没有降本。** 账单只有一个总数时，你无法判断该动 system、动历史、
   动模型还是动输出。按 `by_tag` 拆开后立刻看到 plan/reason/final 各占 1/3 ——
   说明浪费是**每一次调用都发生**的结构性浪费，而不是某个阶段的病。

2. **输入侧：重复且冗余。**
   实测单次调用总输入 1635 token → 精简后 250 token（-84.7%）：
   system 890 → 21（-97.6%），历史 528 → 199（-62.3%，滑动窗口 + 摘要）。

3. **输出侧：不限长。** 输出单价 15.0 / 1.0M vs 输入 5.0 / 1.0M = **3 倍**；
   基线每次调用输出 140 token，硬约束到 96 后单次成本 `$0.010275 → $0.009615`。
   注意：基线里输入太大，所以省得少（-6.4%）；**prompt 瘦身后输出就成了大头**
   （`$0.003350 → $0.002690`，-19.7%）。

4. **模型选择：贵的不一定必要。** 全量大模型时 large-400b 占 100% 成本；
   按任务类型路由后 large 仍占 80% 成本、但 small+mid 覆盖了 50% 的请求。

5. **重试是乘法。** 45% 错误率 + 重试 2 次 → 调用数 20 → 40、账单 +100%，
   而成功请求数没变多。失败也计费，这条必须写进 SLO 与告警。

6. **缓存/批处理省的是"整次调用"。** 结果缓存让调用数从 72 降到 35；
   5 个小请求合并成 1 个让成本从 `$0.000549` 降到 `$0.000134`（-75.5%）。

## 生产做法

### 降本手段对比表（本 lab 的核心交付物）

| 降本手段 | 省钱幅度 | 代价（质量/延迟/复杂度） | 可回滚 | 优先级 |
| --- | --- | --- | --- | --- |
| 模型路由/降级 | -93.1% | 难任务误路由→答错 | 是 | P0 |
| prompt 精简 | 单次输入 -84.7% | 指令丢失→行为漂移 | 是 | P0 |
| 上下文裁剪 | 历史 token -62.3% | 长程依赖丢失（需摘要兜底） | 是 | P0 |
| 前缀缓存 | -40.7%（含结果缓存） | 前缀逐字节变动即失效 | 是 | P0 |
| 输出硬约束 | -6.4%（瘦身后 -19.7%） | 答案被截断 | 是 | P1 |
| 批处理/合并 | -75.5% | 延迟上升、失败粒度变粗 | 是 | P1 |
| 结果缓存 | -40.7% | 脏答案/串租户（见 lab_07） | 是 | P1 |
| 预算熔断 | 触发降级 7 / 拒绝 0 次 | 超预算请求被降级/拒绝 | 是 | P0 |
| 重试治理 | 把 +100% 压回基线 | 重试预算用完即放弃 | 是 | P0 |

### 1）模型路由/降级（省钱最多）

- **做什么**：按可观测特征（是否需要工具、任务类型、上下文长度）选档：
  `tools/code → large`、`analysis/long → mid`、其余 → `small`。
- **为什么**：实测每请求成本 `$0.030825 → $0.001922`（-93.8%）。
- **代价**：**路由错 = 答错**。只按上下文长度做粗糙路由时质量分掉到 0.750；
  换成"长度 + 工具 + 任务类型"后回到 1.000。阈值与规则必须用离线评测守住。

### 2）prompt 精简

- **做什么**：删冗余指令、压缩 few-shot、长文档先做摘要；用 `count_tokens` 实测前后。
- **为什么**：system 890 → 21 token，单次输入 -84.7%。
- **代价**：指令丢失会导致行为漂移（格式、拒答边界），必须配回归用例；
  精简要**逐步 + 可回滚**，一次砍太多没人能定位问题。

### 3）上下文裁剪

- **做什么**：滑动窗口保最近 N 轮 + 一段滚动摘要；超预算用 `fit_to_budget` 保尾截断。
- **为什么**：历史 528 → 199 token；摘要保留关键结论，不丢"已确认租户"这类状态。
- **代价**：长程依赖会丢（用户 10 轮前提过的约束），所以摘要质量决定上限，
  详见 lab_08。

### 4）前缀缓存复用

- **做什么**：稳定 system 放最前，`srv.warm_prefix(model, prefix_key(msgs), tokens)`；
  命中后输入按 10% 计费。
- **为什么**：实测前缀命中 735 token；连同结果缓存，每请求成本
  `$0.001922 → $0.001140`（-40.7%），调用数 72 → 35。
- **代价**：前缀必须逐字节稳定（时间戳/会话 ID 进 system 就全废）；
  多模型路由时要**按模型分别预热**。

### 5）输出长度硬约束

- **做什么**：应用层 `max_tokens`（本 lab 96）+ "用要点回答"的提示词。
- **为什么**：输出单价是输入的 3 倍，输出从 140 → 96 token。
- **代价**：答案可能被截断（丢结论/丢格式），必须显式告诉用户"这是摘要"，
  并提供"展开"入口。

### 6）批处理/合并请求

- **做什么**：把 N 个小请求合成 1 个（同一 system 只付一次）。
- **为什么**：5 个独立请求 `$0.000549 / 395ms` → 合并 1 个 `$0.000134 / 71ms`（-75.5%）。
- **代价**：**失败粒度变粗**（一次失败 = 5 个答案全丢）、延迟由最慢的子任务决定、
  单个子任务出错会污染整批输出。适合离线/异步场景，不适合强交互。

### 7）缓存命中（精确 + 语义）

- **做什么**：整次调用级的结果缓存（key 带 tenant/model/参数/版本）。
- **为什么**：命中即省掉整次调用（实测调用数 72 → 35）。
- **代价**：脏数据、串租户、时效数据过期 —— 必须按 lab_07 的策略表执行，
  副作用/时效/PII 一律不进缓存。

### 8）预算与熔断（最后一道闸门，必须硬编码）

- **做什么**：单请求 token 预算（超了裁剪/降级）+ 单租户日预算（超了先降级、再拒绝）。
- **为什么**：实测日预算 `$0.010` 下实际花费 `$0.0098`，触发降级 7 次、拒绝 0 次
  —— 预算把"无限增长"变成"可预测"。
- **代价**：超预算的请求会拿到降级答案（质量下降）或被拒绝（体验下降）；
  预算阈值需要按租户分层，且**绝不能问 LLM"你贵不贵"**。

### 9）重试成本治理

- **做什么**：把重试挂在同一个 deadline 上 + 共享重试预算 + 只重试可重试错误。
- **为什么**：上游 45% 抖动时，重试让账单 +100% 而成功数不变；重试预算是止损阀门。
- **代价**：重试预算用完就放弃，会牺牲一部分成功率 —— 这个取舍要显式写进 SLO。

### 降本的边界：哪些钱不能省

- **安全检查 / 内容审核**：省了就是合规事故。
- **权限校验**：省了就是越权（lab_16）。
- **必要的一次精排**：省了答案质量直接掉（lab_10）。
- **关键任务的大模型**：路由到小模型等于把准确率交给运气。
- **必要的重试**：上游瞬时抖动时不重试 = 白白失败。
- **判断原则**：问自己"这次计算是不是**必要的一次**" ——
  是必要的就不能省，是重复的/冗余的/可以推后的，才在降本清单里。

```
[VERIFY] cache_hit_ratio: 0.000 -> 0.084 (+8.4%)

[VERIFY] quality_score_naive_router: 0.750 -> 1.000 (-33.3%)
[VERIFY] retry_cost_usd: 0.002148 -> 0.003866 (+80.0%)  # direction: increase-expected （上游抖动时重试放大账单，这是结论本身）
```

```
[FIX-APPLIED] 每请求成本 $0.030825 → $0.001140（-96.3%），每请求输入 token 4905 → 366，
              质量分 1.000 → 1.000（未下降）；预算闸门降级 7 次 / 拒绝 0 次
```

关于 `quality_score`：它是"被路由到的模型质量 ≥ 该任务门槛"的比例，
基线（全大模型）本来就是 1.000，所以它在前后对比里必然持平 ——
**持平正是要证明的结论（降本没有牺牲质量）**；
真正有判别力的是 `quality_score_naive_router`（0.750 → 1.000），
它证明这个质量口径确实能区分好坏路由。

## 常见错误认知

1. **"先砍模型档位，立竿见影。"**
   半错。路由确实是省钱最多的一步（-93.8%），但没有质量口径就会砍出事故：
   只按长度路由时质量分 0.750。**降本必须同时报"省了多少"和"质量有没有掉"。**

2. **"输入才是大头，输出不用管。"**
   错。输出单价是输入的 3 倍；在 prompt 瘦身之后，输出会成为单次调用成本的主要部分
   （实测 `$0.003350 → $0.002690`，-19.7%）。

3. **"重试是提高成功率的手段，不算成本。"**
   错。失败/超时也计费（provider 先计量再计算），45% 抖动下账单 +100%，
   而成功请求数没有变多。必须配重试预算与成本告警。

4. **"批处理一定更好。"**
   错。批处理把成本降到 -75.5%，但延迟由最慢子任务决定、**失败粒度从 1 变成 N**。
   强交互链路不适合，离线链路才是它的主场。

5. **"给每个租户一个预算就够了。"**
   不够。预算是**两级**的：单请求 token 预算（防单点爆炸）+ 单租户日预算（防累积爆炸），
   而且超预算的处理要分级（先降级、再拒绝），不能一律 429。

6. **"让模型自己注意别写太长。"**
   错。长度、预算、路由、降级全部是**工程硬编码**的闸门
   （`fit_to_budget` / `max_tokens` / 预算表），不能依赖模型自觉。
