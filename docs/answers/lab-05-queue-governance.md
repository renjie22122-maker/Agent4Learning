# 生产环境 Agent 出现大量的异步任务堆积，如何做这种任务队列的一些治理？

> 对应实验：`labs\lab_05_queue_governance.py` · 运行：`python -m labs.lab_05_queue_governance`

## 一句话答案

队列治理的核心是三个「有界」加一个「不丢」：**队列有界**（满了就背压拒绝，别让它变成
内存泄漏）、**重试有界**（毒任务用 `max_attempts` + 指数退避 + DLQ 隔离）、**并发有界**
（按队列 age 动态扩缩 worker）、**任务不丢**（租约 + 可见性超时兜底 worker 崩溃，代价是
at-least-once，所以任务必须幂等）。而"堆积"这件事要盯的指标是 `oldest_age_ms`（最老任务的
老化时间，用户实际感受到的东西），不是 `queue_depth`（表象）。实测同一份负载：
age P95 2034ms → 65ms、队列深度峰值 9431 → 0、交互式 SLO 达成率 0% → 100%、
丢任务 1 → 0，而代价是 **3592 个批处理任务被背压拒绝** —— 这就是"牺牲谁"的答案。

## 先复现：不做防护会发生什么

实验构造了一份真实负载：生产者持续投递（实测 4459/s），4 个 worker 消费（2101/s），
中间夹一个毒任务（每次执行都抛异常）、一个会让 worker 崩溃的任务、以及 1.5s 时注入的
20 个交互式请求（SLO 500ms）。

| 观测项 | v0（无界队列 + FIFO + 无租约） | v1（有界 + 双车道 + 租约 + DLQ + 动态并发） |
| --- | --- | --- |
| queue_depth（末尾 / 峰值） | 9431 / 9431 | 0 / 0 |
| oldest_age_ms（age P50 / P95） | 1058 / 2034 | 43 / 65 |
| enqueue_rate / dequeue_rate | 4459/s / 2101/s | 3523/s / 3487/s |
| queue_rejected_total（背压） | 0 | 3592 |
| worker 数（动态） | 4 → 4（固定） | 2 → 8（按 age 扩缩，峰值 8） |
| 交互式 SLO 达成率 | 0%（P95 1675ms） | 100%（P95 9ms） |
| 丢任务数 | 1 | 0 |
| retry_total / dlq_size | 7 / 0 | 1 / 0 |
| RSS 变化 | +13.0MB | +0.4MB |

三件事被真实复现：

1. **堆积**：生产 4459/s > 消费 2101/s，队列从 0 单调涨到 9431，age 从 0 涨到 2034ms，
   RSS +13MB。`age` 时间序列 `0 → 339 → 678 → 1019 → 1362 → 1704 → 2056` 是标准的
   线性上涨 —— 队列不是"有点慢"，是**永远追不上**。
2. **毒任务**：在浅队列的对照实验里，同一个毒任务在 v0 被重试 **3000 次**（吃满重试预算，
   占全部重试的 100%），而 v1 重试 **2 次**后就进 DLQ，worker 立刻回去干正事。
3. **丢任务**：worker 在处理中"崩溃"（不 ack 也不 nack），v0 里这个任务就永远消失了
   （队列里看起来"处理过了"），v1 靠租约超时把它捞回来重做，丢任务 1 → 0。

## 根因分析

1. **无界队列不是队列，是内存泄漏**。`queue.Queue(0)` 永远不拒绝，生产快于消费时增长的
   是 RSS，直到 OOM。生产端"我提交成功了"和消费端"我处理不过来"之间没有任何反馈信号。
2. **age 才是堆积的本质指标**。深度会波动（一批消费完就掉了），但只要 age 单调上涨，
   系统就是在持续落后。用深度做告警会漏报：深度 100 但 age 30s 比深度 10000 但 age 1s
   严重得多。
3. **没有重试上限 = 毒任务永久占用 worker**。一个每次都失败的输入，靠"再试一次"永远
   不会成功，却会持续消耗并发资源，把好任务饿死。这就是"重试风暴/毒丸"。
4. **没有 lease/ack 就没有 at-least-once**。任务一旦 `get()` 出来就从队列消失了，
   worker 崩溃/被 OOM kill/网络分区时，这个任务既不完成也不重投 —— 无声丢失。
5. **所有任务抢同一条 FIFO 队列**。交互式请求排在几万个批处理任务后面，SLO 由别人的
   流量决定，根本没有可承诺性。

## 生产做法

**1) 有界队列 + 背压**

满了直接拒绝生产者，返回 429/503 + Retry-After，并打点 `queue_rejected_total`。
*为什么*：拒绝是**便宜且诚实**的失败；排队是昂贵且不诚实的失败（占内存、超时后还是要失败）。
*代价/边界*：拒绝会把压力推回给上游/用户，必须配套重试策略和明确的 SLO 说明；
本实验里 v1 拒绝了 3592 个批处理任务 —— 这是设计如此，不是故障。

**2) 双车道 + 容量预留（优先级 + 公平）**

交互式请求和批处理走**两条独立队列**，worker 先取交互式车道；批处理车道满了只拒绝批处理。
*为什么*：单队列上的"优先级"仍然可能被大批量任务挤占（要考虑队头阻塞和容量分配），
独立车道 + 预留容量才能给 SLO 一个硬保证。
*代价/边界*：车道数不能无限增加（每条车道都要预留容量，过多会让整体利用率下降）；
预留比例要根据真实流量分布定期校准，否则要么 SLO 保不住，要么批处理被过度牺牲。

**3) 租约 + 可见性超时**

worker 领走任务时登记 `(task, 领走时刻, worker_id)`；监控线程扫描超过 `lease_s` 未 ack
的任务，重新入队（`lease_timeout_total` 打点）。超过 `max_attempts + 2` 进 DLQ。
*为什么*：这是队列对"worker 会死"这件事的唯一正确答案，也是 at-least-once 的来源。
*代价/边界*：**at-least-once 意味着任务会被重复执行**，所以每个任务必须幂等
（这也是 lab_09 的幂等表要存在的原因）；lease 太短会误判"慢但正常"的任务为超时
（重做浪费），太长会让真崩溃的任务迟迟不回来 —— 一般取 P99 处理时间的 2~3 倍。

**4) 重试上限 + 指数退避 + 死信队列（DLQ）**

`max_attempts=3`，退避用 `min(cap, base * 2^attempt)` + 抖动；超限进 DLQ。
*为什么*：把"永远失败"和"这次失败"分开处理，worker 资源只花在有希望的尝试上。
*代价/边界*：DLQ 不是垃圾桶，必须有告警 + 查看面板 + 一键重放 + 明确责任人；
`max_attempts` 小于业务真实恢复窗口时，会把可恢复的任务误判为永久失败。

**5) 动态并发（按 age 扩缩）**

规则：`oldest_age_ms > SLO 的 10%` → 加 worker（到上限为止）；`oldest_age_ms < 20ms`
→ 减 worker（到下限为止）。实测 worker 数 2 → 8 自动爬升。
*为什么*：固定并发要么在低峰浪费、要么在高峰堆积；age 是"用户已经在等了"的直接信号。
*代价/边界*：扩缩要有冷却时间与步长限制，否则会震荡；扩容上限要受下游配额约束
（加 worker 只会让我们更快地打到 provider 限流，见 lab_04）；缩容只能"逻辑缩容"，
正在执行的任务必须跑完。

**6) 任务分片/批量（降本，但要看清代价）**

把 1000 个小任务合并成 10 个 100 条的批量任务，实测成本 \$0.0152 → \$0.0062
（**-59.1%**）：省下来的是每次调用的固定开销（system prompt/格式说明 77 tokens × 1000 次）
和更紧凑的输出（批量共享一次结构化外壳）。**每任务 84 token 的内容省不掉。**
*代价/边界*：单任务延迟变高（要等整批凑齐）、一批失败要整批重试（所以任务级幂等是前提）、
prompt 变长后注意力衰减。批量只适合**离线/近线**任务，交互式请求绝不上批量。

**7) 要盯的指标面板**

`queue_depth`、`oldest_age_ms`、`enqueue_rate`、`dequeue_rate`、`retry_total`、
`dlq_size`、`lease_timeout_total`、`queue_rejected_total` —— 这八个指标在本实验里
全部真实打点（`METRICS.render("lab-05 指标快照", include=["queue_"])`）。

## 落地时的取舍对照（选型用）

| 治理手段 | 解决什么 | 没解决什么 | 主要代价 |
| --- | --- | --- | --- |
| 有界队列 + 背压 | 内存无限增长 / OOM | 生产端仍然在失败 | 上游必须能处理 429/503 |
| 独立车道 + 预留容量 | 交互式被批处理挤死 | 批处理的吞吐 | 预留比例不当会浪费容量 |
| 租约 + 可见性超时 | worker 崩溃导致丢任务 | 重复执行 | at-least-once → 必须幂等 |
| 重试上限 + 退避 + DLQ | 毒任务吃满 worker | 永久失败的任务本身 | 需要有人看 DLQ 并重放 |
| 动态并发（按 age） | 低峰浪费 / 高峰堆积 | 下游配额限制 | 扩缩震荡、上限受 provider 约束 |
| 任务分片/批量 | 单位成本（实测 -59%） | 单任务延迟 | 延迟变高 + 整批重试 + 质量衰减 |

## 常见追问（面试/评审里最容易被追问的三条）

**Q1：我们用 Kafka，堆积了就是加消费者，为什么还要 DLQ 和租约？**
加消费者解决"吞吐不够"，解决不了"某个消息永远处理失败"。毒任务会让某个分区一直卡住
（或者一直被重投），加再多消费者也只是让更多消费者一起卡在那条消息上。DLQ 负责把
"永远失败"从主流程里摘出去。租约则解决另一半：消费者进程崩溃时 Kafka 的 rebalance
会有延迟，业务侧的可见性超时能更快地把任务捞回来。

**Q2：为什么不用队列深度做告警？**
深度是**结果**，age 是**体验**。深度 100 但 age 30s 说明系统已经落后很久（消费能力
远小于生产），而深度 10000 但 age 1s 说明只是一次批量投递、马上就会消化掉。
本实验里 v0 的 age 序列 `0 → 339 → 678 → ... → 2056` 才是"持续落后"的判据。

**Q3：动态扩容看起来很好，为什么还要设上限？**
因为下游有配额。加 worker 只会让我们更快地打到 provider 的并发上限
（lab_04 里 small-8b 只有 24 个并发槽），堆积会从"自己的队列"转移成"上游的 429"，
问题没解决只是换了个地方爆。扩容上限必须和下游配额一起算。

## 实验里 v0 / v1 的对照配置（一眼看懂改了什么）

| 维度 | v0 | v1 |
| --- | --- | --- |
| 队列 | `queue.Queue(0)` 无界 | 两条有界车道（交互式预留 1/6 容量） |
| 排队顺序 | FIFO，所有任务一条队 | 交互式车道优先派发 |
| 重试 | 没有上限（毒任务反复占 worker） | `max_attempts=3` + 指数退避 + 抖动 |
| 失败归宿 | 无（继续重试） | 死信队列 DLQ + 告警建议 |
| 任务所有权 | `get()` 出来就消失 | 租约 + 可见性超时自动回队 |
| 并发 | 固定 4 个 worker | 2 → 8 按 `oldest_age_ms` 动态扩缩 |
| 满队列行为 | 无界，永不拒绝 | 拒绝 + 计数（`queue_rejected_total`） |

这份对照表本身就是答案骨架：**每条治理手段都对应 v0 里的一个具体缺陷**，
没有一个是为了好看加的。

## 出问题时的排查顺序（照着做）

1. **先看 `oldest_age_ms` 的趋势**，不是绝对值：单调上涨 = 系统持续落后，
   与深度无关。age 稳定但深度大，通常只是生产者一次批投。
2. **再看 `enqueue_rate` vs `dequeue_rate`**：差值就是积压速度，可以直接算出
   "多久后会撑爆内存/SLO"。
3. **再看 `retry_total` 的构成**：如果少数几个任务贡献了大部分重试 → 毒任务，
   上 DLQ；如果所有任务都在均匀重试 → 下游整体故障，先限流/熔断。
4. **再看 `lease_timeout_total`**：持续有租约超时说明 worker 处理时间 > lease，
   要么调大 lease，要么任务该拆分（长任务不该占着 worker 不放）。
5. **再看 `queue_rejected_total` 落在哪个车道**：批处理车道被拒是设计如此；
   交互式车道被拒说明预留容量不足，这是**要立刻处理的 SLO 事故**。

## 可运行验证

```
[BROKEN-REPRODUCED] 无界队列 17835 入队 / 8396 完成；age P95=2034ms、峰值 2146ms；
                    丢任务 1 个；交互式 SLO 达成 0%
[FIX-APPLIED] 有界队列 14093 入队 / 13948 完成 / 3592 背压拒绝；age P95=65ms；
              丢任务 0 个；交互式 SLO 达成 100%

[VERIFY] queue_age_p95_ms: 2034 -> 65 (-96.8%)
[VERIFY] lost_tasks: 1 -> 0 (-100.0%)
[VERIFY] interactive_slo_attainment: 0.000 -> 1.000
[VERIFY] queue_depth_peak: 9431 -> 0 (-100.0%)
[VERIFY] batch_rejected_total: 0 -> 3592    # direction: increase-expected
[VERIFY] poison_retry_total: 3000 -> 2 (-99.9%)
```

两条"反向"断言要读懂：

- `batch_rejected_total` 从 0 变成 3592 **是背压生效的证据**：v0 不拒绝，是把无限量的
  任务堆在内存里（深度峰值 9431、RSS +13MB）；v1 选择在入口就把批处理挡住。
- `poison_retry_total` 变少**不是"没得重试"**，而是毒任务两次之后就进了 DLQ，
  worker 不再被它占用。

## 常见错误认知

1. **"队列越深说明吞吐越大"** —— 队列深度是滞后的结果指标，age 才是。深度可以因为
   一次性批量入队而暴涨，但只要 age 稳定在毫秒级，系统就是健康的。
2. **"加机器/加 worker 就能解决堆积"** —— 加 worker 只会更快地打到下游配额
   （provider 的并发槽是有限的），堆积会从"自己的队列"转移到"上游的 429"。
   扩容必须和限流一起设计。
3. **"失败就重试，重试到成功为止"** —— 毒任务会永远失败；没有上限的重试是把
   worker 资源送给一个永远不会成功的任务。
4. **"任务领出来就算处理了"** —— 没有 ack/lease 的话，worker 崩溃时任务静默丢失，
   而且监控上完全看不出来（队列在变短，看起来"很健康"）。
5. **"有了 DLQ 就万事大吉"** —— 没人看的 DLQ 等于把故障藏起来。DLQ 必须有告警、
   有查看面板、有重放工具、有责任人。
6. **"批量合并是纯赚"** —— 成本降 59%，但延迟变高、失败要整批重试、prompt 变长后
   质量下降。批量是**离线任务的工具**，用错场景会同时损失延迟和质量。

## 附：如果要在自己的服务里落地，按这个顺序

1. **先给队列加上界**（`maxsize`），并把"满了怎么办"写清楚：拒绝 + 429 + Retry-After。
   这一步就能挡住"RSS 涨到 OOM"这类最严重的事故。
2. **再做优先级/车道**：交互式与批处理分离，给交互式预留容量。SLO 才有承诺的基础。
3. **再补 ack/lease**：把"领走"和"完成"分开，超时自动回队；同时立刻给任务加幂等，
   因为 at-least-once 从这一刻起就是事实。
4. **再加 DLQ 与重试上限**：让毒任务快速出局，并且**真的有人看 DLQ**（告警 + 面板 + 重放）。
5. **再做动态并发**：按 `oldest_age_ms` 扩缩，注意扩缩冷却、上限受下游配额约束。
6. **最后做批量合并**：只对离线/近线任务启用，并评估延迟与质量代价。
7. **持续盯八个指标**：`queue_depth`、`oldest_age_ms`、`enqueue_rate`、`dequeue_rate`、
   `retry_total`、`dlq_size`、`lease_timeout_total`、`queue_rejected_total`。
