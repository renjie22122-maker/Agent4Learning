# 生产环境的 agent，如何评定性能成本和稳定性？他们核心指标会观测哪些？

> 对应实验：`labs\lab_18_observability_slo.py` · 运行：`python -m labs.lab_18_observability_slo`

## 一句话答案

生产 agent 的评定体系分四层：**RED**（服务层：Rate / Errors 按错误码 / Duration 的
P50-P95-P99）、**USE**（资源层：Utilization / Saturation 队列深度 / Errors 拒绝数）、
**Agent 专有**（链路：每请求 LLM 调用数、工具调用数、推理轮数、检索候选数；质量：
工具选择正确率、结构化输出解析失败率、无依据回答率、任务完成率；上下文：prompt token
分布、压缩率、关键事实保留率；缓存：分层命中率与错误命中率；成本：每请求成本、按
租户/功能分摊、token 效率）、**业务层**（任务成功率、人工介入率、放弃/重试率）。
稳定性用 **SLI/SLO + 错误预算** 度量，用**多窗口 burn-rate 告警**（快烧 + 慢烧）触发，
而不是瞬时阈值；经济性用 **cost_per_success（每成功任务成本）** 而不是
cost_per_request。一句话：观测的终点是**能做决策**（降级/限流/回滚），不是画图。

## 先复现：没有观测就没有结论

lab 跑同一段混合负载（120 请求 / 并发 20，含正常 + 检索慢 + 工具慢 + 模型慢 + 模型错 +
贵模型 6 类桶，并注入一段上游 503 故障窗口）：

| 观测能力 | 瓶颈归因准确率 | 发现故障耗时 |
| --- | --- | --- |
| v0：只有端到端耗时 + 成功/失败 | **40.8%**（凭经验猜：失败→检索；>800ms→工具；否则→模型）| **3181s**（虚拟秒，只能事后人工复盘）|
| v1：span 级追踪 + 四层指标 | **80.8%**（`argmax(span.duration)` 逐请求定位）| **1011s**（burn-rate 告警自动触发）|

实际负载下 v0 看到的现象是"120 个请求里 22 个失败、1 个超 3000ms"，但**回答不了
"慢在哪一层"**。有了 span 之后的耗时归因表立刻给出答案：

```
llm        p50= 242.4ms p95=1003.3ms max=3013.4ms
tool       p50=   0.0ms p95= 350.3ms max= 350.5ms
retrieve   p50=   0.6ms p95= 241.1ms max= 241.6ms
validate   p50=   0.0ms p95=   0.1ms max=   0.1ms
```

剩下 19.2% 与"注入点"不一致的请求（注入的是 llm，但 argmax 落在 tool/retrieve），
恰恰是真实存在的现象 —— **注入点 ≠ 实际最耗时阶段**，所以要同时看 span 和注入标签。

## 根因分析

1. **聚合指标不可归因**。端到端 P95 是一个"求和结果"，检索 +200ms、工具 +200ms、模型
   +200ms 在总数上完全等价，但处置方式完全不同（改索引 / 改工具 / 换模型）。没有 span
   就没有拆分，所有优化都是猜。
2. **平均成本掩盖了成本结构**。总账单里看不出"是哪个租户、哪个功能、哪次重试"烧的钱，
   于是降本只能砍功能。必须按租户/功能/标签分摊到每一次调用。
3. **瞬时阈值告警必然导致告警疲劳**。错误率 >2% 这类静态阈值贴在正常抖动上，
   天天响、天天被忽略；而真正的事故（上游持续 503）反而被淹没在噪声里。
4. **没有错误预算，稳定性和迭代速度无法谈判**。"要不要发版"变成拍脑袋；定 100% 的 SLO
   等于永远不发版。
5. **cost_per_request 会奖励失败**。请求失败得越快，单请求平均成本越好看 ——
   指标和业务价值反向。必须换成
   **cost_per_success**（对齐"交付一个成功任务要花多少钱"）。

## 生产做法

### 1. 四层指标一起上：RED / USE / Agent 专有 / 业务

- **做什么**：一个请求同时在四层打点（见下方指标字典）。
- **为什么**：RED 回答"用户是否受影响"，USE 回答"资源是否饱和"，Agent 专有回答
  "为什么"（轮数、工具、解析、依据、上下文、缓存、成本），业务层回答"值不值"。
  少任何一层都会出现"知道有问题但不知道该动哪里"。
- **代价/边界**：指标基数（cardinality）会爆炸 —— 把 tenant/user/session 当标签打
  Prometheus 会打爆内存。原则：**标签只放低基数维度**（模型、工具名、错误码、
  租户档位），高基数维度（session_id、query hash）只进 trace 不进 metrics。

### 2. span 级链路追踪做耗时归因

- **做什么**：每个请求一棵 span 树，逐阶段（retrieve / llm / tool / validate）记录耗时与
  属性（候选数、模型、token 数）；跨请求聚合出 P50/P95/max 归因表。
- **为什么**：把"端到端 P95"拆成"哪个阶段的 P95 贡献最大"，优化才有靶子。
- **代价/边界**：采样（高 QPS 下 1%~10% 采样 + 慢请求全采）；trace 存储成本；
  跨线程/异步要显式传 trace 上下文（和 lab_16 的 ctx 显式传递是同一件事）。

### 3. SLI / SLO / 错误预算

- **做什么**：先定义"好事件"（本 lab：单请求 ≤3s 且成功），SLI = 好事件比例，SLO =
  99%（预算 1%），记录预算消耗与剩余。
- **为什么**：SLO 是**产品与工程的合同**：它把"稳定性"换算成可消耗的额度，让"发版速度
  vs 稳定性"变成可以算的账。
- **代价/边界**：SLO 必须从用户视角定，且**绝不能定 100%**（没有预算就没法做权衡，
  也会逼团队为了一个不可能的目标过度投入）。SLO 定得太松失去意义、太紧压制迭代，
  需要按季度复盘；本 lab 实测一次故障窗口就把 1% 的预算烧穿（窗口内违规率 95%），
  这正是"预算该被认真对待"的证据。

### 4. 多窗口 burn-rate 告警（该响的响、不该响的不响）

- **做什么**：`burn_rate = 窗口内错误占比 / 预算占比`；快烧窗口（20 分钟）阈值 14.4、
  慢烧窗口（1 小时）阈值 6；再加三道闸：**窗口必须被填满**（span ≥ 半个窗口）、
**样本数下限**、**错误数下限**；最后必须**连续 N 次成立**且**只在"未响→响"的边沿**记录。
- **为什么**：多窗口区分"急性事故"与"慢性失血"；样本/错误数门槛避免小样本噪声；
  边沿触发避免同一个事故被重复通知 N 次（这正是告警疲劳的机制）。
- **代价/边界**：告警变少 = 灵敏度下降，可能漏掉小概率长时间的低烈度劣化；阈值（14.4 /
  6）是取舍，需要按"希望多大比例预算在多久内烧完"反推；告警必须配
  Runbook（响了之后做什么），否则只是换个人焦虑。

### 5. 症状告警 vs 原因告警

- **做什么**：症状告警 = 用户可见指标（P95、成功率、任务完成率），负责**叫醒人**；
  原因告警 = 内部指标（舱壁满、429 多、GC 高、队列深），负责**给线索**，
  一般只做看板与工单，不直接 page。
- **为什么**：把两者混在一个阈值里，要么被内部指标吵死，要么漏掉真正的用户影响。
- **代价/边界**：原因告警也需要有人看（否则形同虚设），通常绑定到"症状告警触发后
  自动附上最近 5 分钟的原因指标快照"，既省注意力又不丢线索。

### 6. 预算-质量-延迟三方权衡面板

- **做什么**：根据烧毁速率与剩余预算选择模式：预算充足 → `quality` （上更好的模型）；
  烧毁过快 → `stability` （熔断故障上游 + 降级到快模型保可用）；中间 → `balanced`。
  面板的决策**真实作用在请求上**（本 lab 实测切换 41 次、故障窗口内降级 40 条请求）。
- **为什么**：观测的终点是决策。指标再全，如果不能自动改变行为，就只是装饰。
- **代价/边界**：降级会牺牲质量（要同时观测质量指标，防止"为了 SLO 悄悄降智"）；
  策略抖动会带来体验不一致，需要**滞回（hysteresis）**与冷却时间；
  切换本身要有审计，事后能回答"这段时间为什么变便宜了"。

### 7. 用 cost_per_success 衡量经济性

- **做什么**：`unit_cost = 总成本 / 成功任务数`，同时保留 `cost_per_request` 作对照。
- **为什么**：失败也要花钱（provider 先计量后计算，超时/失败照样计费），
  `cost_per_request` 会奖励"快速失败"。实测：v0 拍脑袋"全都上中档模型"是
**$0.000258/成功任务**，v1 按预算决策 + 故障期降级是 **$0.000132（-48.8%）**，
同时任务成功率 **81.7% → 97.5%**。
- **代价/边界**：分母"成功"的定义必须和业务对齐（本 lab 用"请求成功"，生产上要按
  "任务真正达成用户目标"），否则会出现"成功率很好看但用户不满意"；
  还要防止用低价模型刷成功率导致质量下滑 —— 所以质量指标必须同屏。

```
[VERIFY] detection_time_s: 3181.0 -> 1010.6 (-68.2%)
[VERIFY] false_positive_alerts: 1 -> 0 (-100.0%)
[VERIFY] alert_false_positive_rate: 0.333 -> 0.0 (-100.0%)
[VERIFY] unit_cost_usd: 0.000258 -> 0.000132 (-48.8%)
[VERIFY] task_success_rate: 0.817 -> 0.975 (+19.3%)
[VERIFY] budget_saved_ratio: 0.0 -> 1.0
```

说明：`detection_time_s` 用的是压缩后的虚拟秒（本 lab 把时间轴压缩 600×，1 真实秒 = 600
虚拟秒，6 秒跑完 1 小时），所以数字是"1 小时窗口内的秒数"。
误报的判定不依赖人工划定的事故窗口，而是问：**告警触发时，它自己看的那个窗口里到底
有没有真实的 SLO 违规**？没有 = 纯被噪声触发 = 误报（v0 的 `lat>700ms` 规则就是这样）。

## 常见错误认知

1. **"加个 Prometheus 就算有可观测性了"** —— 错。只有计数器没有 span，你依然无法回答
   "慢在哪一层"。指标回答"是否异常"，trace 回答"为什么异常"，两者缺一不可。
2. **"告警阈值拍一个错误率 >2% 就行"** —— 错。静态瞬时阈值贴着正常抖动，
   结果是该响的不响、不该响的狂响。要用 burn-rate（相对于预算的燃烧速度）+ 多窗口 +
   样本门槛 + 边沿触发。
3. **"SLO 定 100%，追求零故障"** —— 错。100% 等于禁止发版，且没有 error budget
   就没法做"稳定性 vs 速度"的权衡。SLO 应该是"用户可接受"的水平（本 lab 用 99%）。
4. **"用每请求成本衡量降本效果"** —— 错。失败/超时的请求也会产生 token 成本，
   成本按请求平均会奖励"快速失败"。要用 cost_per_success，并且和成功率、质量同屏看。
5. **"所有维度都打成 metrics 标签，方便随便切"** —— 错。高基数标签（session_id、
   user_id、query hash）会打爆时序库内存。低基数进 metrics，高基数进 trace/日志。
6. **"有告警就够了，不需要决策闭环"** —— 错。观测的终点是能自动或人工地改变行为
   （降级、限流、回滚、扩容）。本 lab 的预算-质量-延迟面板就是把"看"变成"做"的最小实现。
