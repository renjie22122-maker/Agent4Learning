# 生产环境如何解决 agent 的长任务执行失败，然后又需要从头跑的这种问题？

> 对应实验：`labs\lab_09_long_task_resume.py` · 运行：`python -m labs.lab_09_long_task_resume`

## 一句话答案

长任务的可用性不来自"模型更聪明"，而来自三件工程约束：**每一步都能恢复**
（每步成功后持久化 checkpoint：`run_id + version + step_index + 已完成结果 + 累计 token`）、
**每个副作用都幂等**（`idempotency_key = run_id + step_name` + 幂等表，重复执行被检测并跳过）、
**每个错误都有明确处置**（可重试的瞬时错误退避重试，不可重试的业务错误立即进失败终态
并触发 saga 补偿）。实测第 13 步崩溃、整任务重跑的 v0：浪费 507 token、
重复发 12 条通知、恢复要 632ms；v1 断点续跑：浪费 token 0、重复副作用 0、
恢复 251ms（第 2 轮只调用 9 次 LLM，而不是 21 次）。

## 先复现：不做防护会发生什么

实验任务：20 篇文档 → 每篇抽取要点（20 步）→ 汇总报告（1 步），每步都调 LLM。
在第 13 步注入一次上游 5xx **持续故障窗口**（进程内重试也救不回来），然后模拟进程崩溃。

v0 的写法就是一个函数从头跑到尾，状态全在局部变量里：

| 观测项 | v0（无 checkpoint） | v1（checkpoint + 幂等 + 补偿） |
| --- | --- | --- |
| 重跑轮次 | 2（第 1 轮崩在第 13 步 + 第 2 轮从第 1 步再来） | 2 轮，但第 2 轮从 checkpoint 续跑 |
| LLM 调用次数 | 24（其中 12 次是重做前 12 步） | 21（前 12 步一次都没重做） |
| 消耗 token | 1558 | 888 |
| 浪费 token（重做部分） | 507 | 0 |
| 浪费美元 | \$0.000122 | \$0.000000 |
| 重复副作用（同一批通知发 2 次） | 12 | 0 |
| 恢复耗时（重新跑到完成） | 632ms | 251ms |

故障是怎么传导的：

1. 第 13 步抛 5xx，函数异常退出。**前 12 步的结果只存在于栈上**，随进程一起消失；
2. 唯一的补救方式是"整个任务重跑"：前 12 次 LLM 调用被完整地重做一遍 → 白花的 token/钱；
3. 更糟的是**副作用被重复执行**：第 1~12 步每步都给客户发了一条"文档 N 完成"的通知，
   重跑让同一批客户收到 2 条一模一样的通知 —— 线上这就是脏数据和客诉；
4. 如果错误是"输入非法"这类业务错误，重跑 100 次也不会成功，但每次都要烧钱。

注意实验里第 2 轮是**真的成功**了（故障窗口已过），所以 v0 看起来"最后也完成了"——
这正是最危险的地方：**很多团队的系统在正常路径上完全没问题，只有在故障时才暴露成本与脏数据。**

## 根因分析

1. **状态的生命周期跟函数栈绑定了**。`for i in range(20): result = llm(...)` 这种写法，
   所有中间结果都在内存里；进程崩溃、被 OOM kill、滚动发布、网络分区，任何一个都会
   让这些计算结果归零。长任务（分钟到小时级）撞上这些事件的概率接近 1。
2. **没有"断点"这个概念，重试的粒度就是错的**。粒度只能是"整个任务"，因为系统不知道
   已经做到哪一步了 —— 粒度错，代价就必然是"全部重做"。
3. **副作用没有幂等语义**。`send_notification()` 这种调用执行两次就是两个副作用；
   重跑 = 重复发送。这不是"小概率问题"，只要重试机制存在，它就一定会发生。
4. **没有错误分类**。把 5xx（瞬时、可重试）和 400/输入非法（永久、不可重试）混在一起，
   要么全都重试（浪费 + 放大故障），要么全都不重试（可恢复的也没救）。
5. **失败没有终态**。任务失败了但没人知道它"已经彻底失败"，也没有补偿动作，
   已产生的副作用留在外部系统里成为不一致状态。

## 生产做法

**1) Checkpoint：每一步成功后持久化**

```python
task.save(done)   # {"run_id", "version", "step_index", "done": [...], "tokens", "calls"}
```

实验中写 `.lab_state/<run_id>.json`（原子写：先写临时文件再 rename）。
*为什么*：把"进度"从进程内存搬到外部存储，进程死了进度还在。
*代价/边界*：每次落盘都有 IO 开销（高频小步骤要合并/异步刷盘）；存储本身会失败，
要处理写失败（重试 + 告警，不能静默忽略）；**生产该放 Redis/DB**，带 TTL、唯一索引与
乐观锁，本地 json 只适合 demo。

**2) 断点续跑：重启后从 `step_index` 继续**

`done` 里的步骤直接标记为"来自 checkpoint"并跳过，不再调用 LLM。
实测续跑起点 `step_index=12`，第 2 轮只做 9 次 LLM 调用（v0 第 2 轮要 21 次）。
*为什么*：这是"不从头再跑"的直接实现，省下的是 token、钱和时间。
*代价/边界*：要求每一步是**可重入**的 —— checkpoint 之前的步骤可以重做（幂等读、
纯计算），但**绝对不能重做的步骤（扣款、发通知、写外部系统）必须靠工程硬编码判定**，
不能交给 LLM 自主决定（这正是 lab_11 的论点：边界是工程约束，不是模型能力）。

**3) 幂等：`idempotency_key = run_id + step_name`**

```python
value, did = idem.run_once(f"{run_id}:notify#{i}", lambda: send(text))
if not did:   # 已经发过了 → 跳过，不产生第二个副作用
    ...
```

实测 v0 重复副作用 12 次 → v1 0 次。
*为什么*：at-least-once 是分布式系统的默认语义（lab_05 的租约也是这个代价），
唯一能把它变成"业务上 exactly-once"的办法就是幂等。
*代价/边界*：幂等表本身要持久化、要有 TTL（否则无限增长）、要能对账；
key 的设计必须包含**所有影响结果的输入**（run_id + step + 关键参数哈希），
否则会错误地把"参数不同"的两次调用判成重复。

**4) 补偿（saga）：失败时做反向操作**

不可重试的错误触发补偿：撤销已发出的通知、把运行状态写成 `failed:business_error`、
标记草稿。实验中补偿动作被真实执行并打印。
*为什么*：长任务跨越多个外部系统，一旦中途失败必然留下不一致状态，必须主动收敛。
*代价/边界*：补偿**只能覆盖可逆的副作用**。钱扣了退回去是补偿，货发了就不可逆 ——
所以真正的做法是"先做不可逆操作之前的所有可逆步骤"，把不可逆操作放到最后一步
（saga 的经典排序原则）。

**5) 可控重试 vs 不可重试（必须硬编码分类）**

```python
except LLMError as exc:
    if not exc.retryable:                 # 400/权限：直接终态 + 补偿
        task.terminal = f"business_error:{exc.code}"; task.compensate(...)
    else:                                 # 503/超时：退避重试（有上限）
        time.sleep(backoff(attempt))
```

实测：可重试错误消耗 3 次尝试后成功；业务错误第 1 次就进终态 + 补偿。
*为什么*：判据是 HTTP 码/异常类型这类**机器可判定**的东西，不能依赖模型判断 ——
模型说"这个错误应该能重试"时没有任何依据，而重试扣款是真实损失。
*代价/边界*：错误分类表需要和上游对齐并持续维护（上游加了一个新错误码，
你的分类就会退化）；重试上限要小于"用户可接受的完成时间"。

**6) 进度可视化**

打印步骤表：步骤名 / 状态 / 耗时 / 累计 token / 是否来自 checkpoint。
长任务没有进度可视化，运维就只能靠猜；这张表也是"到底哪一步慢/贵"的归因起点。

## 落地时的取舍对照（选型用）

| 手段 | 解决什么 | 没解决什么 | 主要代价 |
| --- | --- | --- | --- |
| 步骤化（`for step in plan`） | 让"断点"这个概念存在 | 状态仍在内存 | 需要重构任务代码 |
| Checkpoint（每步落盘） | 崩溃后不用重算 | 重复副作用 | 每步一次 IO；存储可能失败 |
| 幂等键 + 幂等表 | 重复执行不产生重复副作用 | 幂等表本身的膨胀 | key 设计错误会误判重复；需要 TTL/对账 |
| 断点续跑 | 恢复时间与成本 | checkpoint 之前的步骤仍要信任 | 每步必须可重入 |
| 错误分类（可/不可重试） | 不浪费重试、不放弃可恢复的 | 分类表要持续维护 | 上游新增错误码时分类会退化 |
| Saga 补偿 | 失败后的状态一致性 | 不可逆操作无法补偿 | 补偿本身也会失败，需要重试与人工兜底 |
| 步骤进度表 | 可观测、可归因 | 不改变执行本身 | 要保证打点不成为瓶颈 |

排序建议：**把不可逆操作排到最后一步**。这样"补偿"只需要覆盖前面所有可逆步骤，
saga 的复杂度会下降一个数量级 —— 这是所有长任务设计里最划算的一条约束。

## 常见追问（面试/评审里最容易被追问的三条）

**Q1：为什么不让模型自己决定"这一步要不要重跑"？**
因为模型没有外部系统的知识，也不承担一致性责任。它无法知道"这个通知是否已经发出去"、
"这笔扣款是否已经到账"，只能给出看起来合理但没有任何依据的判断。而重跑扣款是真实损失。
能不能重跑必须是**工程硬编码**的属性（写在步骤定义里），与 lab_14 的"硬编码边界"一致。

**Q2：checkpoint 频率多高合适？**
按"重做的代价"决定，不是按时间。如果一步要花 30s 和几万 token，就每步都存；
如果一步只要 50ms，就每 N 步或每 T 秒合并存一次（本实验为了演示每步都存，
生产里高频小步骤要合并，否则 IO 会成为新瓶颈）。另外落盘必须原子（临时文件 + rename）
并且**写入失败要告警** —— 静默失败的 checkpoint 比没有 checkpoint 更危险。

**Q3：有了 checkpoint 和幂等，是不是就不会重复执行了？**
不是。checkpoint + 幂等保证的是"重复执行不产生重复**副作用**"，
但重复**计算**仍然会发生（checkpoint 间隔内崩溃、或者幂等表在"检查"和"执行"之间有竞态）。
要想彻底避免重复计算，需要把"幂等检查 + 执行 + 记录"放进同一个事务或唯一索引里，
这也是为什么幂等表必须持久化而不是放在进程内存里。

## 出问题时的排查顺序（照着做）

1. **先确认失败发生在哪一步**：看步骤进度表；没有这张表，先补上（否则一切归因都是猜）。
2. **再确认这一步是"重算的"还是"重做副作用的"**：前者只需要 checkpoint，
   后者必须幂等 —— 两者的修法完全不同，别搞混。
3. **再看 checkpoint 有没有真的写成功**：`step_index` 是不是停在崩溃前那一步？
   如果落后很多，说明落盘失败没被处理（静默失败最危险）。
4. **再看错误分类**：这次失败是 `retryable=True` 被误判成终态，还是业务错误被误判成可重试？
   看一下 `terminal` 字段和错误码分布。
5. **最后验证恢复流程**：真的 `kill -9` 一次，看续跑路径能不能跑通 ——
   没演练过的恢复流程等于没有。

`wasted_*` 的口径是"因为重跑而白做的那部分"：v0 把前 12 步重做了一遍，v1 一步都没重做。

## 常见错误认知

1. **"失败就整个重跑，反正 LLM 快"** —— 实测重跑一轮的浪费是 507 token、12 次重复副作用、
   632ms；放到线上就是 20 步 × N 个并发任务的真金白银，以及一批重复通知的客诉。
2. **"有 checkpoint 就够了"** —— 没有幂等的话，续跑仍然会把 checkpoint 之后的副作用
   重复执行；checkpoint 解决"重复计算"，幂等解决"重复副作用"，两者缺一不可。
3. **"让模型自己判断这一步能不能重跑"** —— 模型没有外部系统的知识，也没有一致性责任；
   能不能重跑必须由工程硬编码（扣款/发通知绝不重跑，幂等读/纯计算随便重跑）。
4. **"所有错误都重试几次，总能成功"** —— 业务错误（输入非法）重试 100 次也不会成功，
   只会持续烧钱并占住并发；必须按错误类型分流。
5. **"补偿动作随便写一个就行"** —— 补偿只能覆盖可逆操作；正确做法是把不可逆操作
   （扣款、发货）排到最后一步，前面全是可逆/可重跑的步骤。
6. **"本地写个 json 就是 checkpoint 了"** —— demo 可以，生产要考虑并发写、原子性、
   TTL、多副本一致性、schema 版本迁移（实验里 `version` 不匹配会显式作废而不是静默误用）。

## 附：checkpoint 该存什么（最小可用集合）

```json
{
  "run_id": "v1-run",
  "version": 3,
  "step_index": 12,
  "done": ["analyze#1", "...", "analyze#12"],
  "tokens": 507,
  "calls": 12
}
```

- `run_id`：幂等键的前缀，也是"这次运行"的唯一标识（重跑必须换 run_id，
  否则会把两次不同的运行判成同一次）。
- `version`：schema 版本。实验里版本不匹配会**显式作废**并打印提示，而不是静默误用 ——
  长任务的 checkpoint 会跨越代码发布，schema 演进必须显式处理。
- `step_index` / `done`：断点位置。用列表而不是单个整数，才能支持"部分步骤被跳过/
  被补偿"这类真实情况。
- `tokens` / `calls`：成本对账用。没有它就无法回答"这次重跑多花了多少钱"。
- **不应该存的东西**：大模型的原始输出全文（体积爆炸）、敏感字段（PII）、
  可重新计算的中间结果。生产里这些放对象存储，checkpoint 里只放引用。

## 附：如果要在自己的服务里落地，按这个顺序

1. **先给每一步编号并显式建模**：`for step in plan:` 而不是把 20 步写成一坨。
   没有步骤边界，就没有断点。
2. **再给有副作用的步骤发幂等键**：`f"{run_id}:{step}"`，并且把幂等表和业务写入
   放在同一个事务/同一个唯一索引里（否则"检查过没发过"和"发送"之间仍有竞态）。
3. **再加 checkpoint**：每步成功后落盘（原子写 + 版本号 + TTL）。先跑通，
   再优化写频率（合并小步骤、异步刷盘）。
4. **再加错误分类**：把异常映射成"可重试 / 不可重试"，不可重试的直接进失败终态。
5. **最后加补偿（saga）**：把不可逆操作排到最后一步，前面全部设计成可重跑/可逆。
6. **持续做**：定期演练"跑到一半 kill -9"，验证续跑路径真的可用 ——
   没演练过的恢复流程等于没有。

## 一句话记住这个 lab

> 长任务的可用性 = 每步可恢复 + 每个副作用幂等 + 每个错误有明确处置；
> 这三件事全是工程约束，没有一件能靠"让模型更小心"解决。
