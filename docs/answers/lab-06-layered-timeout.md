# LLM 响应慢导致整个 agent 链路超时，分层超时的熔断策略是什么？

> 对应实验：`labs\lab_06_layered_timeout.py` · 运行：`python -m labs.lab_06_layered_timeout`
> 相关实验：`lab-04`（限流）、`lab-13`（降级链与模型调度）

## 一句话答案

**超时是一个向下传递的预算，不是每层各写一个常数。**
`child_timeout = min(本阶段上限, 父级剩余预算)`；重试必须挂在同一个预算上，并且要有
进程级共享的重试预算（否则 3 层各重试 3 次就是 3^3 = 27 倍流量）；
熔断保护的是**调用方自己**（不发无用请求、不占线程），而且**慢调用也必须计入失败**。

实测（24 并发、上游 p50 1.2s 且 20% 503）：

| 指标 | v0 各层硬编码超时 | v1a 分层预算 | v1b +熔断 | 说明 |
| --- | --- | --- | --- | --- |
| P95 延迟 | 4151ms | — | **2187ms** | −47% |
| 超预算请求占比 | 62.5% | 0% | **0%** | 客户端预算终于算数 |
| 每美元买到的 SLO 内成功数 | 405 | — | **1708** | +322% |
| 成本 | $0.00494 | — | **$0.00176** | −64% |
| 原始成功率 | 20.8% | 12.5% | 12.5% | 见下方「反直觉现象」 |

## 先复现：不做防护会发生什么

这个 lab 先用一段最小复现把"超时的本质"钉死：

**① 对端挂死时，没有超时 = 完全失去自救能力**

```
未设超时 → 客户端实际等了 4101ms（对端自己"好"了才返回）
设 400ms 超时 → 客户端 402ms 就返回 TIMEOUT
[BROKEN-REPRODUCED] 设了超时 400ms 就能自救
```

**② 但超时不会让服务端的活停下来 —— 这是最关键的一点**

```
provider 请求=2 成功=1
客户端超时=1 其中服务端仍在跑=1（这些调用照样产生 token 成本）
```

也就是说：**客户端走了，上游还在算、并发槽还被占着、token 照样计费。**
这就是"上游抖动 → 自己被拖垮"的传导路径。很多人以为"我设了超时就安全了"，
其实只是把自己这一侧摘出来了，上游被你占着的资源一点没少。

**③ 分阶段超时之和 > 总预算时，没有统一预算就必然超支**

```
retrieve: 申请 900ms，只拿到 600ms（预算不足，降级）
llm:      申请 2200ms，只拿到 1800ms（预算不足，降级）
tools:    申请 900ms，只拿到 600ms（预算不足，降级）
summarize 直接拒绝进入：[BUDGET] stage=summarize 超出预算 3000ms
```

## 根因分析

### 1. 为什么"每层各写一个超时"必然失败

假设链路是 `检索 1s → LLM 10s → 工具 5s → 汇总 3s`，每层都"看起来合理"：

- 最坏情况总耗时 = 1 + 10 + 5 + 3 = **19 秒**，但客户端 3 秒就走了；
- 有重试的话还要乘：(1+10+5+3) × 3 = **57 秒**；
- 更糟的是：**预算早已耗尽，系统还在为用户早已放弃的请求干活** —— 这部分资源
  完全浪费，而且在故障时正是它把容量吃光。

根因是**缺少一个全局量**。每层的超时是局部最优，叠加起来是全局灾难。

### 2. 为什么重试会把故障放大

重试的次数是乘法而不是加法：

```
3 个层级 × 每层重试 3 次 = 27 倍流量打向一个已经出问题的上游
```

上游已经在抖，你还给它 27 倍流量 —— 这是把"抖动"变成"雪崩"的标准手法。

### 3. 为什么熔断必须统计"慢调用"

只统计报错的熔断器会漏掉最危险的情况：**上游不报错，但每次都要 20 秒**。
此时错误率是 0%，熔断器永远不打开，而你的线程/连接已经被慢调用占满。
所以熔断的失败判据必须是"**错误 或 超过慢调用阈值**"。

### 4. 熔断的三态语义

```
closed  ──连续失败≥阈值──▶ open ──冷却时间到──▶ half_open ──探针成功──▶ closed
                              │                      │
                          快速失败              只放 1 个探针
                          （不占线程）          （防恢复期放量）
```

**半开只放 1 个探针**这件事经常被忽略：如果半开时把积压的流量一次放出去，
上游刚恢复就会被二次打死，于是永久卡在 open/half_open 循环里。

## 生产做法

### 1. 分层预算（`Deadline`）

```python
dl = Deadline.root(3000, stages={"retrieve": 500, "llm": 1100, "tools": 600})
with dl.stage("llm") as st:
    reply = server.call(msgs, timeout=st.timeout_s(floor_s=0.15))
```

四条规则：

- 子阶段预算之和**允许**大于父预算 —— 由 `Deadline` 动态收敛（取 min）；
- 每个下游调用都必须用 `min(阶段上限, 剩余预算)` 作为自己的 timeout，
  **绝不能出现硬编码的 30s**；
- 给 llm 阶段留出"至少能重试一次"的预算（本 lab 里 llm 阶段 1100ms < 上游 p50 1200ms，
  这是故意的：让单次调用经常超时，但预算还剩得下第二次尝试，才能验证重试真的有用）；
- 预算耗尽时**主动拒绝进入**该阶段（抛 `BudgetExceeded`），而不是进去再失败。

### 2. 受控重试

```python
RetryPolicy(max_retries=2, base_s=0.06, cap_s=0.4, jitter="full")
RetryBudget(total=64)          # 进程级共享
call_with_retry(fn, policy, deadline=dl, budget=rb)
```

- **全抖动（full jitter）**：`sleep = random(0, base × 2^n)`。
  等间隔或固定退避会让所有客户端在同一时刻重试，形成"重试波峰"；
- 每次重试前检查 deadline，**剩余时间不够就不重试**（直接失败比拖到超时更好）；
- 共享重试预算：单点故障不应该引发全网重试风暴。

### 3. 熔断

```python
CircuitBreaker(name, failure_threshold=5, cooldown_s=1.2,
               half_open_max=1, slow_call_ms=2500)
```

- `slow_call_ms` 是必须项（见根因 3）；
- 冷却时间要按"业务能承受的失败窗口"来定，不是拍脑袋。**冷却太长会让熔断在
  故障期间拒绝掉本来能成功的请求** —— 本 lab 里 v1b 的成功率低于 v1a 就是这个原因。

### 4. 舱壁与快速失败

```python
Bulkhead("agent", limit=28)     # 满了立刻失败，不排队
```

舱壁满时**立刻返回可重试信号**（带 `Retry-After`），而不是让请求烂在内存队列里。
这是 `lab-02`（并发 panic）里"无界队列 → 内存涨 → 雪崩"的直接解药。

### 5. 熔断必须配降级链才算完整

熔断只解决"不发无用请求"，它**不产生答案**。所以必须接一条降级路径：

```
large 熔断 → mid → small → 缓存/模板答案 → 明确告知降级
```

没有降级链时，用户看到的是"更快地失败"，而不是"更快地成功"。
这一点在 `lab-13`（模型调度）里有完整实现和实测。

## 一个必须讲清的反直觉现象

**v1b 的"原始成功率"比 v0 更低**（12.5% vs 20.8%）。看起来修复让事情变糟了，但实际上：

- v0 的 20.8% 是**靠无脑等待换来的** —— 它愿意挂 4 秒以上，而用户早在 3.5 秒的
  预算线就流失了。这些"成功"对用户毫无价值；
- 更公平的口径是 **SLO 内成功率（成功 且 在预算内）**：v0 只有 4.2%，v1 是 12.5%；
- 最能说明问题的是 **每美元买到的 SLO 内成功数**：405 → 1708（+322%）。

**教训：只有一个"成功率"指标是不够的。** 它必须带上时间约束，
否则会奖励"让用户干等"的实现。同理，熔断在上游没恢复时主动拒绝请求、拉低成功率，
这是**用可用性换延迟与成本的决策**，不是纯粹的优化 —— 所以它必须配降级链。

## 常见错误认知

| 错误认知 | 为什么错 |
| --- | --- |
| "每层设一个合理超时就够了" | 局部最优叠加成全局灾难；总耗时是各层之和 × 重试次数 |
| "设了超时就安全了" | 客户端超时不会让服务端的活停下：上游仍被占用、token 照样计费 |
| "重试能提高成功率，多试几次" | 重试是乘法放大流量；上游抖动时重试是雪崩的加速器 |
| "熔断只看错误率就行" | "不报错但很慢"比报错更能拖死自己，必须统计慢调用 |
| "熔断打开后等它自己恢复" | 半开不放探针就永远恢复不了；半开放太多就二次打死上游 |
| "熔断能提高可用性" | 熔断只止损、不产出；没有降级链时用户看到的是"更快地失败" |
| "成功率越高越好" | 不带时间约束的成功率会奖励"让用户干等"的实现 |
| "超时时间调大一点，成功率就上去了" | 你只是把失败从"超时"改成了"用户早就走了"，成本和资源占用反而更高 |
