# 小模型推理较弱、成本便宜，大模型相对准一点、成本又很高，如何做平衡？生产环境如何做模型调度？

> 对应实验：`labs\lab_13_model_routing.py` · 运行：`python -m labs.lab_13_model_routing`

## 一句话答案

平衡的答案是**置信度级联（cascade）**：先用基础档模型，用"自置信度 + 校验器"判断是否升级，
**只把不确定的交给大模型**；再叠加**成本约束**（按任务价值分配升级额度）和**调度层四件套**
（多端点负载均衡、降级链、灰度与一键回滚、租户配额）。
实测 300 个任务：全 large 成本 `$2.1000` / 准确率 0.970；
级联（small→large）成本 `$1.3020` / 准确率 0.933（-38% 成本，只掉 3.7pp）；
而**以 mid 打底的级联 `$0.9030` / 0.953 直接支配了 small 打底的级联** ——
**级联的起点比校验器更关键**。
"模型调度"≠"选哪个模型"：降级链在 large 上游 85% 失败时仍让 **34~39 / 40 个请求**
拿到答案，多端点让同一端点劣化时服务量从 96 提到 406（4.2 倍）。

## 先复现：不做防护会发生什么

两条极端路线都会出事（300 个任务，隐藏难度 easy 98 / medium 116 / hard 86）：

```
[BROKEN-REPRODUCED] 全 small：成本 $0.0210 但准确率只有 0.517；
                    全 large：准确率 0.970 但成本 $2.1000（100 倍）
```

按隐藏难度归因（本 lab 的质量口径）：

| 难度 | 任务数 | small 期望准确率 | large 期望准确率 |
| --- | --- | --- | --- |
| easy | 98 | 0.97 | 0.97 |
| medium | 116 | 0.33 | 0.97 |
| hard | 86 | 0.29 | 0.97 |

**小模型的损失全部集中在 medium/hard**（能力不足），easy 上几乎无损 ——
所以正确做法不是"全都升级"，而是"只在能力不足时升级"。

调度层不做防护同样出事：

- 只有一个端点且它劣化时，0.4s 只能服务 **96** 个请求；
- 没有降级链时，large 上游 85% 失败 = 请求直接失败；
- 没有灰度/回滚 = 新版本出问题只能全量回滚或硬扛。

## 根因分析

1. **成本结构极度不均匀。** 按 token 价格表：small `(800×0.05 + 200×0.15)/1e6 = $0.00007`、
   mid `$0.00084`、large `$0.0070` —— large 是 small 的 **100 倍**、mid 的 **8.3 倍**。
   这决定了任何"平均主义"的路由都会把钱烧在大模型上。

2. **能力是分档的，任务是分难度的，两者错配才产生浪费。**
   门槛 `req`（easy=0.62 / medium=0.84 / hard=0.95）正好等于三档模型的 quality；
   只要模型档位 ≥ 门槛，答对概率就是 0.97；低于门槛就掉到 `0.45 × q/req`（≈0.29~0.40）。

3. **观测特征与真实难度不完全对齐。**
   本 lab 里 `kind`（faq/analysis/code）是难度的**噪声代理**：
   `faq` 有 25% 是 medium、5% 是 hard。静态规则（faq→small）就是被这 30% 拖累的
   —— 静态规则准确率只有 0.853。

4. **校验器的质量决定级联的收益。**
   发现能力 0.92 = 能力不足时能发现（该升级的升上去）；
   误报率 0.08 = 本来够用也被升级（白花大模型的钱）。
   本 lab 的 large 占比 38%（= 升级率 / (1+升级率)），就是这两个参数的直接结果。

5. **预算是硬约束，不是建议。** 预算不足时必须由工程层决定"谁被降级"，
   按任务价值（code > analysis > faq）排序分配升级额度 ——
   实测按预算 $0.45 约束的级联拿到 0.663 准确率。

6. **可用性来自调度层，不来自路由。** 路由决定"平时花多少钱"，
   负载均衡/降级链/灰度/配额决定"故障时能不能活"。

## 生产做法

### 四种（本 lab 实际跑了六种）策略对比表

| 策略 | 成本$ | 准确率 | large 占比 | P95 延迟 | 调用/请求 |
| --- | --- | --- | --- | --- | --- |
| 全 small | 0.0210 | 0.517 | 0% | 404ms | 1.00 |
| 全 mid | 0.2520 | 0.817 | 0% | 404ms | 1.00 |
| 级联(small→large)+预算约束 | 0.4690 | 0.663 | 18% | 2585ms | 1.21 |
| 静态规则（faq→small/analysis→mid/code→large） | 0.7910 | 0.853 | 33% | 3363ms | 1.00 |
| **级联(mid→large)** | **0.9030** | **0.953** | 24% | 2794ms | 1.31 |
| 级联(small→large) | 1.3020 | 0.933 | 38% | 3691ms | 1.61 |
| 全 large | 2.1000 | 0.970 | 100% | 4786ms | 1.00 |

**准确率-成本帕累托前沿**（非支配集）：全 small、全 mid、静态规则、级联(mid→large)、全 large。
**被支配的策略**：级联(small→large)+预算约束（←全 mid）、级联(small→large)（←级联(mid→large)）
—— 存在"更便宜且更准"的选择，应当淘汰。
这条前沿就是选型依据：**先确定成本预算，再在前沿上挑准确率最高的那个**。

### 1）静态规则路由（起步方案）

- **做什么**：按任务类型/长度/是否需要工具硬编码选档。
- **为什么**：实现成本最低、行为可解释、可灰度和回滚；本 lab 实测 0.7910 / 0.853。
- **代价**：观测特征与真实难度错配时准确率上不去（本 lab 里 faq 类有 30% 是难题），
  规则会随业务漂移而腐化，需要定期用线上数据回归。

### 2）置信度级联（平衡的核心答案）

- **做什么**：基础档先跑 → 校验器（自置信度 + 结构校验 + 自一致性投票）判断是否升级 →
  只把不确定的升级到大模型。
- **为什么**：实测用 38% 的 large 调用拿到 0.933（全 large 是 0.970 / 100% 调用）；
  换成 mid 打底只要 24% 的 large 调用就拿到 0.953。
- **代价**：延迟变成"两段之和"（P95 3691ms vs 全 large 4786ms，比全 mid 的 404ms 高得多）；
  校验器本身要成本（投票 = 多次调用）；**校验器质量决定收益**，必须评测。

### 3）级联的起点选择（本 lab 最重要的发现）

- **做什么**：不要默认"从最小的模型开始"，而是选"能覆盖大多数任务的最低档"。
- **为什么**：mid 打底的级联只对 hard 任务升级（24%），既比 small 打底便宜
  （少升级）又更准（大部分任务 mid 本来就够）。
- **代价**：需要知道任务的难度分布；难度分布漂移时要重新评估起点。

### 4）成本约束路由

- **做什么**：单请求预算 + 整租户预算；预算不足时按任务价值排序保留升级额度，
  剩下的强制留在基础档。
- **为什么**：把"成本不可控"变成"成本可预测"（实测预算 $0.45 下准确率 0.663，
  但绝不会超支）。
- **代价**：低价值任务被降级（质量下降）；价值排序本身是业务判断，需要和产品对齐。
  **绝不能问 LLM"你贵不贵"** —— 预算必须是工程硬编码。

### 5）调度①：多端点负载均衡与优先级

- **做什么**：`ModelSpec.max_parallel` + `Bulkhead` 模拟多个部署端点，
  按"最少在飞"选择端点；不同优先级走不同池。
- **为什么**：同一个端点劣化时，单端点 0.4s 只能服务 96 个请求，
  3 端点 + 最少在飞优先能服务 406 个（4.2 倍），劣化端点只承担 32 个。
- **代价**：多端点意味着配额/版本/监控都要按端点维度管理；
  "最少在飞"需要实时的负载反馈（反馈滞后会抖动）。

### 6）调度②：降级链

- **做什么**：`large → mid → small → 模板答案`，每一级用真实 `CircuitBreaker` 保护；
  大模型熔断后自动下沉。
- **为什么**：large 上游 85% 失败时，**34~39 / 40 个请求仍拿到答案**，
  只有 0~1 个落到模板兜底；熔断器 `state=open opened=1~4 rejected=28`。
- **代价**：降级答案的质量与格式可能与主链路不一致（要保证 schema 兼容）；
  降级率必须打点告警，否则"悄悄降级"会变成长期质量事故。

### 7）调度③：灰度/版本切换与一键回滚

- **做什么**：`RolloutController` 按 `md5(tenant:req_id) % 100` 做**稳定分桶**，
  按比例切到新模型版本；出问题 `rollback()` 一键归零。
- **为什么**：实测灰度 10% 时 v2 占比 11.0%，回滚后累计降到 7.3%（新增流量全部走 v1）。
- **代价**：同一租户要保持版本一致（否则回答风格突变）；灰度期间要同时监控两个版本
  的质量与成本；回滚必须能在秒级生效。

### 8）调度④：租户配额与优先级

- **做什么**：不同 tier 拿到不同的模型权限（free=small、pro=small+mid、enterprise=全档），
  超配额自动降级。
- **为什么**：实测 60 个请求里 free 降级 20 次、pro/enterprise 0 次 ——
  配额把"成本"变成产品能力的一部分。
- **代价**：用户体验分层，要提前和商务/产品对齐；降级必须对用户可见（避免"以为买了大模型"）。

## 常见错误认知

1. **"级联一定比静态规则好。"**
   错。级联(small→large) 成本 $1.3020 / 0.933，静态规则 $0.7910 / 0.853 ——
   在"预算只有 $0.8"的场景里静态规则才是对的。**先定预算，再在帕累托前沿上选**。

2. **"从最小的模型开始级联最省钱。"**
   错。本 lab 实测：small 打底的级联 $1.3020 / 0.933，被 mid 打底的
   $0.9030 / 0.953 **完全支配**（更便宜且更准）。起点选错，校验器再准也白搭。

3. **"校验器越灵敏越好。"**
   半错。发现能力高 = 更准，但误报率高 = 更多不必要的升级 = 更贵。
   本 lab 用"发现 0.92 / 误报 0.08"两个参数显式刻画这个取舍，
   并把 large 占比（38%）作为结果指标打出来。

4. **"预算不够时让模型自己判断要不要省。"**
   错。预算是**工程硬约束**：单请求预算 + 整租户预算 + 按任务价值分配升级额度，
   全部硬编码 + 可观测。问 LLM"你贵不贵"既不可靠也不可审计。

5. **"降级链会降低质量，能不用就不用。"**
   错。降级链是**可用性资产**：large 上游 85% 失败时，34/40 个请求仍拿到答案。
   要做的是把降级率打点告警、保证降级答案 schema 兼容，而不是不降级。

6. **"多端点只是为了扩容。"**
   错。多端点的关键收益是**隔离**：同样的总并发上限下，一个端点劣化时
   单端点服务量 96、多端点 406。容量可以买，隔离必须设计。
