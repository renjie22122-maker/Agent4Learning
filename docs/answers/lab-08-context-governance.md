# agent 多轮对话上下文越来越大、越来越冗余，如何工程化做治理？多种上下文压缩技术分别是什么？

> 对应实验：`labs\lab_08_context_governance.py` · 运行：`python -m labs.lab_08_context_governance`
> 实测耗时 1.01s，8 条 `[VERIFY]`，全部数字来自真实运行（30 轮对话真的调了 30×2 次 provider）。

## 一句话答案

上下文治理不是"找个摘要模型压一压"，而是一条**分层流水线**：
**先删零信息冗余（免费）→ 把关键事实搬进置顶的结构化 state（近乎无损）→ 大工具结果外置成「摘要 + ref」（可回查）→ 最后用 `fit_to_budget()` 硬闸门按工程硬编码的固定顺序降级**。
压缩率必须和**关键事实保留率**一起看：只盯 token 降了多少，省下的钱会用意想不到的答错来还。

实测一句话：第 30 轮 prompt 从 **20,739 → 1,070 tokens（-94.8%）**，累计成本 **$0.01653 → $0.00177（-89.3%）**，而有效召回率反而从 **0.224 → 0.750（+234%）**。

## 先复现：不做防护会发生什么

### 1. 线性膨胀 → 成本平方增长

30 轮真实对话（每轮 = 用户问题 + 3 条检索片段 + 一个"故意很大"的工具结果 + 助手回答），历史原样回灌：

| 轮次 | 单次 prompt | 累计 in token | 单次延迟投影 | 累计延迟 | 单次 $ | 累计 $ |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 691 | 691 | 195 ms | 195 ms | 0.00005 | 0.00005 |
| 5 | 3,446 | 10,271 | 815 ms | 2,511 ms | 0.00018 | 0.00057 |
| 10 | 6,990 | 38,129 | 1,613 ms | 8,979 ms | 0.00036 | 0.00201 |
| 15 | 10,526 | 83,686 | 2,408 ms | 19,429 ms | 0.00054 | 0.00435 |
| 20 | 14,033 | 146,920 | 3,197 ms | 33,857 ms | 0.00071 | 0.00756 |
| 25 | 17,381 | 227,124 | 3,951 ms | 52,103 ms | 0.00088 | 0.01162 |
| 30 | 20,739 | 324,110 | 4,706 ms | 74,125 ms | 0.00105 | 0.01653 |

`[BROKEN-REPRODUCED] 第30轮 prompt 20,739 tokens = 第1轮 691 的 30.0 倍；累计 324,110 tokens 是线性基线的 15.6 倍（平方增长）；累计成本 $0.01653`

关键读法：
- **单轮成本随轮数线性涨**（691 → 20,739），**累计成本就随轮数平方涨**。
  实测累计 / 线性基线 = **15.6x**，而理论值 `TURNS/2 = 15`。这就是"多轮对话越聊越贵"的数学本质。
- 延迟同理：单轮 196 ms → 4,706 ms，累计 74.1 s。**用户感知到的"越聊越慢"就是 prefill 长度在涨。**
- 注意这只是 30 轮。轮数翻倍，累计成本翻 4 倍。

### 2. 冗余：三成 token 是零信息量

| 冗余来源 | token | 占比 |
| --- | --- | --- |
| 工具信封样板 ×30（每轮返回同一段 schema/免责声明） | 5,370 | 25.9% |
| 重复检索片段（同一份文档被检索进来 5 次） | 940 | 4.5% |
| 废弃的中间推理（已被推翻的旧结论留在历史里） | 592 | 2.9% |
| 重复寒暄（每轮都是同一句开场） | 360 | 1.7% |
| **合计** | **7,262** | **35.0%** |

而 token 花在哪？**tool = 66% / doc = 21% / answer = 7%**，真正约束模型的 `system` 只占 **0.1%**。
换句话说：**你在为一个 20,000 token 的 prompt 付钱，其中只有几个 token 在定义"什么是对的"。**

### 3. 污染：两类问题各自独立地让答案变错

**(a) lost in the middle** —— 把 3 条关键约束埋在正中间，再堆无关内容，关键事实召回率：

| 目标上下文 token | 实际 token | 约束在**头部**·召回率 | 约束在**中间**·召回率 | 中间位置损失 |
| --- | --- | --- | --- | --- |
| 500 | 514 | 0.62 | 0.39 | 38% |
| 2,000 | 2,019 | 0.59 | 0.34 | 43% |
| 8,000 | 8,003 | 0.40 | 0.25 | 38% |
| 16,000 | 16,012 | 0.34 | 0.21 | 37% |
| 32,000 | 32,020 | 0.18 | 0.09 | 50% |

两件事同时发生：**上下文越长，召回率越低（0.62 → 0.18）；同样的内容放在中间，比放在头部再低一档（→ 0.09）。**

**(b) 旧结论污染** —— 历史里留着一段已废弃的判断（"根因是缓存穿透，与连接池无关"），
它被读取器注意到的概率是 0.182，而**正确**决策被注意到的概率是 0.220：

`[BROKEN-REPRODUCED] 历史里的废弃结论仍有 45.3% 概率把模型带偏`

> 40% 以上的概率答错，而这段文字**从头到尾没有任何作用**——它是纯负债。

## 根因分析

1. **上下文是一个只增不减的数据结构。** 大多数 agent 循环写的是 `messages.append(...)`，
   从来没有 `messages` 的回收路径。token 成本 = Σ 每轮的 prompt 长度 = O(N²)。

2. **工具返回的是"接口响应"，不是"给模型看的信息"。** 真实工具响应里 60%+ 是信封、
   schema、分页、限流头、免责声明 —— 这些字段对**调用方代码**有用，对**模型**零信息量，
   却和关键约束争抢同样的注意力预算。

3. **注意力不是均匀的，也不免费。** 位置权重呈 U 型（首尾高、中间低）+ 长度稀释 + 噪声占比，
   三者相乘决定了一个事实能不能被"读到"。内容变多 ≠ 信息变多，往往是信息变少。

4. **历史里同时存在"正确"和"曾经正确"两种内容，而模型分不出来。** 删掉废弃推理是
   **提升**质量的，不是丢信息。

5. **压缩本身有损，而且损失分布极不均匀。** 引用 id、数字这类"低频精确项"最先丢，
   而它们恰恰是最不能丢的（回查靠 ref，校验靠数字）。

6. **"让模型自己注意别太长"不是方案。** 模型看不到自己的 prompt 长度、看不到单价、
   看不到上下文窗口的余量。预算必须由代码算、由代码执行。

## 生产做法

六种技术**真实实现**并逐一对账（同一个 30 轮对话、同一套事实真值集：48 条关键事实 =
7 约束 + 6 决策 + 5 数字 + 30 引用）：

| 技术 | token | 压缩率 | 事实保留率 | 读取召回率 | 有效召回率 | 信息损失 |
| --- | --- | --- | --- | --- | --- | --- |
| T0 v0 全量回灌（无治理） | 20,739 | 0.0% | 1.00 | 0.22 | 0.22 | 丢 0 条 |
| T1 滑动窗口（保头2轮 + 保尾4轮） | 4,060 | 80.4% | 0.50 | 0.54 | 0.27 | 丢 24 条 |
| T2 滚动摘要（抽取式，最近4轮保原文） | 2,901 | 86.0% | 0.42 | 0.60 | 0.25 | 丢 28 条 |
| T3 结构化状态外置 + 最近6轮原文 | 4,308 | 79.2% | 0.88 | 0.69 | 0.60 | 丢 6 条 |
| T4 去重与引用（一轮不丢，只删重复） | 15,015 | 27.6% | **1.00** | 0.23 | 0.23 | **丢 0 条** |
| T5 T3 + 工具结果压缩（摘要 + ref 回查） | 1,991 | 90.4% | 0.85 | 0.83 | 0.71 | 丢 7 条 |
| **T6 分层记忆 + 硬闸门（生产版）** | **1,070** | **94.8%** | **0.85** | **0.88** | **0.75** | 丢 7 条 |

> 「事实保留率」= 压缩后上下文里**仍然存在**的关键事实比例（有损压缩的直接代价）。
> 「读取召回率」= 这些存在的事实里，模型**实际能读到**的比例（位置 + 长度 + 噪声决定）。
> 「有效召回率」= 两者相乘。v0 的保留率是 1.00，但有效召回只有 0.22 —— **东西都在，就是找不到**。

逐条说清代价：

1. **滑动窗口 / 截断（保头保尾）** — 实现最便宜（一个切片），压缩率 80.4%，但事实保留率直接腰斩到 **0.50**：
   中间 24 轮的所有 `ref` 和决策整段消失。**丢中间丢的是"引用可回查性"** —— 后面再想回查原文，
   连 ref id 都没了。适用：纯闲聊、无引用需求的短会话。
2. **滚动摘要（抽取式）** — 按 `MUST/必须/禁止` + `决定:` + 数字 + `ref=` 打分抽句，**不需要 LLM**，
   260 token 摘要覆盖早期 26 轮。保留率 0.42 —— 比窗口差，因为它把**引用 id 也压掉了**。
   代价：摘要会引入"表述漂移"，且无法精确回查。适用：早期轮次只提供背景、不需要精确引用的场景。
3. **结构化状态外置（重点）** — 每轮重写一个 state 对象放在 prompt 顶部：
   `目标 / 已确认事实与约束 / 决策 / 待办 / 可用引用`。**只多花几百 token，保留率从 0.50 跳到 0.88。**
   为什么最有效：它把散落在 30 轮里的**唯一事实集合**收敛成一份去重清单，
   同时天然解决 lost-in-the-middle（关键约束永远在位置 1~2，位置权重最高）。
   代价：state 必须有**上限**（实测 `ref` 上限 24 条，超出按 LRU 淘汰），
   所以 T6 仍丢 7 条（6 个老 ref + 1 个样板数字）；state 超预算时**必须瘦身，不能截断**。
4. **工具结果压缩（摘要 + ref 回查）** — 上下文只放 80 token 摘要 + `ref=tr-NN-3`，原文进
   `ToolResultStore`。压缩率再涨 11 个点而保留率只掉 3 个点。**代价是要付出一次额外查询**
   （实测本 lab 为 0 次，因为 30 轮里没有真正需要回查的时刻 —— 生产上要监控回查率，
   回查率过高说明摘要抽得不好）。
5. **去重与引用** — 两个层次：① 整段重复 → `[ref rN]`；② **段落内部重复的行**
   （工具信封样板 30 份、每轮一样的免责声明）→ 只留第一次出现。**这是唯一"纯赚"的技术：
   保留率 1.00 不降，token 降 27.6%。** 代价：几乎为零，唯一的坑是别把"内容相同但语义不同"的
   东西误判为重复（例如同一句话在两个租户下的含义不同 —— 所以去重必须在租户/会话维度内做）。
6. **分层记忆（短期 / 工作 / 长期）+ 预算分配** — 三层各自有层内预算，最后交给硬闸门：

   | 预算层 | 占比 | 预算 token（总 6000） | 层内内容 | 超预算时的动作 |
   | --- | --- | --- | --- | --- |
   | system | 10% | 600 | 角色 / 硬约束 | 永不丢（pinned） |
   | memory | 20% | 1,200 | 工作记忆 state | state 必须瘦身，禁止截断 |
   | retrieval | 40% | 2,400 | 长期记忆召回 | 按分数从低到高丢 |
   | history | 30% | 1,800 | 最近 N 轮原文 | 保头保尾丢中间 |

   **注意：预算分配是「上限」不是「配额」** —— 用不满的层应把余量让给历史层（动态再分配），
   但任何一层都不能超。实测这个 30 轮会话只用掉 1,070 token，远低于 6,000 预算。

### 硬闸门与降级顺序（这一条必须硬编码）

`fit_to_budget(texts, budget, keep_tail=1)` 是最后一道闸门：把可丢内容按**优先级从低到高**
排列成一个列表，它从尾部往前保留，超出预算的部分自然被丢掉。
**顺序由代码里列表的位置决定，和 LLM 无关：**

| 顺序 | 丢什么 | 为什么是这个顺序 |
| --- | --- | --- |
| 1 | 废弃推理 / 重复片段 / 工具样板 | 零信息量，丢了不产生任何损失 |
| 2 | 滚动摘要 | 有损层，最老的信息，丢了还有 state 兜底 |
| 3 | 长期记忆召回片段 | 按相关度分数从低到高丢，当前问题相关度最高 |
| 4 | 工具结果原文（保留摘要 + ref） | ref 可回查，信息没有真丢 |
| 5 | 中间轮次原文（保头保尾） | 头是任务定义、尾是当前进展 |
| 6 | 最近 N 轮原文 | 最后才动 —— 动了就等于丢工作记忆 |
| **pinned** | **system / 结构化 state / 当前问题** | **永不截断：截它等于改需求或改约束** |

预算阶梯实测（同一个会话，只改预算）：

| token 预算 | 实际 token | 事实保留率 | 有效召回率 | 约束/决策/引用 保留 | 硬闸门动作 |
| --- | --- | --- | --- | --- | --- |
| 4,000 | 1,070 | 0.85 | 0.75 | 1.00 / 1.00 / 0.80 | 预算内，未触发降级 |
| 2,000 | 915 | 0.85 | 0.75 | 1.00 / 1.00 / 0.80 | 历史层预算 600 → 丢 1 段 |
| 1,500 | 776 | 0.85 | 0.75 | 1.00 / 1.00 / 0.80 | 历史层预算 450 → 丢 4 段 |
| 1,100 | 661 | 0.85 | 0.73 | 1.00 / 1.00 / 0.80 | 历史层预算 330 → 丢 7 段 |
| 800 | 591 | 0.85 | 0.75 | 1.00 / 1.00 / 0.80 | 历史层预算 240 → 丢 8 段 |
| 500 | 509 | 0.85 | 0.67 | 1.00 / 1.00 / 0.80 | 历史层预算 150 → 丢 11 段 |

规律：**预算越紧，有损压缩越早介入，但「约束 / 决策」的保留率始终是 1.00**，因为它俩在 pinned
的 state 里；掉的是引用（本来就受 LRU 上限约束）。**这就是为什么降级顺序必须硬编码 ——
如果让模型决定先丢什么，它很可能先丢掉那句"禁止在生产开启 debug"。**

### 压缩质量代价（本 lab 最重要的输出）

| 视角 | v0 无治理 | v1 治理后 | 说明 |
| --- | --- | --- | --- |
| 事实保留率（在不在） | 1.000 | 0.854 | **-14.6%，这就是压缩的代价** |
| 读取召回率（找不找得到） | 0.224 | 0.880 | +293% |
| 有效召回率（乘起来） | 0.224 | 0.750 | +234% |
| 可覆盖率（含 ref 回查） | 0.854 | **1.000** | 丢的 7 条里 6 条是 ref，原文还在 store 里 |

**结论：外置 ≠ 丢失。** 那 6 条老 ref 只是不在常驻上下文里，原文仍在 `ToolResultStore`，
需要时一次查表就能拿回来。所以真正的"信息损失"只有 1 条（样板里的 `60s`）——
而那是我们**故意**丢掉的噪声。

## 常见错误认知

1. **"找个摘要模型把历史压一压就行了。"**
   错。实测纯摘要（T2）保留率只有 **0.42**，比滑动窗口还差 —— 它把数字和引用 id 一起压没了。
   摘要应该只压"叙述性历史"，**关键事实要走结构化 state**（T3 保留率 0.88）。

2. **"压缩率越高越好。"**
   错。T1 压缩 80.4% 但保留率 0.50，T4 只压缩 27.6% 但保留率 1.00。
   **只看压缩率会系统性偏向"压得最狠、答得最错"的方案。** 必须成对看压缩率 + 保留率。

3. **"把原文都删了就是省 token。"**
   错。正确做法是**外置 + 引用**，不是删除。原文进 `ToolResultStore`，上下文只放摘要 + `ref`，
   需要时回查。实测 T6 的「可覆盖率（含 ref 回查）」是 1.000 —— 信息一条没丢。

4. **"让模型自己判断哪些内容重要、该丢什么。"**
   错。降级顺序必须硬编码（见上面的阶梯表）。模型看不到 token 预算、看不到单价、
   也不知道 `system` 里的安全约束丢了会造成什么后果。**模型可以建议，不能决定。**

5. **"给足上下文窗口就行，128k 不用治理。"**
   错。lost-in-the-middle 实测：32,000 token 时中间位置召回率只有 **0.09**。
   窗口大只是让你**塞得进去**，不保证模型**读得到**。而且 128k 的 prefill 成本是实打实的。

6. **"压缩是纯收益，没有代价。"**
   错。事实保留率 `1.000 → 0.854` 就是代价。工程上要做的是：
   把代价压到"只丢噪声"，并把丢掉的每条都记进指标（本 lab 的 `FactChecker.missing()`），
   让"这次压缩丢了什么"可审计。
