# agent 在批处理任务的时候，CPU 和内存瞬间打满，这类问题如何解决？

> 对应实验：`labs\lab_17_batch_resource.py` · 运行：`python -m labs.lab_17_batch_resource`

## 一句话答案

批处理打满 CPU/内存，根因几乎从来不是"算得慢"，而是**没有边界**：没有内存边界（一次性
加载）、没有并发边界（一次起几百个任务）、没有队列边界（无界缓冲）、没有优先级边界
（批处理和交互式抢同一份资源）。工程解法是给每一维都装上闸门并观测它：**chunked 流式**
把内存峰值从 O(数据量) 降到 O(chunk)；**Bulkhead 舱壁 + 容量预留（70/30）** 把并发闸住，
给交互式留余量；**CPU/IO 分池**（CPU 池 = 核数）避免 IO 任务排在 CPU 后面干等；
**有界队列 + 背压**（满了阻塞或拒绝）；**小任务按 token 预算合并**降本提吞吐；
**可取消标志**让批处理能被抢占；最后用 **ResourceSampler** 把 RSS/线程/队列/CPU
打成时间序列 —— 这才是"如何发现被打满"的答案。

## 先复现：不做防护会发生什么

lab 用真实测量复现了 4 类"打满"（数字均为实测）：

| 故障 | 复现方式 | 实测 |
| --- | --- | --- |
| 一次性加载 | 30k × 2KB 记录全读进内存，再复制一份中间结果 | RSS 增量 **110MB**；曲线 12→23→36→47→59→110MB；外推 100 万条 **3.6GB → OOMKilled** |
| 无并发上限 | 一次丢 240 个任务（200 线程）打 provider | 线程峰值 **226**，provider 排队峰值 32，**429 共 114 次 / 实际调用 530 次**（重试风暴把调用量放大 2.2×），任务延迟 p95 **241.9ms** |
| CPU 与 IO 同池 | 16 个 CPU 密集后处理 + 24 个 IO 任务共用一个 4 worker 线程池 | IO 任务 P95 被拖到 **597ms**（分池后 126ms）|
| 大对象 + GC | 每个任务造一个带引用环的 ~0.7MB 临时上下文 | GC **240 次 / 38ms**，峰值 +22MB |

故障传导链：**一时冲动 → 提交全部任务/读入全部数据 → 线程数与 RSS 同步骤增 → provider
队列打满 → 429 → 重试 → 调用量再翻倍 → 交互式请求排在队尾 → P95 爆炸**。
内存那条线更狠：容器里超过 memory limit 不是变慢，是内核直接 SIGKILL。

## 根因分析

1. **内存峰值由"驻留集合"决定，而不是由"数据总量"决定**。`list(make_records(n))` 让整批
   数据同时驻留；再叠一份"中间结果"（本 lab 里 `staging`）就是 2×。OOM 看的是峰值，
   不是平均值。
2. **线程数 ≈ 并发数 ≈ 资源占用**。每个线程都有栈 + 请求上下文（prompt、中间结果）；
   一次起 200 个线程，等于把 200 份上下文同时按住在内存里。**无界排队 = 无界内存**。
3. **CPU 密集与 IO 密集混在一个池子里，是排队问题不是算力问题**。CPU 任务占住 worker，
   IO 任务即使只需要 40ms 也要排在后面等 —— 实测被拖到 597ms。注意 GIL：纯 Python 的
   CPU 逻辑分池只能解决"排队"，**不能解决"并行"**；本 lab 的后处理用 `zlib` / `hashlib`
   这类会释放 GIL 的 C 实现才是生产上的真实形态。
4. **引用环让 GC 真的有事可做**。没有环的对象靠引用计数立刻回收，GC 几乎不花时间；而
   agent 的任务上下文（traceback、闭包、回调、parent/child 互指）天然带环，只能等 GC ——
   这才是 GC 停顿的来源。
5. **没有资源观测，就只能靠猜"卡住了"**。看不出是线程爆了、队列积压了，还是 CPU
   时间斜率已经打满。

## 生产做法

### 1. 流式 / 分页处理（chunked）

- **做什么**：`chunked(iterable, size)` 生成器，一次只驻留一个
  chunk；中间结果只保留聚合值。
- **为什么**：内存峰值从 O(数据量) 变成 O(chunk_size)，与总数据量解耦。实测峰值 **110MB
  → 0.8MB（-99.3%）**，GC 时间 37.9ms → 0.1ms。
- **代价/边界**：不能做需要全局信息的操作（全局排序、全局去重、跨 chunk 聚合）；
  失败重试要按 chunk 粒度设计（幂等键）；chunk 太小会让调用/事务次数上升，要按"单条大小
  × 并发数 ≤ 内存预算"反推 chunk_size。

### 2. 并发闸门 + 容量预留

- **做什么**：`Bulkhead(limit=BATCH_LIMIT)` 限制批处理并发；容量按 70/30 分给批处理与
  交互式；闸门满时批处理**有界等待**（可等），交互式**快速失败**（不能等）。
- **为什么**：批处理和交互式抢同一份下游容量时，批处理永远赢（它可以无限排队），
  结果就是交互式 P95 被打穿。预留是唯一能保证交互式 SLO 的做法。实测：交互式 P95
  **1073ms → 453ms（-57.8%）**，线程峰值 **226 → 34（-85.0%）**，429 **114 → 0**。
- **代价/边界**：预留的那部分容量在批处理高峰时是"闲置"的，整体吞吐会下降；70/30
  要按业务 SLO 调，并且要有"交互式空闲时把预留借给批处理"的动态机制
  （borrowing），否则利用率会长期偏低。

### 3. CPU / IO 分池

- **做什么**：CPU 池大小 = `os.cpu_count()`，IO 池单独设置（可以更大，因为 IO 等待不占
  CPU）。
- **为什么**：两类任务的资源模型完全不同：CPU 任务占着 worker 不放，IO
  任务大部分时间在等。同池就等于让 IO 去排 CPU 的队。实测 IO P95 **597ms →
  126ms（-78.9%）**。
- **代价/边界**：池子变多，总线程数上限上升（要各自设上限，否则"分池"变成"多开"）；纯
  Python 的 CPU 逻辑受 GIL 限制，要真多核并行必须上**进程池**或释放 GIL 的 C 实现，
  代价是序列化开销与部署复杂度。

### 4. 背压：队列必须有界

- **做什么**：有界队列（上限 ≈ 2× 并发）；满时先阻塞、超时则拒绝，并打点。
- **为什么**：无界缓冲只是把 OOM 推迟几分钟，同时把延迟无限拉长（每个排队的请求都带着
  自己的 prompt 和中间结果占内存）。实测缓冲深度 **120 → 8**，触发背压 112 次。
- **代价/边界**：背压会把压力**传导回上游**（生产者被阻塞或收到拒绝），
  上游必须能处理"被拒绝"（重试/降级/丢弃），否则只是把故障点前移。

### 5. 批量合并小任务

- **做什么**：把小任务按 token 预算（≤4k tokens）合并成一次 LLM 调用（本 lab 3 条合 1
  次）。
- **为什么**：每条消息的结构开销（system prompt、格式模板、role 标记）被摊薄，调用数从
  144 降到 60，吞吐 **85.2 → 126.6 条/s（+48.6%）**，成本
**$0.001305 → $0.000552（-57.7%）**。
- **代价/边界**：单批失败会放大影响面（一批 3 条全废），需要"拆批重试"；
  批量会拉长单次延迟（首条要等整批凑齐），所以要设"凑批超时"（等 50ms 或凑满即发）。

### 6. 可中断与优先级

- **做什么**：`cancel` 标志 +
  协作式检查（每个任务在开始/关键点检查）；支持暂停/取消/抢占。
- **为什么**：批处理必须能给交互式和 SLO 让路，否则它会把整个系统拖死。实测 64 个任务在
  90ms 时取消：32 个完成、32 个被取消，墙钟 0.20s → 0.10s。
- **代价/边界**：协作式取消要求每个任务执行体都检查标志（不可中断的 C 调用、阻塞 IO
  仍然会跑完）；取消后要保证**幂等与清理**（已产生的副作用、已计费的成本）。

### 7. 资源观测：ResourceSampler

- **做什么**：后台线程定期采样 `RSS / 线程数 / 队列深度 / CPU 时间`，打印时间序列表。
- **为什么**：这是"如何发现被打满"的唯一答案 —— CPU 时间列的斜率 ≈ 核数×1000ms/s 就是
  CPU 饱和信号；线程列说明是不是无界并发；队列列说明是不是积压。
- **代价/边界**：采样本身有开销（要选对间隔，本 lab 用 0.08~0.12s）；
  单机采样不够，生产要落到 metrics 系统（counter/histogram）并配阈值告警。

资源治理参数表（本 lab 核心交付物）：

| 参数 | 建议值 | 依据 | 超了会怎样 |
| --- | --- | --- | --- |
| chunk_size | 500 条（≈1MB）| 单 chunk 内存 × 并发数 ≤ 内存预算 | 峰值内存线性上涨 → OOM |
| 批处理并发上限 | 容量的 70%（本 lab 14/20）| 给交互式留 30% 容量 | 交互式 P95 被拖垮 |
| cpu pool size | `os.cpu_count()` | CPU 密集受核数 + GIL 限制 | 上下文切换开销上升，吞吐不涨 |
| io pool size | 4× 核数 / 并发预算 | IO 等待不占 CPU | 线程暴涨，栈内存吃光 |
| 队列上限 | 2× 并发（≈32）| 背压：满则阻塞或拒绝 | 无界缓冲 = 延迟与内存双爆 |
| 单任务内存上限 | 8MB，buffer/上下文复用 | 短生命周期大对象 = GC 压力 | GC 停顿 + 峰值翻倍 |
| LLM 调用超时 | 1.5s（P99 附近）| 孤儿线程仍占并发槽、照样计费 | 槽位被慢调用占死 |
| 批合并 token 预算 | ≤4k tokens/批 | 模型上下文 + 单批失败代价 | 单批失败放大成本与重试 |

## 常见错误认知

1. **"内存不够就加内存 / 调大 memory limit"** —— 错。峰值随数据量线性上涨，加内存只是
   把事故推迟；必须先把 O(数据量) 改成 O(chunk)。
2. **"任务全丢进线程池，反正有队列"** —— 错。无界队列 = 无界内存 + 无界延迟。
   队列必须有上限，满了要背压（阻塞或拒绝）。
3. **"CPU 密集和 IO 密集用一个池，池子开大点就行"** —— 错。池子开大只是让更多请求
   一起排队；两类任务的排队语义不同，必须分池。另外纯 Python 的 CPU 逻辑受 GIL 限制，
   分池解决排队、不解决并行。
4. **"批处理是内部的，不用管交互式 SLO"** —— 错。它们共享同一份下游容量与同一台机器，
   批处理会把交互式拖垮。必须做容量预留与优先级。
5. **"取消（cancel）不重要，跑完就行"** —— 错。没有取消能力，一次误提交就要等几小时，
   期间所有资源被占死；而且取消失败会造成重复副作用，必须做幂等。
6. **"内存看平均值就够了"** —— 错。OOM 由**峰值**决定；而且容器里超限是直接杀进程，
   没有"慢慢变慢"的缓冲期。
