# 高并发下会如何解决 LLM 接口限流的问题？多用户并发，如何避免一个租户打满全局配额？

> 对应实验：`labs\lab_04_rate_limit_fairness.py`
> 运行：`python -m labs.lab_04_rate_limit_fairness`（约 2s，真实墙钟 + 虚拟时钟混合）

## 一句话答案

限流不是"加一个全局 QPS 上限"，而是**四层闸门 + 有租户维度的排队**：入口全局限流保护
自己、每租户配额做隔离、每模型/每 provider 限流保护上游、每工具限流保护下游；队列用
WFQ（加权公平队列）替代 FIFO，让请求多的大租户无法把小租户挤到队尾；服务端超限返回
429 + `Retry-After`（不是 500），客户端读它做全抖动退避，两边都要限流。实测同一份负载下
小租户成功率 94% → 100%、P95 1971ms → 999ms，代价是上游总调用次数 +157%、
大租户 makespan 1.98s → 6.22s —— **公平性是用吞吐和批处理时长换来的，这就是它的价格。**

## 先复现：不做防护会发生什么

实验里 6 个租户共用"一个配额 + 一条 FIFO 队列 + 一个舱壁"：`tenant-big`（批量任务）在
t=0 一次性甩出 300 个请求，5 个小租户各 20 个交互请求稍后到达。

| 观测项 | v0（全局共享 + FIFO） | v1（四层限流 + WFQ） |
| --- | --- | --- |
| 小租户平均成功率 | 94.0% | 100.0% |
| 大租户成功率 | 99.3% | 100.0% |
| 小租户最差 P95 | 1971ms | 999ms |
| Jain 公平指数（成功率口径） | 0.2828 | 0.2899 |
| Jain 公平指数（P95 倒数口径） | 0.9827 | 0.8330 |
| provider 稳态在飞 P95 | 44.6 | 34.5 |
| provider 峰值在飞 / 排队 | 47 / 1（上限 48 / 24） | 47 / 1 |
| 上游总调用次数（含重试） | 512 | 1316 |
| 大租户 makespan | 1.98s | 6.22s |
| Retry-After 遵守率（429 探针） | 0.000 | 1.000 |

故障是怎么一步步传导的：

1. `tenant-big` 的 300 个请求在 t=0 全部进入 FIFO 队列，把 provider 的并发槽（48）
   和排队位（24）占满，稳态在飞被顶到 P95 = 44.6；
2. 小租户的请求只能排在 300 个批量请求后面，**排队时间由别人的流量决定** ——
   排到队尾的请求还没被派发，客户端 1.5s 预算就已经耗尽，provider 直接返回 `TIMEOUT`；
3. 客户端只能重试，重试又是排到队尾，于是成功率掉到 94%、P95 抬到 1971ms；
4. 失败和超时**照样产生 token 成本**（provider 是先计量再"计算"），越重试越贵。

另一半故障是**限流算法本身选错**。同一份 260 请求的边界突发（t=0.99s 与 t=1.0s 各
130 个请求，limit=100/s）实测：

```
算法                     放行   拒绝   50ms内峰值   = ×limit
固定窗口 100/s           200     60         200       2.0×
滑动窗口 100/s           100    160         100       1.0×
令牌桶 r=100 burst=100   100    160         100       1.0×
漏桶 r=100 queue=10       10    250          10       0.1×
```

固定窗口给 `[0,1)` 和 `[1,2)` 各算一份配额，两次突发**都被放行** —— 上游在 10ms 内收到
2×limit 的流量。这就是"窗口边界双倍突发"，是必须知道的经典坑。

## 根因分析

1. **FIFO 对"请求多的租户"天然有利**。它按到达顺序服务，谁发得多谁占的队头多；
   一个租户的批量任务可以把队列填满，让其他租户的请求排在后面干等。FIFO 不是"公平"，
   它是"按提交量分配资源"。
2. **没有租户维度的舱壁 = 没有多租户**。全局一个并发池时，大租户打满后小租户连
   "快速失败"的机会都没有 —— 只能排队，排到超时。
3. **排队时间算在客户端预算里**。provider 慢慢腾出槽位并不能让客户端原谅你：
   1.5s 预算里如果 1.2s 花在排队上，剩下的时间不够一次真实推理。
4. **限流算法与语义不匹配**。固定窗口便宜但边界漏流量；滑动窗口精确但要存时间戳；
   令牌桶是"稳定速率 + 有界突发"，最贴合配额语义；漏桶只整形、不允许突发。
5. **429 被当成故障**。把 429 转成 500、或者立刻原地重试，等于用更猛的方式撞已经满载的
   上游 —— 重试风暴会把"过载"放大成"雪崩"。
6. **公平性没有度量**。没有 Jain 指数这类指标，"是不是不公平"只能靠感觉，
   容量规划和配额调整都失去依据。

## 生产做法

**1) 四层限流，每层都真实实现并打点**

| 层 | 保护对象 | 本实验配置 | 超限返回 |
| --- | --- | --- | --- |
| L1 入口全局 | 自己（不被打穿） | 600 rps，burst 100 | 429 + Retry-After |
| L2 每租户配额 | 隔离其他租户 | tenant-big 50 rps/burst 8；小租户 100 rps/burst 20 | 429 + Retry-After |
| L3 每模型/provider | 上游配额 | 300 rps，burst 60 | 429 |
| L4 每工具 | 下游脆弱依赖 | 200 rps，burst 40 | 429 |

*为什么*：不同层保护的对象不同，缺一层就有一类故障无处拦截。
*代价/边界*：层数越多每请求判断越多（本实验都是内存计数器，可忽略）；配额必须有变更
流程和审计 —— 否则"临时提额度"会把隔离设计悄悄拆掉；层与层之间的额度要自洽
（L2 之和不能长期大于 L1，否则 L1 会变成事实上的瓶颈）。

**2) WFQ / 轮转排队替代 FIFO**

每个租户维护自己的虚拟时间，只有"该租户当前虚拟时刻最小"的请求才优先派发；请求多的
租户虚拟时间被推远，小租户的请求就能插到它前面。
*为什么*：这是"不饿死小租户"的唯一办法，FIFO 在原理上做不到。
*代价/边界*：实现比 FIFO 复杂；"租户无限多"要让虚拟时间的租户表有界（否则本身就是
泄漏）；权重配置错了会变成事实上的不公平；WFQ 只解决**排队**公平，不解决**配额**公平。

**3) 配额 + 突发：每租户独立 TokenBucket**

`rate` 决定长期平均，`burst` 决定"能不能一口气打一批"。
*为什么*：agent 场景天然有突发（用户点一下触发 10 个工具调用），纯速率限制会误杀正常用法。
*代价/边界*：burst 越大，短时间打到上游的峰值越高；对脆弱下游要用漏桶而不是令牌桶；
burst 的取值要有依据（例如"一次交互最多产生多少个并发调用"），拍脑袋会两头不讨好。

**4) 429 的正确处理（客户端侧）**

```python
except LLMError as exc:
    if exc.code == "429":
        wait = max(backoff_with_full_jitter(attempt), exc.retry_after)  # 读它、用它
        time.sleep(wait)
```

实测遵守率 0.000 → 1.000（服务端用核心 `TokenBucket` 做每租户配额，超限抛带
`retry_after` 的 `LLMError.rate_limited`，与真实 429 语义一致）。
*为什么*：429 是"稍后再来"，不是"我坏了"；服务端知道自己的恢复节奏，客户端不该猜。
*代价/边界*：`Retry-After` 只是建议，上游可能给得偏短；必须有重试预算上限，
否则每个请求各自退避也会累加成风暴。

**5) 限流放服务端还是客户端？两边都要**

服务端限流保护自己（拒绝比排队便宜：排队要占内存、连接和线程）；客户端限流是礼貌 + 省成本
（不打无用请求，也就不为超时和失败付 token 费）。本实验 v1 同时实现服务端四层闸门和
客户端节流队列：拿不到令牌时领一个"最早可放行时刻"排队，而不是原地空转重试。

**6) 用公平指数把"公平"变成可度量的东西**

`J(x1..xn) = (Σxi)² / (n·Σxi²)`，1.0 表示所有租户完全一致。
*为什么*：没有度量就无法验收，也无法在容量规划时回答"加机器之后谁受益"。
*代价/边界*：**必须和绝对延迟一起看**。本实验 P95 倒数口径的公平指数 v0 反而更高
（0.9827），因为大家都被同一个大租户拖慢了 —— 单看公平指数会得出完全相反的结论。

## 落地时的取舍对照（选型用）

| 隔离手段 | 解决什么 | 没解决什么 | 主要代价 |
| --- | --- | --- | --- |
| 全局令牌桶（L1） | 自己被打穿 | 租户之间互相影响 | 突发被削平，正常批量会被误伤 |
| 每租户令牌桶（L2） | 配额被一个租户吃光 | 排队顺序仍然不公平 | 需要配额体系与变更流程 |
| 每租户舱壁（BulkheadSet） | 一个租户占满并发 | 排队时间仍算在别人头上 | 预留容量导致整体利用率下降 |
| WFQ / 轮转排队 | 小租户不被饿死 | 大租户的绝对吞吐会下降 | 实现复杂、要处理租户表上界 |
| 客户端节流 + 退避 | 不打无用请求、省成本 | 不保护服务端（要靠服务端自己做） | 客户端排队会拉长端到端延迟 |
| 滑动窗口 | 窗口边界双倍突发 | 内存按 limit 增长 | 每租户要存 limit 个时间戳 |

结论：**这几种不是三选一，而是要按层叠加**。本实验 v1 把 L1/L2/L3/L4 四层 + WFQ +
客户端节流全用上了，任何单独一层都挡不住"一个租户拖垮全站"。

## 常见追问（面试/评审里最容易被追问的三条）

**Q1：我们只有一个大客户，没有多租户，还需要这套吗？**
需要，只是维度换成"请求类别"：交互式请求 vs 批量任务、前台 vs 后台、付费功能 vs 免费功能。
实验里 tenant-big 的角色就是"批量任务"——它不需要是另一个客户，只需要是**另一个流量类别**。
隔离的本质是"不同 SLO 的流量不要抢同一份资源"。

**Q2：我们已经用了 Kafka/消息队列，是不是就不用管限流了？**
不是。队列解决的是**削峰**（把突发摊平），限流解决的是**准入**（决定谁进、进多少）。
没有准入的队列只会把"立即失败"变成"延迟失败 + 内存增长"；本实验 lab_05 里无界队列
正是这个反例（深度 9431，RSS +13MB）。两者必须配合：队列负责缓冲，限流负责保护。

**Q3：为什么公平指数不能单独作为验收指标？**
因为公平可能是"大家一起慢"带来的。本实验 v0 的 P95 倒数口径公平指数是 0.9827，
比 v1 的 0.8330 还高 —— 但那是因为所有人都在被同一个大租户拖慢。必须和绝对延迟、
成功率一起看，才能判断是不是真的变好了。

## 出问题时的排查顺序（照着做）

1. **先看是不是全局饱和**：`llm_inflight` / `llm_queued` 是否贴住上限？
   是 → 先做 L1 全局限流，别急着调租户配额。
2. **再看是不是某个租户吃满**：把所有指标按 `tenant` 标签拆开，看谁的拒绝率最高、
   谁的调用量占了 80%。一个租户占比异常就是隔离缺失的信号。
3. **再看排队是否公平**：同一时刻各租户的 P95 差异有多大？如果小租户 P95 是大租户的
   几倍，问题在调度器（FIFO）而不是配额。
4. **再看客户端行为**：`retry_total / 成功数` 是多少？如果重试次数接近成功次数，
   说明客户端在无脑重试，先修客户端再谈配额。
5. **最后看算法**：`429` 是不是集中在窗口切换的瞬间？是 → 固定窗口的边界问题。

```
[BROKEN-REPRODUCED] 固定窗口边界 50ms 内放行 200 = 2.0× limit(100)；滑动窗口 1.0×、令牌桶 1.0×
[FIX-APPLIED] 小租户成功率 94% -> 100%；大租户 makespan 1.98s -> 6.22s（配额让它变慢 —— 这就是公平的代价）

[VERIFY] small_tenant_success_rate: 0.940 -> 1.000 (+6.4%)
[VERIFY] fairness_jain_index: 0.2828 -> 0.2899 (+2.5%)
[VERIFY] steady_inflight_p95: 44.6 -> 34.5 (-22.7%)
[VERIFY] small_tenant_p95_ms: 1971 -> 999 (-49.3%)
[VERIFY] retry_after_honored_ratio: 0.000 -> 1.000
[VERIFY] upstream_calls: 512 -> 1316 (+157.0%)        # direction: increase-expected
[VERIFY] batch_makespan_s: 1.98 -> 6.22 (+214.1%)     # direction: increase-expected
```

两条反向断言（`increase-expected`）是设计如此、必须保留的权衡：

- `upstream_calls +157%`：限流把大租户的请求摊开成更多次尝试，小租户因此不再被挤掉。
  这是**用调用量换公平**，不是退化。
- `batch_makespan_s +214%`：按租户公平排队让批处理不再独占资源，总完成时间变长。
  这是**隔离生效的证据**：配额的存在意义就是限制它。

## 常见错误认知

1. **"加一个全局 QPS 上限就够了"** —— 全局配额不解决隔离，大租户照样吃掉全部配额，
   小租户一样拿不到。限流必须**有维度**（租户/模型/工具）。
2. **"用固定窗口最省事"** —— 边界会放过 2×limit（本实验实测 200 > limit 100），
   上游看到双倍突发。要么滑动窗口，要么令牌桶。
3. **"429 就重试，多试几次总能成功"** —— 不读 `Retry-After` 的重试是用更猛的力度撞
   满载的上游；必须有全抖动退避 + 重试预算。
4. **"客户端限流没用，服务端限了就行"** —— 服务端限流会先让请求排队/超时，而这些调用
   **照样计费**；客户端提前不发无用请求，省的是真金白银。
5. **"公平就是让每个人延迟一样"** —— 公平是"份额隔离"：大租户可以慢（makespan 6.22s），
   但小租户不能因为大租户而变慢。把两者混为一谈会做出错误的容量决策。
6. **"限制住了就万事大吉，不用管客户端体验"** —— 被拒绝的请求要给出明确的 429 +
   `Retry-After` 和降级路径，否则客户端只能瞎猜、或者把 429 当故障处理。

## 附：如果要在自己的服务里落地，按这个顺序

1. **先度量**：给每个租户打上 `tenant` 标签，把成功率、P95、拒绝率按租户拆开。
   不拆开就永远发现不了"一个租户拖垮全站"。
2. **再加闸门**：从 L1 全局限流开始（一行令牌桶就够），确认自己不会被打穿。
3. **再做隔离**：加 L2 每租户配额 + 每租户舱壁（`BulkheadSet`），这是投入产出比最高的一步。
4. **再改排队**：把 FIFO 换成 WFQ/轮转（这一步最难，但决定了小租户的 P95 是否可承诺）。
5. **最后做客户端**：读 `Retry-After`、全抖动退避、共享重试预算、把 429 透传给上层。
6. **持续校准**：用公平指数 + 绝对延迟一起看，定期调整各层配额；
   配额调整必须走变更流程，否则隔离会被"临时提额"侵蚀掉。

## 一句话记住这个 lab

> FIFO 按"谁发得多"分配资源，WFQ 按"谁在等"分配资源；
> 多租户隔离的关键不在配额多大，而在**排队和舱壁有没有租户维度**。
