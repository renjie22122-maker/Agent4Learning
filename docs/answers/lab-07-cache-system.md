# 生产环境完整的 agent 缓存体系，哪些数据可以去做缓存，哪些不能做缓存？

> 对应实验：`labs\lab_07_cache_system.py` · 运行：`python -m labs.lab_07_cache_system`

## 一句话答案

缓存要分五层做，每层的 key 维度、TTL、失效方式都必须显式声明：
**L1 精确结果缓存**（key = 规范化 prompt + tenant + model + 参数 + 知识库版本）、
**L2 语义缓存**（词袋/字符 n-gram 相似度 + 阈值 + 实体护栏）、
**L3 前缀缓存**（稳定内容放前、易变内容放后）、
**L4 工具/检索结果缓存**（TTL + 上游版本号）、
**L5 会话状态缓存**（按 session 隔离）。
而"绝对不能缓存"的是一份硬编码清单：**权限/ACL 判定结论、带副作用的写操作、时效数据
（股价/库存/工单状态）、temperature>0 的创作类回答、含 PII 的结果、计费与配额余额**。
判断标准只有一条：**缓存省的是"重复计算"，不是"必须发生的计算"**。
最后一句话是这份答案的重点：**能不能缓存是工程硬编码的决策，不能交给 LLM 判断**。

## 先复现：不做防护会发生什么

本 lab 把"缓存错东西"的五类事故全都跑成了可对账的数字（`python -m labs.lab_07_cache_system`）：

| 事故 | 朴素做法的实测结果 |
| --- | --- |
| key 里没有 tenant | B 租户问同一句话，**越权命中 3 次**，拿到 A 租户的私有文档 |
| 缓存了带副作用的操作 | 3 次真实下单请求被缓存吃掉，**漏执行 3 次**（用户以为下单成功） |
| 没有幂等键 + 客户端重试 | 同一单被下了 3 次，**重复执行 2 次** |
| 缓存时效数据（TTL 300s） | 上游调价后，**9 / 20 次返回了过期报价** |
| 缓存创作类回答 | 6 次请求只产出 3 条内容，**重复回答 3 次** |
| 缓存含 PII 的结果 | **2 次跨用户泄露**（user-B/user-C 拿到 user-A 的手机号） |
| L3 把时间戳放进 system | 前缀缓存命中率 **100% → 0%**，成本 `$0.002354 → $0.008045`（涨 3.4 倍） |
| L2 语义缓存阈值拍成 0.5 | 命中 19 次里**错答 4 次**（错命中率 17%） |

故障是怎么一步步传导的：基线（无缓存）在 150 次请求、16 并发的负载下
P50 = 121.8ms、成本 `$0.018011`；"加缓存"之后命中率 66.7%，
P50 降到 ≈0ms、P95 从 121.8ms 降到 95.4ms（-21.6%）、成本降到 `$0.005992`（-66.7%）、
上游调用从 150 次降到 ≈49 次。**收益巨大，所以大家都会加缓存 —— 也正是因为收益巨大，
加错地方的代价同样巨大**：越权、重复下单、脏数据、PII 泄露，每一条都是生产事故。

## 根因分析

1. **key 的维度 ≠ 所有会影响答案的输入，就会串味/串租户。**
   本 lab 规范化后的 key 是 `sha256(tenant|norm(prompt)|model|params|kb_version)[:16]`。
   实测：同问法不同空白/大小写 → 同 key（`a0cd9c20.. == a0cd9c20..`）；
   同问法不同时间戳/会话 ID → 同 key（`580821ab.. == 580821ab..`）；
   换租户 → 不同 key（`e8a53e69..`）；换参数 `temp=0.9` → 不同 key（`c0ac4eb9..`）。
   少任何一个维度，都会把"别人的答案"发给当前用户。

2. **缓存的是"结果"，但副作用发生在"执行"。**
   把 `帮我下单 商品X 数量1` 的**响应**缓存下来，第二次相同的请求就再也不会真的下单 ——
   缓存把"幂等读"的语义错误地套用到"非幂等写"上。反之，没有幂等键的重试会真的重复下单。

3. **TTL 是"时间上界"，不是"正确性保证"。**
   外部世界的变化与 TTL 无关：TTL=300s、上游 120s 就调价，就有 180s 的窗口在撒谎。
   实测 20 次请求里 9 次返回过期数据。

4. **语义缓存的阈值无法同时保住召回与正确性。**
   这是本 lab 最有价值的量化结论。同义改写的相似度分布是
   `min=0.25 mean=0.54 p95=0.86 max=0.86`；而**跨意图易混对**的相似度是
   `限流配置 ↔ 熔断配置 = 0.600`、`缓存穿透 ↔ 缓存击穿 = 0.500` ——
   最像的跨意图对（0.600）**高于同义改写的均值（0.54）**。
   也就是说：想靠抬高阈值挡住错答，必然连正确命中一起砍掉。
   穿透 vs 击穿只差一个汉字，字符 n-gram 天生分不开。

5. **前缀缓存的命中率由"字节排布"决定，不由模型决定。**
   provider 的前缀缓存语义是"最前面那段连续稳定内容"。把 `当前时间: 2025-03-0XT…`
   拼进 system，前缀就每请求都变 → 命中率 0%；把它挪到消息末尾，命中率 100%。

## 生产做法

### 1）先立一张声明式策略表（本 lab 的核心交付物）

这张表就是"能不能缓存"的工程答案，代码里以 `POLICY` 常量维护、启动时打印，
评审和变更都走它：

```
[L1] FAQ / 固定文档问答最终答案          可缓存        TTL=1h       key=(tenant+model+params+kb_version+norm(prompt))   理由: 少一个维度就串味
[L1] 检索+排序后的候选文档               可缓存        TTL=5m       key=(tenant+groups+query+kb_version)                理由: 权限维度不进 key = 越权
[L2] 语义近邻答案                       可缓存        TTL=15m      key=(tenant+intent+阈值+实体护栏)                    理由: 阈值换召回，护栏防错答
[L3] system+工具定义+few-shot 前缀      可缓存        TTL=provider 侧  key=(前缀字节)                                  理由: 稳定内容放前，易变内容放后
[L4] 只读工具结果（汇率/文档/字典）        可缓存        TTL=60s      key=(tenant+tool+params+上游版本)                   理由: TTL <= 上游刷新周期
[L4] 写操作（下单/发邮件/转账）            ★绝对不可缓存  TTL=-        key=(幂等键（不是 prompt）)                         理由: 副作用不可重放
[L5] 会话短期记忆 / 上下文               可缓存        TTL=会话期     key=(session_id)                                  理由: 会话级隔离，禁止跨会话复用
[L5] 用户长期画像 / 偏好                 可缓存        TTL=1h       key=(tenant+user_id)                              理由: 按用户隔离，注销要失效
[-]  权限 / ACL 判定结论                 ★绝对不可缓存  TTL=-        key=(-)                                          理由: 撤权后仍放行 = 越权窗口
[-]  安全审核 / 内容合规结论              可缓存        TTL=30s      key=(content_hash+rule_version)                   理由: 规则变更必须主动失效
[-]  时效数据（股价/库存/工单状态）          ★绝对不可缓存  TTL=-        key=(-)                                          理由: 缓存即错，只能直读或极短 TTL
[-]  temperature>0 的创作类回答          ★绝对不可缓存  TTL=-        key=(-)                                          理由: 随机性本身就是产品需求
[-]  含 PII / 敏感信息的结果              ★绝对不可缓存  TTL=-        key=(-)                                          理由: 跨用户复用即泄露
[-]  计费 / 配额 / 余额                  ★绝对不可缓存  TTL=-        key=(-)                                          理由: 钱相关必须强一致
[-]  模型路由决策（按 query 特征）         可缓存        TTL=5m       key=(query_shape+策略版本)                         理由: 决策可缓存，但要能一键失效
```

**做什么**：把"可缓存/不可缓存/TTL/key 维度"写成配置，而不是散落在 `if` 里。
**为什么**：缓存策略是**安全边界**，必须可评审、可审计、可一键开关。
**代价/边界**：表本身要维护；新增数据类型时必须强制过这张表（代码评审卡点），
否则新功能会成为绕过边界的后门。

### 2）L1 精确缓存：key 规范化 + 租户隔离 + TTL + LRU

```python
def cache_key(prompt, model, params, tenant, tenant_scoped=True):
    dims = [normalize(prompt), model, params, KB_VERSION]
    if tenant_scoped:
        dims.insert(0, tenant)          # ← 这一行是安全边界，不是优化
    return hashlib.sha256("|".join(dims).encode()).hexdigest()[:16]
```

- **做什么**：`normalize()` 去掉空白、大小写、时间戳、会话/请求 ID；key 带租户。
- **为什么**：同一次逻辑请求会因为无意义变量产生不同 key（命中率掉），
  也会因为少了 tenant 而串租户（事故）。
- **代价**：多一个 hash 与一次字典查找（实测 `cache_lookup_ms` p50 < 0.1ms，可忽略）；
  规范化规则要小心，**别把有意义的差异也抹平**（例如 `temp` 必须进 key）。

### 3）L2 语义缓存：阈值 + 实体护栏（两条腿）

实测取舍曲线（34 条问法、8 个意图）：

| 阈值 | 命中 | 命中率 | 错命中 | 错命中/命中 | +实体护栏后 命中 | 错命中 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.25 | 32 | 66.7% | 7 | 17.9% | 40 | 0 |
| 0.30 | 25 | 52.1% | 9 | 26.5% | 34 | 0 |
| 0.35 | 23 | 47.9% | 6 | 20.7% | 25 | 0 |
| 0.40 | 23 | 47.9% | 6 | 20.7% | 25 | 0 |
| 0.45 | 19 | 39.6% | 5 | 20.8% | 20 | 0 |
| 0.50 | 19 | 39.6% | 4 | 17.4% | 20 | 0 |
| 0.60 | 17 | 35.4% | 1 | 5.6% | 17 | 0 |

- **做什么**：阈值只负责"召回"，正确性交给**实体护栏** —— 缓存项记下自己的领域实体集，
  新 query 的实体集必须与它"可比"（互为子集）才允许复用。
- **为什么**：穿透/击穿、限流/熔断这类同形异义靠相似度永远分不开。
- **代价**：需要维护一份领域词表（本 lab 用 `DOMAIN_TERMS`）；护栏会拒绝一部分
  本来能命中的改写（实测在 0.3 阈值下仍保住 34 次正确命中，说明代价可接受）。

### 4）L3 前缀缓存：把稳定内容放前面

- **做什么**：顺序固定为 `system（角色+规则+工具定义+few-shot） → 固定知识库前言 →
  会话摘要 → 会话历史 → 用户输入（时间戳放最后）`。
- **为什么**：provider 只缓存"最前面连续的稳定字节"。实测时间戳放 system：
  命中率 0%、p50 42ms、成本 `$0.008045`；放最后：命中率 100%、p50 24ms、成本 `$0.002354`，
  单次请求省下 `10752 / 11056` 输入 token。
- **代价**：前缀必须逐字节稳定 —— 改一个空格就全部失效；**版本化前缀**（前缀里带
  `prompt_version`）可以让失效可控，但每次改版都要重新预热。

### 5）L4 工具/检索缓存：TTL + 主动失效

- **做什么**：key 里带上游版本号 `("quote","sku-1",src["version"])`，同时保留 TTL 兜底；
  上游变更事件直接推失效。
- **为什么**：TTL 是"最坏情况下的兜底"，版本号才是"正确性保证"。实测把版本号放进 key 后，
  过期返回从 9 次降到 0 次，回源只有 3 次（真的变了才回源）。
- **代价**：需要上游提供版本号/更新时间；没有版本号时只能把 TTL 压到刷新周期以内，
  命中率会下降。

### 6）L5 会话状态：会话级隔离

- **做什么**：短期记忆按 `session_id` 缓存，跨会话绝不复用；长期画像按 `tenant+user_id`。
- **为什么**：会话上下文是"最贵的重复内容"，实测每轮重放完整历史 1818 token，
  会话缓存复用后只要 601 token。
- **代价**：会话状态的失效与注销必须联动（用户注销/撤权要立刻失效），详见 lab_08。

## 常见错误认知

1. **"加个 LRU 就行，key 用 prompt 的 hash。"**
   错。没有 tenant → 越权（实测 3 次命中别人的私有文档）；没有 params → 创作类串味
   （`temp=0` 与 `temp=0.9` 混在一起）；没有 kb_version → 知识库更新后继续发旧答案。

2. **"TTL 设短一点就安全了。"**
   错。TTL 只是缩短撒谎窗口，不消除它。实测 TTL=300s 仍有 9/20 次返回过期数据。
   时效数据（股价、库存、工单状态）必须直读或极短 TTL + 主动失效。

3. **"语义缓存把阈值调到 0.9 就万无一失。"**
   错。本 lab 实测：阈值 0.60 时错命中仍有 1 次，而同义改写的命中已经塌到 17 次；
   根本原因是跨意图易混对的相似度（0.600）高于同义改写的均值（0.54）。
   正确做法是阈值管召回、实体护栏管正确性。

4. **"缓存能降 P95。"**
   半错。缓存先把 P50/成本打下来（实测 P50 ≈0ms、成本 -66.7%），
   P95 的收益必须靠"打掉上游排队"才能体现（实测 -21.6%）——
   如果命中率只有 60-70%，P95 仍然落在未命中的那一档里。

5. **"写操作也可以缓存响应，反正有幂等键。"**
   错。缓存的是"响应"，而副作用发生在"执行"上；把响应缓存下来会让真实的第二次下单
   静默消失（实测漏执行 3 次）。写操作的幂等要用**幂等键 + 服务端去重**实现，
   不能用结果缓存实现。

6. **"让 LLM 判断这段内容能不能缓存。"**
   错。这是安全边界，必须是硬编码的声明式表 + 代码评审卡点。LLM 的判断不可审计、
   不可回滚，也无法在事故复盘时解释。
